## 二、关键设计决策

### 2.1 列表中「毕业院校/专业」取哪条教育经历

**结论：取最高学历，学位相同时按 sort_order 升序，使用 `ROW_NUMBER()` 窗口函数。**

一个学生可以有多条教育经历（stu_education 一对多），列表只能展示一行。按学历优先级（博士→硕士→本科→大专→其他）取最高的一条；同学历按 sort_order 取第一条。

**SQL实现**（ROW_NUMBER 派生表 LEFT JOIN，保证 schoolName/major 来自同一行）：
```sql
LEFT JOIN (
    SELECT student_id, school_name, major, degree,
           ROW_NUMBER() OVER (
               PARTITION BY student_id
               ORDER BY FIELD(degree, '博士','硕士','本科','大专','其他'), sort_order ASC
           ) AS rn
    FROM stu_education WHERE del_flag = '0'
) edu ON s.student_id = edu.student_id AND edu.rn = 1
```

**被淘汰方案**：两个独立标量子查询分别取 schoolName/major——可能取到不同行的数据，产生"清华大学 + 计算机"(实际是北航计算机+清华数学)的错位数据。

### 2.2 排序实现

**结论：后端排序，Controller 白名单校验，HashMap映射列名，静默降级默认值。**

- 前端传 `sortField`(schoolName/major/createTime)和 `sortOrder`(asc/desc)
- Controller 层白名单校验：`Set.of("schoolName","major","createTime")`
- 非法值静默降级为默认排序 `create_time DESC`（不返回错误，避免给攻击者信息）
- Mapper 用 `@Select` 注解动态 SQL + `${sortColumn}` 拼接（仅经白名单校验后的值传入）

**被淘汰方案**：`LambdaQueryWrapper`——不支持 JOIN+子查询+派生表；前端排序——列表数据经SQL子查询计算得出，前端无原始数据。

**排序列映射表**：

| sortField | SQL ORDER BY 列 | 说明 |
|-----------|----------------|------|
| schoolName | `edu.school_name` | 教育经历派生表 |
| major | `edu.major` | 同上 |
| createTime | `s.create_time` | stu_user 表 |

### 2.3 详情页展示范围

**结论：基本信息 + 教育经历 + 实习/项目经历 + 简历附件 + 投递历史（最近）。只读展示，不做编辑。**

| 区块 | 数据来源 | 说明 |
|------|---------|------|
| 基本信息 | stu_user + stu_profile | 含完整手机号（不脱敏）、性别、出生日期、邮箱、现居城市 |
| 教育经历 | stu_education | 全部记录，按 sort_order 升序 |
| 实习/项目经历 | stu_internship | 全部记录（P1 预留，若表无数据则隐藏卡片） |
| 简历附件 | stu_resume_file | 当前版本附件（is_current='1'） |
| 投递历史 | app_application + job_position | 最近 5 条，按 apply_time 降序 |

**不包含**：HR内部备注（属简历管理域）、附件在线预览（属简历管理域，可提供下载链接）。

### 2.4 手机号脱敏

**结论：列表保持脱敏(138****1111)，详情展示完整手机号。**

详情页是 HR 联系学生的核心场景，脱敏后失去核心价值。用独立 Mapper 方法查详情（天然返回完整值），不做"开关控制脱敏"的复杂逻辑——消除"某处忘记传参数就泄露"的风险。

### 2.5 鉴权

**结论：与列表权限一致，两角色均可查看。** 学生管理挂在系统管理菜单下，当前就是两角色可见（menu_id=15 两个角色都绑定了），详情接口不额外收紧即可。

## 四、API 设计

### 4.1 修改 `GET /api/admin/students/list`

**新增参数**：

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| sortField | String | 否 | createTime | schoolName / major / createTime |
| sortOrder | String | 否 | desc | asc / desc |

**Controller 白名单校验**：
```java
private static final Map<String, String> SORT_COLUMN_MAP = Map.of(
    "createTime", "s.create_time",
    "schoolName", "edu.school_name",
    "major", "edu.major"
);
// 校验 → 映射 → 传入 Mapper
```

**SQL 改造**：新增教育经历 ROW_NUMBER() 派生表 LEFT JOIN + 动态 ORDER BY（`${safeColumn}` `${safeOrder}`，仅白名单校验后的值）。email 列从 SELECT 列表中移除。

**响应示例**：
```json
{"code":200, "data":{"total":86, "rows":[
  {"studentId":1, "phone":"138****1111", "realName":"张三",
   "schoolName":"北京航空航天大学", "major":"飞行器设计与工程",
   "createTime":"2026-08-01 10:30:00", "status":"ACTIVE", "applyCount":3}
]}}
```

### 4.2 新增 `GET /api/admin/students/{id}`

详情接口，鉴权与列表一致（adminFilterChain 认证即可）。

**逻辑**：
1. 查基本信息（stu_user LEFT JOIN stu_profile）→ StudentDetailVO
2. 查教育经历（stu_education WHERE student_id=?）→ List&lt;EducationVO&gt;
3. 查实习/项目经历（stu_internship）→ List&lt;InternshipBriefVO&gt;
4. 查简历附件（stu_resume_file WHERE is_current='1'）→ List&lt;ResumeFileBriefVO&gt;
5. 查投递历史（app_application JOIN job_position，最近5条）→ List&lt;ApplicationBriefVO&gt;
6. **审计埋点**：写入审计日志（参照 ResumeAdminController.auditResumeAccess 模式），操作类型 `VIEW_STUDENT_DETAIL`

**数据一致性**：五次独立查询，非事务一致性快照。对查看场景可接受。此约束在设计文档中标注。

## 五、前端设计

### 5.1 列表页改造（StudentList.vue）

**列调整**（最终列顺序）：
```
ID(80) | 手机号(130) | 姓名(100) | 毕业院校(140, sortable) | 专业(120, sortable) |
注册时间(170, sortable) | 账号状态(90) | 投递数(80) | 操作(220)
```

邮箱列删除。三列添加 `sortable="custom"` + `@sort-change`。

**排序逻辑**：
```js
const query = reactive({
  pageNum: 1, pageSize: 10, keyword: '', status: '',
  sortField: 'createTime', sortOrder: 'desc',
});

function handleSortChange({ prop, order }) {
  if (!order) {
    query.sortField = 'createTime';
    query.sortOrder = 'desc';
  } else {
    query.sortField = prop;
    query.sortOrder = order === 'ascending' ? 'asc' : 'desc';
  }
  query.pageNum = 1;
  fetchList();
}
```

**操作列新增**：「详情」按钮 + 行点击均可跳转详情页。

### 5.2 详情页（新建 StudentDetail.vue）

**布局**：单列全宽卡片（非左右分栏，无嵌入式 PDF 预览需求）。

```
┌──────────────────────────────────────┐
│ [← 返回列表]              张三      │  ← 顶栏（含启用/禁用按钮）
├──────────────────────────────────────┤
│ ┌─ 基本信息 ────────────────────┐   │
│ │ el-descriptions (2列, border)  │   │
│ │ 姓名|性别  手机|邮箱            │   │
```

**组件风格参照** `ResumeDetail.vue`：顶栏返回 + `el-descriptions` 分组卡片 + `el-table`。投递岗位列可点击跳转到简历详情 `recruit/resumes/:applicationId`。

**空数据/错误处理**：
| 状态 | 处理 |
|------|------|
| 加载中 | `v-loading` 覆盖页面 |
| 学生不存在 | `ElMessage.error` + `router.back()` |
| 教育经历为空 | `el-empty` 显示「暂无教育经历」 |
| 投递历史为空 | `el-empty` 显示「暂无投递记录」 |
| 实习/附件为空 | 隐藏对应卡片 (`v-if="length>0"`) |
| 网络错误 | request.js 拦截器统一处理，详情页 catch 中 `router.back()` |

## 六、数据相关决策

### 6.1 不需要 DDL 变更

所有数据来源于现有表（stu_user、stu_profile、stu_education、stu_internship、stu_resume_file、app_application、job_position），不新增表/列/索引。当前数据量（101学生、146教育经历）下排序性能可忽略。

### 6.2 数据现状说明（已知，非本模块引入）

数据探索发现 `stu_education` 表存在数据质量问题（degree 中英文混存、sort_order 96.6% 为 0、重复教育经历），这些问题影响列表"取最高学历"的准确性，但属于独立的数据治理任务，不在本模块修复范围内。本模块的 ROW_NUMBER() 排序逻辑对这些数据做了最佳努力（FIELD 包含所有已知 degree 值包括"其他"）。

## 七、审计埋点（审查发现补充）

学生详情页展示的数据包含教育经历、投递历史等个人敏感信息。参照 `ResumeAdminController.auditResumeAccess()` 模式，详情接口必须在返回前写入审计日志。

```java
// 在 StudentManageController.detail() 方法中
private void auditStudentAccess(Long studentId) {
    AuditResumeAccess log = new AuditResumeAccess();
    log.setOperatorId(AdminUserHolder.getUserId());
    log.setOperatorName(AdminUserHolder.getUsername());
    log.setOperationType("VIEW_STUDENT_DETAIL");
    log.setTargetStudentId(studentId);
    log.setIpAddress(IpUtils.getClientIp(request));
    log.setUserAgent(request.getHeader("User-Agent"));
    // 写入 audit_resume_access 表（复用现有审计基础设施）
    auditResumeAccessMapper.insert(log);
}
```

## 九、关键风险与已知限制

| 风险 | 等级 | 说明 |

| degree 中英文混存 | Medium | 列表"取最高学历"排序可能不准，属既有数据质量问题，非本模块引入 |

| 详情五组查询非事务一致性 | Low | 查看场景可接受，已在文档标注 |
