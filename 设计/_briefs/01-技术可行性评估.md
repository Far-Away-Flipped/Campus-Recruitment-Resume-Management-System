# 技术可行性报告：遨天科技校园招聘简历管理系统

> 评估日期：2026-08-06
> 评估基线：设计简报 V1.0 + 开发需求文档 V1.0

---

## 1. 技术需求分解

| 需求项 | 计算量级 | 数据量级 | 延迟要求 | 现有栈能否支撑 |
|--------|---------|---------|---------|-------------|
| 学生注册/登录（短信验证码） | 极低 | 数千用户 | <3s | 新建项目，无现有栈 |
| 岗位浏览+多条件筛选+关键词搜索 | 低（全文搜索） | 数十岗位 | <1s | 需引入搜索方案 |
| 简历投递（含10MB附件上传） | 低 | 数百~数千份 | <3s | 需文件上传+预览方案 |
| PDF/Word 附件在线预览 | 中（格式转换需要） | 附件≤10MB | <5s 首屏 | **核心难点，需专门方案** |
| 简历列表+多维筛选排序 | 低 | 数千条 | <1s | 数据库索引即可 |
| 简历导出Excel | 低 | 数十~数百条/次 | <5s | 成熟现成轮子 |
| 富文本岗位JD编辑 | 极低 | 数十岗位 | <1s | 成熟前端组件 |
| 到期岗位自动下架 | 极低（定时检查） | 数十岗位 | 分钟级 | 需要调度机制 |
| 权限管理（RBAC） | 极低 | 数个角色/数十HR | — | 成熟框架 |
| 数据报表 | 低（聚合查询） | GB级 | <3s | SQL聚合即可 |

**结论**：所有需求均在单台台式机的计算能力范围内。唯一的工程难点是 **PDF/Word 在线预览**（须解决格式转换与渲染），其余均为成熟通用需求的组合。

## 2. 后端技术栈选型

### 2.1 候选方案对比

| 维度 | Java Spring Boot 3.x | Python Django 5.x | Python FastAPI | Node.js NestJS |
|------|---------------------|-------------------|---------------|----------------|
| 最新稳定版 | 3.4.x (2025-12) | 5.1.x (2025-12) | 0.115.x (2025) | 11.x (2025) |
| 语言版本 | Java 17/21 LTS | Python 3.12+ | Python 3.12+ | Node.js 22 LTS |
| 单机内存占用（空载~业务） | ~250MB~512MB (JVM, -Xmx256m) | ~80MB~200MB (Gunicorn) | ~60MB~150MB (Uvicorn) | ~80MB~200MB (单进程) |
| 启动时间 | ~3-5s (JVM) | ~1s | ~1s | ~1s |
| 国内人才可得性 | **极高**（Java 为国内后端第一语言，招聘市场简历最充足） | 高（Python 全栈开发者多，但 Django 占比下降） | 中高（近几年上升） | 中（Node.js 全栈有但以 Express 为主） |
| ORM 成熟度 | JPA/Hibernate、MyBatis-Plus | Django ORM（内置，成熟） | SQLAlchemy + Alembic | TypeORM、Prisma |
| 后台管理开箱度 | **需自行搭建或基于 RuoYi 等开源框架** | Django Admin 内置（但定制复杂后台体验差） | 需第三方库 | 需自行搭建 |
| 文件上传处理 | Spring MultipartFile + Apache Commons FileUpload | Django FileField（内置） | python-multipart | Multer |
| Excel 导出 | EasyExcel（阿里开源，内存友好） | openpyxl / xlsxwriter | openpyxl | exceljs |
| 权限框架 | Spring Security 6.x + RBAC 模型 **生态最成熟** | django-guardian + 自定义 | fastapi-permissions 等（小） | @nestjs/passport + CASL |
| 中文文档与社区 | **极高**（中文资料数量第一） | 高 | 中高 | 中 |
| 生态成熟度评分 | ★★★★★ | ★★★★☆ | ★★★☆☆ | ★★★☆☆ |

### 2.2 Go 语言补充评估

Go 在运行时性能（内存 ~20-50MB，启动 <0.1s）上碾压上述所有方案，但：
- 国内 Go 开发者在招聘管理后台领域的经验储备远不如 Java；
- 缺乏 Spring Security / Django Admin 级别的开箱安全与后台基座；
- ORM（GORM）相比 JPA/MyBatis 在复杂查询和关系映射上不如成熟；
- 对于本项目（20 并发、GB 级数据）性能优势毫无意义。

**淘汰原因**：生态成熟度不足，人才难找，为不需要的性能牺牲开发效率。

### 2.3 四方案综合打分（满分 50 = 5 维度 × 10 分）

| 维度 | Spring Boot 3 | Django 5 | FastAPI | NestJS |
|------|:--:|:--:|:--:|:--:|
| 单机部署难度与资源占用 | 7 | 8 | 9 | 7 |
| 国内人才可得性 | 10 | 7 | 5 | 5 |
| 生态成熟度 | 10 | 7 | 5 | 6 |
| 学习/接手成本（对新人） | 6 | 8 | 7 | 5 |
| 中文文档与社区活跃度 | 10 | 7 | 5 | 5 |
| **总分** | **43** | **37** | **31** | **28** |

### 2.4 后端推荐结论

**推荐：Java Spring Boot 3.4.x + Java 17 LTS**

理由：
1. **人才可得性绝对第一**：遨天科技作为硬科技企业，现有团队大概率有 Java 背景（航天软件领域 Java 为主流）。即使后续外部招聘，Java 开发者供给远超其他语言。
2. **生态最完整**：文件上传（MultipartFile）、Excel 导出（EasyExcel）、权限框架（Spring Security）、定时任务（@Scheduled）、数据库操作（MyBatis-Plus）全部有久经考验的成熟库。
3. **开源后台基座可选**：可以基于 **RuoYi-Vue3**（若依框架，Spring Boot 3.x + Vue3 + Element Plus 版本，GitHub 20k+ star，Apache 2.0 协议）起步。RuoYi 自带：用户/角色/菜单/部门管理、数据权限、操作日志、代码生成器——这些直接覆盖了系统管理端（A-001/A-002/A-003）的 60% 以上工作量。
4. **内存不是问题**：16GB 台式机，-Xmx512m 足够（实际业务负载下 300-400MB），留 12GB+ 给 OS 和文件转换进程。

备选方案：Python Django —— 如果团队完全不会 Java 但会 Python 则考虑。但 Django Admin 对 HR 端表格筛选、批量操作、自定义导出等场景的定制成本极高（需要大量覆盖 Django Admin 模板），而 Spring Boot + RuoYi-Vue3 组合提供的前后端分离架构恰好胜任这些交互密集型后台。

淘汰 FastAPI 原因：需要从零搭建权限/后台，引入第三方 admin 方案（如 FastAPI-Admin / React-Admin），集成工作量大，且国内人才生态薄弱。

淘汰 NestJS 原因：国内 Node.js 后端以 Express/Koa 为主，NestJS 尚属小众；TypeORM 在复杂关联查询时的表现不如 Hibernate/MyBatis。

## 3. 前端方案选型

### 3.1 三方案对比

| 维度 | 服务端渲染模板（Thymeleaf） | 前后端分离 SPA（Vue3 + Element Plus） | 混合（SSR + SPA 混用） |
|------|--------------------------|--------------------------------------|---------------------|
| HR 端表格交互体验 | 差（每次筛选/翻页需整页刷新） | **优**（局部刷新，即时响应） | 实现复杂 |
| 学生端品牌展示/移动适配 | 中（可做响应式，但动态效果受限） | **优**（现代 CSS/动画，移动端组件现成） | 视情况 |
| 开发效率 | 中（前后端耦合，调试困难） | **高**（前后端并行开发，职责清晰） | 低（两套机制） |
| 部署复杂度 | **低**（单一 JAR） | 中低（Nginx 转发静态资源 + API） | 高 |
| 前后端协作 | 差（模板与后端代码耦合） | **优**（API 契约驱动） | 中 |
| 生态与社区 | 萎缩（Thymeleaf 逐渐边缘化） | **活跃**（Vue3 生态第一梯队） | — |

### 3.2 移动端适配特别讨论

学生门户需支持手机浏览器访问（查看岗位、注册、投递）。Vue3 + Vant UI（有赞开源移动端组件库，中文文档完善，npm 周下载量 50k+）或 Element Plus（自带响应式支持）可覆盖此场景。服务端渲染模板方案需要额外写移动端样式，成本更高。

### 3.3 前端推荐结论

**推荐：前后端分离 SPA —— Vue3 + Element Plus（HR 端）+ 学生门户独立构建**

- **HR 端**：**Vue 3.5.x + Element Plus 2.x + Vite 6.x + TypeScript**。Element Plus 中文文档完善（element-plus.org/zh-CN），对表格、筛选、批量操作、弹窗等后台场景支持最佳。中国开发者群体最大。
- **学生端门户**：同上技术栈，但设计上独立构建产物，使用独立的 Vite 多页面/多应用构建。移动端适配使用 Element Plus 响应式布局 + 媒体查询，如需更佳移动体验可补充 Vant 4.x。
- **UI 组件库明确推荐**：Element Plus（版本 2.9.x，2025-12 发布）。不推荐 Ant Design Vue 的原因：Ant Design 源自 React 设计体系，对 Vue 的适配不如 Element Plus 原生于 Vue 设计理念流畅。Naive UI 等其他 Vue3 组件库虽美观但社区体量远小于 Element Plus。

淘汰 Thymeleaf 原因：现代管理后台的核心交互——多条件筛选、动态表格、拖拽排序、批量操作——服务端渲染方案无法提供流畅用户体验。开发效率和前后端协作也是明显劣势。

## 4. 数据库选型

### 4.1 候选方案对比

| 维度 | MySQL 8.0 LTS | PostgreSQL 16 | SQLite 3 |
|------|:--:|:--:|:--:|
| 单机部署 | `apt install mysql-server` / Windows MSI 安装包 | 类似 | 零部署（单文件） |
| 内存占用（空载） | ~400MB | ~300MB | ~5MB |
| 并发写入能力 | 优秀（行级锁） | 优秀（MVCC） | **差（库级锁，写入串行）** |
| 备份工具 | mysqldump / Percona XtraBackup | pg_dump / pg_basebackup | `cp` 复制文件即可 |
| 全文搜索 | 内置 FULLTEXT（ngram 中文分词） | 内置 tsvector + zhparser 插件 | FTS5（需编译启用，中文需分词） |
| 国内使用率 | **第一**（所有云厂商默认支持） | 快速增长 | 极少用于 Web 后端 |
| 社区中文资源 | **极丰富** | 丰富 | 少 |
| Windows 原生支持 | **官方 MSI 安装包 + Workbench GUI** | 官方安装包（但生态工具 Windows 支持偏弱） | 无安装概念 |
| JDBC/MyBatis 适配 | 最成熟 | 成熟 | 不适用于独立服务 |

### 4.2 推荐结论

**推荐：MySQL 8.0 LTS（具体版本 8.0.41+）**

理由：
1. MySQL 8.0 的 FULLTEXT 索引 + ngram 分词器（`WITH PARSER ngram`）可直接满足岗位名称/描述的关键词搜索需求，**无需引入 Elasticsearch**。
2. Windows 上 MySQL 8.0 有官方 MSI 安装包 + MySQL Workbench GUI 管理工具，运维友好。
3. 备份：一行 `mysqldump -u root -p --single-transaction --routines --triggers recruitment > backup.sql` 即可全量备份，配合 Windows 任务计划每日执行。
4. 数据规模数百~数千份简历，单表数据万行级，单机 MySQL 足以支撑，无需读写分离或分库分表。

**单机资源配置建议**：MySQL 8.0 配置 `innodb_buffer_pool_size = 512M`，在 16GB 台式机上余量充足。

淘汰 PostgreSQL：功能强大但在 Windows 上的生态工具（pgAdmin 稳定性、插件编译）不如 Linux 顺畅，且对国内运维人员的学习门槛稍高。本项目不需要 PG 的高级特性（JSONB、PostGIS、窗口函数等）。

淘汰 SQLite：库级写入锁在 20 并发下会形成明显瓶颈，不适合多用户 Web 应用。

## 5. 文件存储选型

### 5.1 候选方案对比

| 维度 | 本地文件系统 | MinIO（自建对象存储） | 云 OSS（阿里云 OSS） |
|------|:--:|:--:|:--:|
| 部署复杂度 | **零（直接用磁盘）** | 需额外安装配置 MinIO 服务 | 需外网访问、计费、配置 |
| 鉴权下载 | 由应用层控制（控制器拦截 + 文件流返回） | 支持 presigned URL | 支持 STS 临时授权 |
| 单机可靠性 | 依赖磁盘 + 备份策略 | 自带纠删码 | 云厂商 SLA |
| 成本 | **免费** | 免费（开源版） | 按量计费 |
| 运维负担 | 无额外服务 | 多一个需维护的进程 | 依赖外网 |
| 存储上限 | 磁盘大小（台式机至少 256GB SSD） | 同 | 按需扩容 |

### 5.2 推荐结论

**推荐：本地文件系统（应用服务器本地磁盘）**

理由：
1. 每份附件 ≤10MB，每届 1000 份简历 × 10MB = 10GB，加上附件原件和新上传，一个招聘季数据量不超过 20GB。台式机 256GB+ SSD 绰绰有余。
2. 鉴权下载由应用层实现：文件存储在 `E:\recruitment-files\resumes\{year}\{uuid}.pdf`，访问通过控制器校验用户身份后读取文件流返回，URL 不可猜测（UUID 文件名）。
3. **内网部署场景下本地存储是最简方案**——不需要额外安装配置任何存储服务。
4. 备份：`robocopy` 或 `rsync` 定期同步文件目录到备份盘/USB/网络位置，与数据库备份脚本一起执行。

淘汰 MinIO：虽然 MinIO 单机部署也很轻量（一个二进制文件），但对于 GB 级数据、20 并发的场景，引入对象存储是典型的 **over-engineering**。MinIO 的价值在于横向扩展和大文件高并发分发，本项目完全不需要。

淘汰云 OSS：遨天科技明确要求支持内网部署，云 OSS 依赖外网访问不适合内网环境；且引入外部计费服务增加了不必要的复杂度。

## 6. 中间件裁决：必要 vs 不必要

对每个中间件给出**明确"要"或"不要"**的裁决。

### 6.1 Redis —— **不要**

**一句话论证**：20 并发下 MySQL 的查询缓存和应用层 Caffeine 本地缓存足以满足性能需求；引入 Redis 会增加一个独立进程的运维负担（安装、配置、持久化 RDB/AOF、内存管理），且会成为系统单点故障源。

具体替代：
- **会话管理**：Spring Session + JDBC（MySQL 存储），不使用 Redis。
- **验证码存储**：MySQL 表 `sms_codes`（含过期时间字段），定时清理。
- **高频读取缓存**：Caffeine（JVM 内本地缓存，零配置），用于岗位列表、部门列表等。
- **登录失败限流**：Guava RateLimiter 或 Spring 自定义拦截器 + MySQL 计数。

**不引入会怎样**：在 20 并发下，MySQL 直接查询的响应时间在 10-50ms，远远不需要缓存层。

### 6.2 消息队列（RabbitMQ/Kafka） —— **不要**

**一句话论证**：项目没有异步解耦需求（不需要通知多系统、不需要削峰填谷、不需要事件溯源）。短信发送是同步调用外部 API，投递成功/失败即时返回即可。

**不引入会怎样**：同步调用短信 API（响应时间 200-500ms）在 20 并发下完全可接受。如果将来需要异步发送短信通知（P2），用 Spring `@Async` + 线程池即可，不需要独立 MQ。

### 6.3 Elasticsearch —— **不要**

**一句话论证**：MySQL 8.0 的 FULLTEXT 全文索引 + ngram 中文分词器，对于数十个岗位描述的关键词搜索完全够用，且维护成本为零；ES 需要额外 1-2GB 内存的 Java 进程，极大的运维负担，性价比为零。

具体方案：
```sql
ALTER TABLE job_positions ADD FULLTEXT INDEX ft_title_desc (title, description) WITH PARSER ngram;
SELECT * FROM job_positions WHERE MATCH(title, description) AGAINST('电源 研发' IN BOOLEAN MODE);
```

**不引入会怎样**：MySQL FULLTEXT 在数十条记录的搜索延迟为 1-5ms，与 ES 无感知差异。但如果数据量到十万级以上并有复杂相关性排序需求时 ES 才有价值——本项目永远不会到这个量级。

### 6.4 Nginx —— **要**（轻量使用）

**一句话论证**：单机部署下 Nginx 作为反向代理可实现：前端静态资源高效分发、API 代理、gzip 压缩、HTTPS 终结、访问日志。Windows 版 Nginx（nginx.org 官方提供）安装为一个目录，配置一个 `nginx.conf` 即可。

**仅需以下功能**，不做复杂配置：
- 前端静态文件 serve（Vue 构建产物）
- `/api/*` 反向代理到 Spring Boot（localhost:8080）
- gzip 压缩
- （可选）HTTPS（如果需公网访问）
- 文件下载限速（`limit_rate` 防止大附件占用带宽）

**不引入会怎样**：Spring Boot 也可以直接 serve 静态文件，但 Nginx 在高并发静态资源分发上效率更高、配置更灵活。对于本项目并发规模，不引入也能跑，但**引入成本极低**（一个 5MB 的 nginx.exe + 30 行配置文件），带来的好处（动静分离、日志、未来 HTTPS）值得。

### 6.5 定时任务框架（Quartz/XXL-Job） —— **不要**

**一句话论证**：Spring Boot 内置的 `@Scheduled` 注解 + cron 表达式足以实现"到期岗位自动下架"和"过期验证码清理"这两个定时任务，无需引入独立的调度框架。

具体：
```java
@Scheduled(cron = "0 */5 * * * *")  // 每5分钟执行
public void autoOfflineExpiredJobs() {
    jobService.offlineExpired();
}
```

**不引入会怎样**：`@Scheduled` 就是 JVM 内的单线程调度器，对于两个简单定时任务（无分布式协调需求、无任务依赖、无失败重试复杂度）完全足够。XXL-Job 是企业级分布式调度平台，需要独立部署调度中心（又是一个 Java 进程），严重过度设计。

## 7. 关键功能的现成轮子调研

### 7.1 PDF/Word 在线预览（P0，核心难点）

这是本项目最大的工程难点。需要区分两种场景：

**场景 A：PDF 预览**——方案成熟，直接前端渲染。
**场景 B：Word（.doc/.docx）预览**——必须经过格式转换。

推荐方案采用**分层策略**：

#### 7.1.1 PDF 预览

**推荐：PDF.js（Mozilla 官方，v4.x，Apache 2.0 协议）**

- 纯前端渲染，浏览器内完成，不需要服务端转换
- 支持分页、缩放、搜索、旋转
- Vue3 封装：`@vue-pdf-viewer` 或直接集成 `pdfjs-dist`
- GitHub 48k+ star，Mozilla 维护，绝对成熟

#### 7.1.2 Word 预览——推荐方案：LibreOffice 服务端转换 + PDF.js 前端渲染

这是落地方案的核心。经过对所有可行方案的对比：

| 候选方案 | 还原度 | 部署复杂度 | 成本 | 结论 |
|----------|:--:|:--:|:--:|------|
| **LibreOffice 命令行转 PDF + PDF.js 渲染** | **高（95%+）** | 中（安装 LibreOffice） | 免费 | **推荐** |
| Apache POI + 自渲染 HTML | 低（50-70%） | 低 | 免费 | 复杂排版丢失严重，不推荐 |
| mammoth.js（前端纯 JS 转 HTML） | 中低（60-80%） | 极低 | 免费 | **作为快速预览备选** |
| docx-preview（前端纯 JS） | 中（70-85%） | 极低 | 免费 | 仅支持 .docx，不支持 .doc |
| OnlyOffice Document Server | 很高 | 高（独立服务） | 免费社区版但功能有限 | 为预览引入协作编辑套件，过度 |
| kkFileView（Spring Boot 项目） | 高 | 中 | 免费 | 内置 LibreOffice 集成，但增加一个独立服务 |
| Aspose.Words（商业） | 极高 | 低 | **$5000+/年** | 成本不适用于本项目 |

**推荐实施路径**：

**方案 1（首选——LibreOffice Headless 命令行）**：

1. 在 Windows 上安装 LibreOffice（免费，https://www.libreoffice.org/）
2. 上传的 .doc/.docx 文件保存后，调用命令行转换：
   ```
   "C:\Program Files\LibreOffice\program\soffice.exe" --headless --convert-to pdf --outdir output_dir input.docx
   ```
3. 转换后的 PDF 文件与原始附件一并存储
4. 前端使用 PDF.js 渲染 PDF
5. Java 通过 `ProcessBuilder` 调用，加超时保护（30s）

- **优点**：还原度最高，支持 .doc/.docx/.ppt/.pptx 等所有 Office 格式；免费无授权风险
- **缺点**：需安装 LibreOffice（约 500MB 磁盘）；转换耗时 2-10 秒（取决于文档复杂度）；并发转换需控制线程数（建议队列化，单线程处理）

**方案 2（轻量备选——前端纯 JS）**：

对于 `mammoth.js`（MIT 协议，npm: `mammoth` v1.8.x）：
- 纯前端，零服务端依赖
- 将 .docx 转为简化 HTML（保留基本格式：标题、加粗、列表、表格、图片）
- 丢失：复杂排版（分栏、页眉页脚、首字下沉）、高级样式
- **可用作"快速预览"模式的首屏展示**，并同时提供"下载原文件"按钮

**最终推荐**：**方案 1 + 方案 2 组合**——上传后立即用 mammoth.js 在前端展示快速预览（1s 内出结果），同时在后台异步调用 LibreOffice 生成高保真 PDF（3-10s），转换完成后切换到 PDF 视图。这样用户体验最佳。

**版本信息**：
- LibreOffice：24.8.x LTS（2025-12 最新 LTS）
- PDF.js：4.10.x（2025-12 发布）
- mammoth.js：1.8.0（MIT 协议，GitHub 5k+ star）

### 7.2 Excel 导出

### 7.5 权限框架（RBAC）

**推荐：Spring Security 6.x（Apache 2.0，Spring 官方）**

- Spring Boot 3.x 原生集成，`spring-boot-starter-security` 一行依赖
- 基于 RBAC 模型：User -(多对多)-> Role -(多对多)-> Permission
- 支持方法级注解 `@PreAuthorize("hasRole('HR_MANAGER')")`
- 支持数据权限（HR 只能看自己部门的简历）——通过 MyBatis-Plus 数据权限插件或自定义 SQL 拦截器实现
- RuoYi 框架已内置完整的 RBAC 实现（含菜单权限、数据权限、按钮权限），可直接复用

**自定义数据权限实现**（HR 只能看本人/本部门授权范围内的简历）：
```java
@PreAuthorize("@ss.hasPermi('recruitment:resume:list')")
@DataScope(deptAlias = "d", userAlias = "u")  // 数据权限注解
public List<Resume> selectResumeList(Resume resume) { ... }
```

淘汰 Apache Shiro：Shiro 在过去是轻量选择，但 2025 年其活跃度已明显下降（最后稳定版 1.13.0 发布于 2023 年）。Spring Security 6.x 的配置已大幅简化（Lambda DSL），不再是"配置地狱"，且在 Spring Boot 3.x 中的集成体验远优于 Shiro。

## 8. 部署与运维方案

### 8.1 部署方案对比

| 维度 | Docker Compose | 裸机安装 | 单可执行包（JAR） |
|------|:--:|:--:|:--:|
| 部署步骤 | `docker-compose up -d` | 分别安装 Java/MySQL/Nginx/LibreOffice | `java -jar app.jar` |
| Windows 兼容性 | 需 Docker Desktop（WSL2 依赖） | **完美** | **完美** |
| 环境一致性 | 优 | 取决于手动配置 | 优（JAR 自包含） |
| 备份脚本化 | 需映射卷 | **直接操作文件** | 需处理外部目录 |
| 运维学习曲线 | 中（Dockerfile + Compose 语法） | **低**（Windows GUI 操作） | **极低** |
| 故障恢复 | 容器重启 | 手动重启 | 重启脚本 |

### 8.2 推荐结论

**推荐：裸机安装（Windows 环境）+ 启动/备份脚本化**

原因：
1. Docker Desktop for Windows 需要 WSL2 支持，且在大公司内部 IT 环境中可能受限（Hyper-V 冲突、组策略限制、WSL 未启用）。
2. 管理方是一台**台式机**而非服务器——很可能就是某台 Windows 10/11 工作电脑，Docker Desktop 会额外消耗 1-2GB 内存。
3. 裸机安装在 Windows 上反而是最直观的方式：MySQL MSI 安装包、JRE MSI 安装、Nginx zip 解压、LibreOffice MSI 安装——每一步都有图形界面。
4. **备份策略极简**：一个 .bat 脚本（GBK 编码）定时执行 mysqldump + robocopy 文件复制。

### 8.3 具体部署清单

| 组件 | 安装方式 | 版本 | 预计磁盘 |
|------|---------|------|:--:|
| JDK | Eclipse Temurin MSI（免 Oracle 许可） | 17.0.14 LTS | 300MB |
| MySQL | 官方 MSI Installer | 8.0.41 | 1GB（含数据） |
| Nginx | 官方 zip 解压到 `C:\nginx\` | 1.26.x | 15MB |
| LibreOffice | 官方 MSI | 24.8.x | 600MB |
| 应用 JAR | `java -jar` 启动 | — | 80MB |

### 8.4 备份方案

创建 `backup.bat`（GBK 编码，不含 BOM）：

```bat
@echo off
set BACKUP_DIR=E:\backups\%date:~0,4%%date:~5,2%%date:~8,2%
mkdir %BACKUP_DIR%

:: 数据库备份
"C:\Program Files\MySQL\MySQL Server 8.0\bin\mysqldump.exe" -u root -pYourPassword --single-transaction --routines --triggers recruitment > %BACKUP_DIR%\db.sql

:: 文件备份
robocopy E:\recruitment-files %BACKUP_DIR%\files /E /R:3 /W:10

echo Backup completed: %BACKUP_DIR%
```

配置 Windows 任务计划程序（Task Scheduler），每日凌晨 2:00 执行。备份文件保留最近 30 天。

### 8.5 日志方案

- **应用日志**：Spring Boot 默认 Logback，输出到 `E:\logs\recruitment\`，按天滚动（`logback-spring.xml` 配置 `maxHistory=30`）
- **Nginx 访问日志**：启用并配置 `log_format`，输出到 `C:\nginx\logs\`
- **MySQL 慢查询日志**：开启 `slow_query_log`，阈值 1s
- **不需要 ELK/日志中心**：文件日志 + Notepad++ 查看对于单机系统完全足够

### 8.6 升级方案

1. 停止应用：`taskkill /F /IM javaw.exe` 或停止注册的 Windows 服务
2. 备份当前 JAR：`copy app.jar app.jar.bak`
3. 替换 JAR 文件
4. 启动应用：`java -jar app.jar`
5. 全部脚本化在 `deploy.bat` 中

## 9. 性能边界测算

### 9.1 假设配置

- CPU：Intel Core i5-13500（6P+8E，20 线程）
- 内存：16GB DDR4
- 磁盘：512GB NVMe SSD
- OS：Windows 11 Pro
- 网络：千兆局域网

### 9.2 单机承载能力预估

| 指标 | 理论极限 | 20 并发下的实际占用 | 余量 |
|------|---------|-------------------|:--:|
| **应用层并发** | ~500 req/s（Spring Boot 单实例 + Tomcat 200 线程池） | <10 req/s | **50x+** |
| **数据库 QPS** | ~5000 QPS（MySQL 8.0 单表万行） | <50 QPS | **100x+** |
| **应用内存** | -Xmx512m 配置 | ~350MB | 充分 |
| **MySQL 内存** | innodb_buffer_pool=512M | ~300MB | 充分 |
| **LibreOffice 转换** | 单线程串行，1 份/5-15s | 峰值 ~2 份/分钟 | 满足（上传非高频） |
| **磁盘 I/O** | NVMe SSD ~3GB/s 读，~2GB/s 写 | 几乎可忽略 | 极大 |
| **简历附件存储** | 5000 份 × 10MB = 50GB | 1000 份 × 10MB = 10GB | 充足 |
| **响应时间（P99）** | 岗位列表<50ms，投递<200ms，预览首屏<3s（含转换） | 同左 | — |

### 9.3 并发上限结论

在 16GB/SSD 配置下，该系统可稳定支撑 **200+ 并发用户**（是需求的 10 倍），瓶颈在 LibreOffice 文档转换队列（可通过限流控制）。20 并发下有**极大的性能余量**，不需要任何性能优化手段。

### 9.4 需要关注的实际瓶颈

唯一需要关注的是 **LibreOffice 并发转换**——如果 5 个 HR 同时点击预览 5 份不同简历的 Word 附件，需排队等待。缓解措施：
- 上传时异步转换（上传后后台自动生成 PDF 缓存），而非预览时才转换
- 转换队列单线程处理，超时 30s 自动跳过
- 前端 mammoth.js 作为快速预览兜底（上传时即可展示）

## 10. 风险清单

| 编号 | 风险 | 严重度 | 触发条件 | 缓解措施 |
|:--:|------|:--:|---------|---------|
| R1 | **LibreOffice 在 Windows 上的转换稳定性** | 中 | 特定 .doc/.docx 文件格式导致 soffice 进程卡死或崩溃 | (1) 设置 30s 超时自动 kill 进程 (2) 上传时异步转换+缓存 PDF (3) mammoth.js 前端预览作为兜底 (4) 同时提供"下载原文件"按钮，确保核心投递链路不受预览影响 |

| R5 | **短信服务商审核不通过** | 低 | 企业资质、短信模板审核被拒 | (1) 提前准备好企业营业执照、ICP 备案（如需要）(2) 阿里云/腾讯云都有企业实名认证→模板审核的标准流程 (3) 如短信不可用，降级为邮箱验证码（Spring Mail + 企业邮箱免费） |
