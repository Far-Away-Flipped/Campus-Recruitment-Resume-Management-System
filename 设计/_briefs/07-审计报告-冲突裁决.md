### C-01　简历快照 vs 重复投递（Critical）

#### 裁决结论

**采用「04 的唯一约束 + 学生主动重投」骨架，快照外移为独立版本表 `app_snapshot`。明确否决 06 的两个结论：既否决"彻底禁止重投"，也否决"学生改资料自动同步已投递快照"。**

具体语义：

| 维度 | 裁决后的唯一行为 |
|---|---|
| 快照可变性 | **绝对不可变**。`app_snapshot` 行一旦写入永不 UPDATE |
| 学生改资料 | **不影响**任何已投递记录，不做任何自动同步 |
| 重复投递 | **允许**，但必须由学生在岗位详情页显式点击「更新简历后重新投递」 |
| 数据形态 | `app_application` 一条（`uk_student_job` 唯一约束保留）+ `app_snapshot` N 条版本行 |
| HR 端可见性 | 默认展示 `current_snapshot_id` 指向的最新版本；若 `version_no > 1`，列表与详情页顶部显示徽标「该候选人已更新简历（第 N 版）」，可下拉查看历史版本 |
| 重投后状态 | 重置为 `PENDING_SCREEN`，并在 `app_status_history` 追加 `to_status=PENDING_SCREEN, remark='学生更新简历后重新投递（第N版）'` |
| 重投限制 | **仅当当前状态为 `PENDING_SCREEN` 时允许**。`SCREEN_PASSED` / `ELIMINATED` 为已决状态，重投会破坏 HR 的决策记录，必须禁止（前端按钮置灰 + 后端 Service 层硬校验） |
| 重投频次 | 同一岗位最多 **3 次**（`version_no <= 3`），防止学生反复刷新投递把自己顶到列表最前 |

#### 裁决理由

1. **需求原文站在"允许重投"一侧**。S-013 括号内"可提示更新简历后重新投递"是甲方明确写下的期望路径。06 选方案 A（彻底禁止）等于删掉了需求原文的一句话，属于设计层擅自缩减需求范围，违反设计简报 2.2 节"P0 严格对齐需求文档标注"。
2. **06 的"等效替代方案"（自动同步）比彻底禁止更危险**。它制造了一个真实的坏场景：HR 在 8 月 6 日基于 A 版简历判定"筛选通过"，学生 8 月 7 日把 GPA 从 3.2 改成 3.9，系统记录显示 HR 通过的是 3.9 版。这在劳动争议或内部审计中无法解释。且 06 自身第 3.3 节声称"快照不再是投递那一刻的冻结"是方案 C 的**缺点**，却在同一节把它作为推荐方案 A 的"等效替代"提出——**06 内部自相矛盾**。
3. **04 的方案同样破坏了不可变性**。04 决策二自称"快照是投递时刻的不可变副本"，决策三却写"更新 `snapshot_*` 字段为最新数据"。字段被 UPDATE 即不可变性消失。04 保留的只是 `app_status_history` 的流转事件，无法回答"HR 当初看到的是哪一版内容"。
4. **编排层建议的 `app_snapshot` 版本表不是过度设计**。反驳"过度设计"质疑的量化依据：
   - 真实业务量：每届 2000 份投递，重投率按最悲观的 15% 估算 = 300 条额外快照行，每行 3–5KB，**年增量 < 1.5MB**。
   - 实现成本：一张 8 字段的表 + 一个 insert + 一个 `current_snapshot_id` 指针字段。无联表复杂度（`app_application` 直接持有指针）。
   - **它反而降低了 04 方案的复杂度**：04 要在 `app_application` 上挂 6 个 JSON 大字段，使这张最热的表行宽膨胀（MySQL InnoDB 中 JSON 走 off-page 存储，但行内仍有 20 字节指针×6，且 `SELECT *` 会拖出全部 JSON）。外移后，H-004 的列表查询不再触碰任何 JSON 列，**列表页性能与代码可读性双改善**。
   - 结论：**这不是为未来预留的抽象，是当下就有收益的正常范式化。判定为"非过度设计"。**

### C-06　快照字段可索引性（Critical，与 C-01 合并落地）

#### 裁决结论

**推翻 04 §6.1 的"先用 job_id+status 过滤至候选集，再在应用层做 JSON 字段匹配"方案。裁决：H-004 的筛选/排序数据源为 `app_application` 上的冗余普通列，不是 JSON、也不是 `stu_*` 连表。**

新增冗余列（写入 `app_application`，投递/重投时从快照同步写入，与快照同源同刻）：

| 字段 | 类型 | 来源 | 用途 |
|---|---|---|---|
| `snapshot_student_name` | VARCHAR(64) | 快照 profile.realName | 列表展示 + 姓名关键词搜索 |
| `snapshot_school` | VARCHAR(128) | 快照 educations[最高学历].schoolName | H-004 学校筛选 + 报表学校分布 |
| `snapshot_major` | VARCHAR(128) | 快照 educations[最高学历].major | H-004 专业关键词 |
| `snapshot_degree` | VARCHAR(32) | 快照 educations[最高学历].degree | H-004 学历筛选 + 报表学历分布 |
| `snapshot_phone_mask` | VARCHAR(20) | 快照 profile.phone 掩码 | 列表展示（不存明文，降低泄露面） |

配套索引（写入 04 §6.1 复合索引表）：

```sql
KEY `idx_job_status_time`  (`job_id`, `status`, `apply_time`),   -- 已有，改名对齐
KEY `idx_school_degree`    (`snapshot_school`, `snapshot_degree`),
KEY `idx_degree`           (`snapshot_degree`),
KEY `idx_name`             (`snapshot_student_name`)
```

#### 裁决理由

1. **"从 `stu_*` 连表查"方案被排除**：会产生"筛选结果与详情内容不一致"的脏体验——学生投递后把学校从"某二本"改成"清华大学"，HR 按"清华大学"筛选能筛到他，点进详情看到的快照却是二本。这是**数据正确性缺陷**，不是性能问题。
2. **"从 JSON 取 + 应用层匹配"方案被排除的量化依据**：04 声称"每岗位最多几百份，JSON_EXTRACT 全扫描 < 20ms"。这个论证只覆盖了"按单岗位筛选"场景，**遗漏了 H-004 的另一半需求**——需求原文 H-004 写的是"支持按状态、学校、学历等多维度筛选排序"，并未限定必须先选岗位。HR 的真实高频操作是"跨全部岗位，看所有硕士以上的待筛选简历"。此时候选集是全库 2000 条（三年 6000 条），应用层 JSON 解析 6000 个对象再排序分页，**单次请求 300–800ms 且无法走 LIMIT 下推**（必须全量拉回内存才能过滤）。同时 EasyExcel 导出、报表学校分布、报表学历分布三处都要重复这套逻辑。
3. **"排序"是 JSON 方案的死穴**：05 §3.7 明确 `orderByColumn` 支持 `school_name` / `degree`。JSON 字段无法做 `ORDER BY` + `LIMIT` 分页下推，只能全量拉回内存排序——第 2 页数据也要扫全表。冗余列是唯一能让 MySQL 直接完成"筛选+排序+分页"的方案。
4. **冗余列不违反"最小化"原则**：这 5 个列合计约 380 字节/行，6000 行 = 2.3MB。代价是投递时多写 5 个字段（零额外查询，数据本来就在手上）。

> **一致性保证**：冗余列**只在 INSERT 快照的同一个事务内写入，此后永不 UPDATE**（除非重投时随新快照一起更新）。因此冗余列与 `current_snapshot_id` 指向的快照内容天然一致，不存在"冗余列与快照不同步"的经典风险。

### C-02　LibreOffice 串行队列延迟（High）

#### 裁决结论

**接受单线程串行方案，不改为进程池。但 06 §5.1 必须补齐三条此前缺失的显式约束，缺一不可：**

1. **转换绝不阻塞学生上传**。上传接口在文件落盘 + 写 `stu_resume_file` 记录后**立即返回 200**，`preview_status=PENDING`。转换任务的提交（`@Async`）在事务提交后（`TransactionSynchronization.afterCommit`）执行。**学生端 UI 不得出现任何等待转换的阻塞态**——上传成功即可投递，预览按钮显示"处理中"是可接受的。
2. **队列满时的降级路径**：06 §5.1.2 用 `CallerRunsPolicy` 是**错误的**，必须改。理由见下。改为 `DiscardPolicy` + 显式回落：队列满时不执行、不抛异常，只把 `preview_status` 置为 `PENDING` 并记 WARN 日志，由定时任务 T2 兜底捞取。
3. **PDF 为主推荐格式**：学生端上传组件的提示文案硬性要求为「**推荐上传 PDF 格式（可即时预览）**，也支持 Word（.doc/.docx，上传后约需 1 分钟生成预览）」。这是把峰值转换量从源头砍掉的零成本手段。

#### 裁决理由

1. **`CallerRunsPolicy` 在本场景是设计缺陷，不是保守选择**。06 §5.1.2 的注释写"队列满时由主线程执行，保证任务不丢（宁可慢，不丢数据）"——这个理由在**同步任务**场景成立，在这里不成立：调用方是**处理学生上传 HTTP 请求的 Tomcat 工作线程**。队列满时该线程会被拉去跑一次 LibreOffice 转换（5–15 秒，超时 60 秒）。后果链：
   - 学生的上传请求挂起最长 60 秒 → 前端超时 → 学生以为上传失败 → **重复上传** → 队列更满 → 更多 Tomcat 线程被占用。
   - Tomcat 默认 200 个工作线程，但真正的瓶颈是：这是一个**自我强化的正反馈**，恰好在投递截止日前夜的峰值触发。
   - 而"不丢数据"这个目标**已经由 DB 状态字段保证了**——`preview_status=PENDING` 的记录躺在库里，T2 每 2 分钟捞一次，任务根本丢不了。用 `CallerRunsPolicy` 换一个已经被满足的保证，纯亏。
2. **转换延迟只影响 HR 预览时效，量化后可接受**。质疑中提出的"100 名学生 10 分钟内集中提交 → 积压 17 分钟"是成立的，但影响面是：HR 在积压期间打开这些简历会看到"转换中"。而 HR 的实际工作节奏是投递截止后集中筛选（次日或更晚），17 分钟的积压在 HR 触达前早已消化完毕。**结论：可接受，但必须在文档中写清这一前提**，不能让实现者以为"预览必须实时"。
3. **进程池方案维持淘汰**：06 的理由（每进程 200–500MB，3 进程 1.5GB）成立，且 16GB 机器还要给 MySQL、JVM、Nginx 留空间。此外多 profile 并发是 LibreOffice 在 Windows 上最经典的不稳定源（03 §8 R2 也点明了这一点）。
4. **队列容量取值不一致，必须统一**：03 §2.2 写"容量 200"，06 §5.1.2 写"queueCapacity(100)"。裁决：**统一为 200**。理由：宣讲会峰值场景下 100 太紧，而队列元素只是一个任务对象（< 200 字节），200 的内存代价可忽略。

| 文档 | 章节 | 改成什么 |
|---|---|---|
| **06** | §5.1.2 `libreOfficeExecutor` | ① `setQueueCapacity(100)` → `setQueueCapacity(200)`；② `new CallerRunsPolicy()` → **`new ThreadPoolExecutor.DiscardPolicy()`**，并在下方补注释："队列满时静默丢弃，任务不会丢失——`stu_resume_file.preview_status` 仍为 PENDING，由 T2 定时任务兜底捞取。**绝不使用 CallerRunsPolicy**：调用方是 Tomcat 请求线程，会导致学生上传请求挂起最长 60 秒" |

### C-04　学生端 JWT 有效期 7 天（High）

#### 裁决结论

**推翻 05 §2.1 的"学生端 JWT 7 天 + 无刷新 + 无黑名单"方案。改为：access token 有效期 2 小时（不落库、无状态验签）+ refresh token 有效期 7 天（落库，可吊销）。**

同时**推翻 03 §5.1.1 实现要点表中"7 天…纯无状态验签 + 版本号字段可全量失效"的表述**——03 提到的"版本号字段全量失效"是一个只能"踢掉所有设备"的粗粒度手段，无法满足"在其他设备退出登录"，且 03 并未在任何 DDL 交接清单中要求该字段，04 也确实没建。属于悬空设计。

#### 具体方案

| 项 | 裁决值 | 说明 |
|---|---|---|
| access token 有效期 | **2 小时** | 与 HR 端一致，无状态验签，不落库、不查库 |
| refresh token 有效期 | **7 天** | 保留 05 原本"学生低频访问、不宜频繁登录"的体验诉求 |
| refresh token 存储 | 新表 `stu_refresh_token`（8 字段小表） | 存 token 的 SHA-256 哈希，不存原文 |
| 刷新接口 | `POST /api/portal/auth/refresh` | 传 refresh token，返回新 access token（refresh token 本身不轮换，降低实现复杂度） |
| 登出 | `POST /api/portal/auth/logout` **DELETE 该 refresh token 行** | 登出后最长 2 小时内旧 access token 仍有效，这是可接受的残留窗口（HR 端 RuoYi 原生也是同样特性） |
| 「在其他设备退出登录」 | 个人中心提供按钮，DELETE 该 student_id 的全部 refresh token 行 | 成本约 0.1 人日，是 PIPL 语境下应尽的安全措施 |
| 设备数上限 | 同一 student_id 最多保留 **5 条** refresh token，超出淘汰最早的 | 防止表无限增长 |

#### 裁决理由

1. **公共设备场景是真实且高频的**。校招投递的典型场景就是宣讲会现场共用笔记本、学校机房、图书馆公用机。7 天长效 token 落在这些机器的 localStorage 里，后续使用者打开门户即已登录，可读取**姓名、手机号、出生日期、户籍地、现居地、教育经历、简历附件原件**——这是完整的个人信息集合，属于 PIPL 下的高风险泄露。
2. **"无法吊销"在 PIPL 语境下不是可接受的权衡**。学生发现账号异常时，系统给不出任何补救手段（改密码也不能让已签发的 JWT 失效）。而修复成本极低。
3. **成本量化对比**：
   - 引入 refresh 机制：一张 8 字段表 + 一个刷新接口 + 前端 axios 拦截器加 401 自动刷新逻辑 ≈ **1.0 人日**。
   - 不引入的代价：一次公共设备账号接管事件 = PIPL 个人信息安全事件，需向监管报告并通知个人（PIPL 第 57 条）。
   - **1 人日 vs 监管报告，无需犹豫。**
4. **反驳"用 Caffeine 存黑名单"的替代方案**：Caffeine 重启即失效，等于吊销失效。而 refresh token 落库既不需要 Redis，也不违反裁决基线（基线禁的是 Redis，不是 MySQL 表）。**这是本项目"不引入 Redis"约束下的正解。**
5. 05 §2.1 论证表中"登出即失效：需引入黑名单（本项目不引入）"这一行的推理是**错的**——它假设了"服务端可吊销"只有黑名单一条路。refresh token 落库是标准的第二条路，且更简单（正向白名单，不需要 TTL 管理）。

#### 裁决结论（三个必答问题）

**问题一：03 的"方案A 59 + 方案B 24"是互斥还是叠加？**

**都不是。这是本次审计发现的一处严重表述缺陷——编排层的提问本身就被 03 的表述误导了。**

核对 03 §7.2 里程碑表可知：**"59" 与 "24" 不是"方案 A"与"方案 B"，而是 `A(人日)` 列与 `B(人日)` 列的合计**，其中 **A = Java 全栈工程师（100% 投入）**、**B = 前端工程师（50% 投入）**——这是 §7.1 定义的两个**人力角色**，与 §3 的"部署方案 A（纯内网）/ 方案 B（公网）"**完全无关，只是恰好同名**。

- 51 + 21 = 72 人日（小计），各自 +15% 缓冲后为 59 + 24 = 83 人日。
- 它们是**两个人并行投入的工作量**，既非互斥、也非简单叠加为一个人的工期。
- **83 人日是"总人力投入"，12 周是"日历关键路径"**（A 的 59 人日 ÷ 5 天/周 ≈ 12 周；B 的 24 人日在 50% 投入下需 48 个工作日 ≈ 9.6 周，被 A 完全吸收）。

> **裁决**：`_冲突与待确认事项.md` C-07 中"方案A 59 人日 + 方案B 24 人日 = 83 人日"这一表述是**编排层的误读**，源于 03 §7.2 表头只写 `A(人日)` `B(人日)` 而未在表格附近重申 A/B 是人名代号。**03 必须修正表述以杜绝此误读**（见落地指令）。

**问题二：统一口径。**

**以 03 的全生命周期口径为准**（含环境骨架、RuoYi 改造、两套前端工程、安全加固、备份脚本、恢复演练、部署培训）。理由：04/05/06 三份的估算都只覆盖各自职责域内的编码，任何一份单独对外都会造成排期误导；只有 03 的口径能回答甲方真正关心的"什么时候能上线"。

#### 三个附加问题的回答

**① 7 处改造总成本是多少？是否已包含在 03 的估算中？**
**2.0 人日。已包含**——03 §7.2 M0 的范围明确写了"**Caffeine 替换 Redis 全量改造**"，M0 合计 5 人日（本报告调整为 5.5）。2.0 人日占 M0 的约 40%，与 M0 其余内容（环境安装、Maven 改名、双过滤链骨架、WinSW、脚本）的分配是合理的。**未发现漏算。**

**② 改造后是否影响 RuoYi 后续版本升级？**
**影响有限，且已被架构设计有意控制。** 关键论据：改造**没有修改 RuoYi 的任何业务类**，只做了两件事——(a) 新增一个 `CaffeineCache` 类，(b) 让 Spring 注入它而非 `RedisCache`。由于方法签名 100% 一致，RuoYi 升级时只需检查 `RedisCache` 是否新增了方法（若有，补实现即可）。**真正的升级障碍不是去 Redis 化，而是本项目对 `SecurityConfig`（拆双过滤链）、`GlobalExceptionHandler`、`SysOperlogController`（删清空接口）的改动**——这些才是与框架核心耦合的地方。且本项目是**一次性交付的内部系统，不是需要持续跟进上游的产品**，RuoYi 升级本身就是低频事件（预计三年内 0–1 次）。

**③ 若改造成本 > 3 人日或阻碍升级，是否该引入 Redis？**
改造成本为 **2.0 人日 < 3 人日阈值**，且不构成主要升级障碍。**两个触发条件均未满足，故维持不引入。**

#### 最终裁决理由（一句话）

**2.0 人日的一次性改造，换掉一个在 Windows 上无官方支持、停更十年、且会成为"全站登录单点"的常驻进程——这笔账在本项目（单机、20 并发、无专职运维）的约束下是明确划算的。裁决基线 00 的结论成立，予以维持。**

### N-01　API URL 前缀三套并存（Critical）

#### 冲突描述

| 文档 | 章节 | 定义的前缀 |
|---|---|---|
| **03** | §1.4「三端在后端的组织方式」表 + §3.2⑥ Nginx 配置 | `/api/portal/**`（学生，**公网唯一放行**）、`/api/admin/**`（HR 业务，内网）、`/api/system/**`（RuoYi 系统管理，内网） |
| **05** | §1.1 URL 命名规范表 + 全文 58 个接口 | `/api/student/`、`/api/hr/`、`/api/system/`、`/api/common/` |

03 §1.4 对此有一段极强的措辞：

> 「URL 前缀是**硬边界**：Nginx 公网 vhost 的白名单、Spring Security 的 `securityMatcher`、审计切面的分类判定，三者都以它为准。约定：任何新增接口必须落在这三个前缀之一，Code Review 检查项第一条。」

而 05 的 58 个接口**没有一个**落在 `/api/portal/**` 或 `/api/admin/**` 下。

#### 为什么会导致实现返工（具体失败场景）

按 03 §3.2⑥ 的 Nginx 配置原样部署，公网 vhost 的行为是：

```nginx
location ^~ /api/portal/ { proxy_pass http://127.0.0.1:8080; }   # 放行 —— 但 05 没有任何接口在此前缀下
location ^~ /api/system/ { return 403; }                          # 05 的 15+ 个系统管理接口被 403（预期内）
# /api/student/、/api/hr/、/api/common/ 均未定义 location
# → 落入 location / { try_files $uri $uri/ /index.html; }
# → 全部返回门户的 index.html（HTTP 200 + text/html）
```

**失败现象**：学生在公网打开门户，点击登录 → 前端收到一段 HTML 而非 JSON → `JSON.parse` 抛异常 → 页面白屏，控制台报错是 `Unexpected token '<'`，**看不出是 Nginx 路由问题**。排查成本极高（前端以为后端挂了，后端日志里根本没有这条请求）。

同时 Spring Security 侧：03 定义 `portalFilterChain` 的 `securityMatcher("/api/portal/**")`，05 的 `/api/student/**` 请求**匹配不到 portal 链**，会落到 `adminFilterChain`（Order 2，兜底全部），被要求提供 RuoYi JWT → 学生 token 验签失败 → **所有学生接口返回 401**。

这不是"接口名字不好看"，是**两条安全链与一份 Nginx 配置全部失效**。

#### 裁决结论

**统一采用 03 的 `/api/portal/**`、`/api/admin/**`、`/api/system/**` 三段前缀。05 的全部 58 个接口按下表整体重映射。`/api/common/` 前缀予以废除。**

**裁决理由**：
1. 03 的前缀承载**安全语义**（公网/内网边界），05 的前缀只承载**业务语义**（谁在用）。冲突时安全语义优先——安全边界写错是静默失效（403 少配一条 = 后台接口上公网），业务语义不直观只是可读性问题。
2. `portal / admin` 比 `student / hr` 更准确表达边界本质：划分依据是「**这个接口能否暴露到公网**」，不是「谁在调用」。未来若有"面试官"角色，他属于 admin 侧而非新开 `/api/interviewer/`。
3. **`/api/common/` 必须废除**——这是本条中最危险的一处。05 §4.5/§4.6 把附件预览与下载放在 `/api/common/file/preview/{fileId}`，声称"学生或 HR 均可携带 token 访问"。这意味着**一个前缀同时服务两套认证体系**，Nginx 无法判断它该不该上公网：放行则 HR 的附件下载接口暴露公网，不放行则学生无法预览自己的简历。**共用前缀 = 边界不可判定 = 必须拆开。**

| **05** | §3.4 S-APP-002、§3.7 H-RESUME-001/002/005/006 | `"status": "待筛选"`、`"筛选通过"`、`"已淘汰"` —— **中文** | API 传输层用中文枚举 |
| **05** | §3.10 COMMON-001 | 字典类型名 `campus_application_status` | 与 04 的 `candidate_status` 不同名 |

#### 为什么会导致实现返工

**三个独立的失败场景**：

1. **`APPLIED` 状态无处安放**。06 §1.3 定义 `APPLIED → PENDING_SCREEN` 是"系统自动，投递校验通过后立即触发"，§3.1 时序图写入投递记录时 `status=APPLIED`。但 04 的 DDL 默认值是 `PENDING_SCREEN`，字典里也没有 `APPLIED`。实现者只能二选一：写 `APPLIED` 则前端渲染状态标签时字典查不到、显示空白；写 `PENDING_SCREEN` 则 06 的状态机第一条跃迁形同虚设。
2. **API 传中文导致的连锁故障**。05 的 `PATCH .../status` 请求体是 `{"status": "筛选通过"}`，引发：① 后端需要"中文→英文码"反向映射表，任何一字不一致（"已淘汰" vs "淘汰"）即静默失败；② 中文作为 URL query 参数（H-RESUME-001 的 `status` 筛选）需 URL 编码，前后端编码不一致时筛选失效；③ **数据库存的是英文码**，每次读写都要转换，转换表与字典表不同步即产生脏数据；④ 与 03 §5.1.7「前端传字段名→后端映射表→真实列名」的白名单防注入设计冲突——中文值无法做白名单校验。
3. **`WITHDRAWN` 与 `APPLIED` 的取舍无人裁决**。04 凭空多出的 `WITHDRAWN` 在 06 状态机、05 接口中均无对应，属孤立枚举值。

#### 裁决结论

**采用 04 的 DDL 默认值 `PENDING_SCREEN`，删除 `APPLIED` 状态；API 传输层一律使用英文码，中文名仅用于前端展示。**

**为什么删 `APPLIED` 而不是补上它**：`APPLIED → PENDING_SCREEN` 的触发条件是"投递校验通过后**立即**触发"，即 `APPLIED` 的存续时间是**同一事务内的零时长**——永远不会有任何一条记录以 `APPLIED` 状态被查询到。**一个不可观测的状态就是不存在的状态。** 保留它只会在实现时制造"该不该先 INSERT 成 APPLIED 再 UPDATE 成 PENDING_SCREEN"的无谓争论，并多一次无意义的写库。

06 §1.3 的另一条 `APPLIED → ELIMINATED`（"资料不完整时系统自动淘汰"）同样删除——06 §3.1 时序图里资料不完整在**投递校验阶段就返回 400，根本不会产生投递记录**。这条跃迁与 06 自身的时序图矛盾。

**`WITHDRAWN` 的裁决**：**保留在字典中，标注 P2 预留**。学生主动撤回是合理的未来功能（与 C-01 的重新投递互补），保留一个字典值成本为零。

### N-04　附件转换状态枚举三套并存（Critical）

#### 冲突描述

| 文档 | 位置 | 枚举值 |
|---|---|---|
| **04** | §4.1 `stu_resume_file.preview_status` DDL + §7.3 `preview_status` 字典 | `PENDING` / `CONVERTING` / `SUCCESS` / `FAILED` |
| **05** | §3.2 S-RESUME-001 响应 + §4.3 转换状态表 + §4.4 轮询接口 | `PENDING` / `PROCESSING` / `COMPLETED` / `FAILED` |
| **06** | §5.1.3 任务状态流转表 + §5.1.1 流程图 | `WAITING` / `CONVERTING` / `COMPLETED` / `FAILED` |

三套值中，只有 `FAILED` 三方一致。"转换中"有 `CONVERTING`/`PROCESSING` 两种写法，"成功"有 `SUCCESS`/`COMPLETED` 两种，"待转换"有 `PENDING`/`WAITING` 两种。

#### 为什么会导致实现返工

1. **前端轮询永远等不到结束**。05 §4.4 的前端轮询逻辑判断 `convertStatus === 'COMPLETED'` 时停止并启用预览按钮。而后端按 04 的 DDL 写入的是 `SUCCESS`。前端会一直轮询到 60 秒超时，显示"处理超时"——**尽管转换早已成功**。学生看到的现象是"简历上传成功但永远预览不了"，而后端日志一切正常。
2. **字典渲染空白**。04 §7.3 的 `preview_status` 字典只有 4 个值（PENDING/CONVERTING/SUCCESS/FAILED），若后端按 06 写入 `WAITING`，前端 `<dict-tag>` 查不到标签，显示为空。
3. **C-02 裁决的降级路径失效**。C-02 裁决要求 T2 扫描 `status IN ('PENDING','CONVERTING')`。若实际写入的是 `WAITING`/`PROCESSING`，队列满被丢弃的任务永远捞不回来——**这是一个静默的数据可用性缺陷**。

#### 裁决结论

**统一采用 04 的 `PENDING / CONVERTING / SUCCESS / FAILED`。**

### N-05　岗位状态枚举三套并存（Critical）

#### 冲突描述

| 文档 | 位置 | 枚举值 |
|---|---|---|
| **04** | §4.2 `job_position.status` DDL + §7.3 `job_status` 字典 | `DRAFT` / `PUBLISHED` / `CLOSED`（已下架） / `EXPIRED`（已到期） |
| **06** | §2.2 状态定义表 + 附录 B `PositionStatus` 枚举 | `DRAFT` / `PUBLISHED` / `OFFLINE`（已下架） / `CLOSED`（已关闭归档） |
| **05** | §3.3 S-JOB-003 响应、§3.6 H-JOB-001/005 | `ONLINE` / `OFFLINE` / `EXPIRED` |

**三方对"CLOSED"的语义完全不同**：04 的 `CLOSED` = 已下架，06 的 `CLOSED` = 已关闭归档（而"已下架"是 `OFFLINE`）。05 则用了两份文档都没有的 `ONLINE`。

#### 为什么会导致实现返工

1. **05 的 `ONLINE` 在字典中不存在**。04 §7.3 的 `job_status` 字典只有 4 个值，无 `ONLINE`。HR 后台岗位列表的状态列会显示空白，且 H-JOB-005 上下架接口传 `{"status":"OFFLINE"}` 时，04 的字典里也没有 `OFFLINE`（04 用 `CLOSED` 表示下架）。
2. **语义反转导致数据灾难**。假设实现者按 06 写代码（`CLOSED` = 归档终态），却按 04 的字典渲染（`CLOSED` = 已下架），则 HR 在界面上看到"已下架"、以为可以重新上架，点击后系统按 06 的状态机拒绝（`CLOSED` 是终态）。**同一个值在两处的含义相反，这是最难排查的一类缺陷。**
3. **`EXPIRED` 与 `OFFLINE` 的职责重叠**。06 §2.3 的到期自动下架把状态置为 `OFFLINE` + `offline_reason='AUTO_EXPIRED'`；04 则设计了独立的 `EXPIRED` 状态。两种建模都能工作，但混用会导致"到期的岗位"在数据库里出现两种状态值，所有查询"在招岗位"的 SQL 都要写 `status='PUBLISHED'` 之外还要排除两种。

#### 裁决结论

**统一采用 06 的 `DRAFT / PUBLISHED / OFFLINE / CLOSED` 四值语义，删除 `EXPIRED`。到期下架用 `OFFLINE` + `offline_reason='AUTO_EXPIRED'` 表达。**

**裁决理由**：
1. **`EXPIRED` 作为独立状态是冗余建模**。"到期"是**下架的一个原因**，不是一种独立状态——它与"HR 手动下架"在业务上的后续处理完全相同（都不接收新投递、已有投递保留、都可重新上架）。用状态区分原因，会导致每个查询都要枚举两个值；用 `offline_reason` 字段区分，查询只需 `status='OFFLINE'`。**原因归字段，状态归状态**是更干净的建模。
2. 06 的 `OFFLINE`（可重新上架）与 `CLOSED`（归档终态）区分有真实业务价值：校招季中途下架的岗位需要能重新上架，而往届已归档的岗位不应再出现在任何列表中。04 的四值模型缺少"归档"这一档。
3. 05 的 `ONLINE` 是三方中唯一的孤例，无字典支撑，直接淘汰。

#### 唯一权威岗位状态枚举表

| 英文码（DB = API） | 中文名 | 学生端可见 | 可投递 | 允许的下一状态 | 触发者 |
|---|---|---|---|---|---|
| `DRAFT` | 草稿 | ❌ | ❌ | `PUBLISHED`；删除（无投递时） | HR |
| `PUBLISHED` | 已发布 | ✅ | ✅ | `OFFLINE` | HR 手动／T1 到期自动 |
| `OFFLINE` | 已下架 | ❌（详情页可达，按钮置灰） | ❌ | `PUBLISHED`（重新上架）、`CLOSED` | HR |
| `CLOSED` | 已关闭（归档） | ❌ | ❌ | — （终态） | HR |
| ~~`EXPIRED`~~ | ~~已到期~~ | **删除** | — | 用 `OFFLINE` + `offline_reason='AUTO_EXPIRED'` 表达 | — |

1. 03 是唯一给出**完整服务器目录规划**（§4，含 app/web/data/logs/scripts/backup/doc 七大目录）并论证了三条硬约束（data 不在 Nginx root 下、config 不入 Git、E: 与 F: 必须两块物理盘）的文档。04 的路径只是决策五里的一段示意。

### N-08　备份方案重复设计且相互冲突（High）

#### 冲突描述

**三份文档各自设计了一套备份方案**，且关键参数相互冲突：

| 维度 | **03** §5.3 | **04** §10 | **06** §6.1 T5 |
|---|---|---|---|
| 执行者 | PowerShell 脚本 + Windows 任务计划 | .bat 脚本 + 任务计划 | **Spring `@Scheduled` 在应用内调 `Runtime.exec()`** |
| DB 备份时间 | 每日 02:00 | 每日 02:00 | 每日 **01:00** |
| 附件备份 | 每日 02:20，`robocopy /E /XO` | 每日 03:00，`robocopy /MIR` | — |
| 保留策略 | 日 30 天 / 周 12 周 / 月 12 月 + 离线周备 | 日 7 天 / 周 / 月（GFS） | 保留 7 天 |
| 完整性校验 | ✅ 三重校验（大小 >80%、尾部 `-- Dump completed`、SHA256） | ❌ 无 | ❌ 无 |
| binlog | ✅ 开启，14 天，RPO≤15min | ❌ 未提 | ❌ 未提 |
| 异盘 | ✅ `F:` 第二块物理盘 + 离线移动硬盘 | ❌ 同盘 `D:` | ❌ 未提 |
| 密码处理 | ✅ MySQL 选项文件 `.my.cnf` + NTFS ACL | ⚠️ `-p` 交互式（脚本会卡住） | ❌ **密码明文拼进命令行** |

#### 为什么会导致实现返工（三个真实缺陷）

1. **04 的 `robocopy /MIR` 会删除备份**。03 §5.3.1 明确警示："`robocopy` **禁用 `/MIR`**，改用 `/E /XO`。`/MIR` 会把源端已删除的文件同步删除，导致误删无法从备份恢复。" 而 04 §10.3 的脚本原样使用了 `/MIR`。场景：T4 数据保留清理任务删除了一批过期简历附件（这是设计内的行为），次日 `/MIR` 把备份端的对应文件也删了——**"清理"变成了"不可恢复的销毁"**，而这恰恰是备份要防止的。
2. **04 的 `mysqldump -p`（无密码值）在无人值守的任务计划中会永久挂起**，等待 stdin 输入。任务计划显示"正在运行"，实际是死锁。**每日备份会静默地一次都不执行**，直到磁盘被 `mysqldump` 的临时输出撑满或有人手工检查。
3. **06 的 T5 把密码明文拼进 `Runtime.exec()` 命令行**：`String.format(cmd, dbUser, dbPass, ...)`。在 Windows 上，命令行参数对同机任何用户的进程列表可见（`wmic process get commandline`）。同时 06 用 `Runtime.getRuntime().exec(String)` 执行含 `>` 重定向的命令——**`exec(String)` 不经过 shell，`>` 会被当作 mysqldump 的一个参数，命令直接失败**。这段伪代码写出来就是不能运行的。

#### 裁决结论

**备份与恢复的唯一权威设计是 03 §5.3。删除 04 §10 全节，删除 06 的 T5 任务。备份由 PowerShell 脚本 + Windows 任务计划承担，应用进程不参与备份。**

**裁决理由**：
1. **备份不应由被备份的应用来执行**。06 的 T5 在应用进程内调用 mysqldump 有一个根本问题：**应用挂了就没有备份**——而"应用挂了"恰恰是最需要备份的时刻。任务计划独立于应用进程，应用崩溃、服务停止、JVM OOM 时备份照常执行。这是可靠性上的定性差异，不是风格偏好。
2. 03 的方案是三者中唯一包含**完整性校验**（"没有校验的备份等于没有备份"）、**binlog**（RPO 从 24h 降到 15min）、**异盘 + 离线副本**（防勒索）、**密码安全处理**的。
3. 03 §5.3.3 的两层脚本结构（.bat 纯 ASCII 只做调度 + .ps1 UTF-8 BOM 承载逻辑）符合用户环境的硬性编码要求；04 的 .bat 直接写逻辑，虽标注"纯 ASCII"但含 `echo Backup completed` 等输出，在中文 Windows 下无问题，但混合了调度与逻辑，不符合 03 已确立的规范。

|---|---|---|---|
| **04** | §10 全节（10.1~10.5） | **整节删除**，替换为指向 03 §5.3 的一句话（见 N-07 指令） | 必改 |
| **06** | §6.1 任务总表 | **删除 T5 `databaseBackup` 行**；任务总数保持 5 个（T5 位置由新的 T5 顶替，见 N-09） | 必改 |

#### 冲突描述

#### 为什么会导致实现返工

1. **`OrphanProcessTask` 缺失是真实的稳定性缺口**。03 §8 R2 把 LibreOffice 转换不稳定列为**概率"高"**的风险，缓解措施④明确写"`OrphanProcessTask` 每小时清理运行超 5 分钟的 `soffice.exe`"。06 作为工作流设计文档，本应承接这个任务的详细设计（03 §9 交接清单也把"定时任务 cron 与幂等设计"交给了工作流设计师），却完全遗漏。后果：僵死的 soffice.exe 进程逐日累积，每个占用 200–500MB，**几天后耗尽 16GB 内存导致整机不可用**。
2. **T4 的一期行为两份文档结论相反**。03 §2.2 与 §7.5 明确"`DataRetentionTask` **P0 以 dry-run 运行**（只扫描并输出报告日志，不删除）"；06 §6.2 T4 写"一期实现：仅实现表字段预留和配置项定义。清理逻辑 P1 实现"。实现者按 06 做则一期完全没有这个任务，03 §5.2.2 审计要求的"数据保留清理任务执行"审计事件无从产生，且无法在上线后验证保留策略是否正确（等到 P1 真删时才发现规则写错，数据已删）。
3. **周期不一致导致验收标准对不上**。03 §7.2 M2 验收标准写"改截止日期为过去→**10 分钟内**自动下架"，若按 06 的 5 分钟实现则验收更宽松（无害）；但 T2 的 2 分钟 vs 15 分钟差异较大——2 分钟意味着一天扫描 720 次，每次全表扫 `stu_resume_file`。数据量小时无所谓，但这是需要一个明确结论的参数。

2. **SEO 与分享链路断裂**。宣讲会分享的岗位链接 `campus.atmoto.cn/jobs/15?source=CAMPUS_TALK`，学生点开若被要求登录，转化率会大幅下降。且 04 §9.2 设计的渠道追踪方案依赖"页面加载时解析 URLSearchParams 存入 sessionStorage"——**如果页面加载就被重定向到登录页，`source` 参数会丢失**，整个渠道追踪功能失效。

### N-11　HR 端认证接口与 RuoYi 基座冲突，且缺 `getRouters`（High）

#### 冲突描述

| 05 §3.5 定义的接口 | RuoYi-Vue 原生路径 | 问题 |
|---|---|---|
| `POST /api/hr/auth/login` | `POST /login` | 路径不同 |
| `GET /api/hr/auth/current-user` | `GET /getInfo` | 路径不同，且返回结构不同 |
| `POST /api/hr/auth/logout` | `POST /logout` | 路径不同 |
| `/api/common/captcha` | `GET /captchaImage` | 路径不同 |
| **缺失** | `GET /getRouters` | ❌ **完全缺失** |

同时 03 §1.4 声明"任何新增接口必须落在三个前缀之一"，但 RuoYi 原生的这四个接口**都不带 `/api` 前缀**。

#### 为什么会导致实现返工

1. **`getRouters` 缺失 = HR 后台菜单树无法加载 = 后台完全不可用**。03 §1.4 明确说明"RuoYi 的路由本就是'**后端返回菜单树 → 前端动态注册路由**'"。RuoYi-Vue 前端在 `permission.js` 路由守卫中调用 `getRouters()` 获取动态路由，若该接口不存在，登录成功后**前端拿不到任何路由，页面停在空白布局壳上**。这是 05 作为接口设计文档最严重的一处遗漏——它设计了 58 个接口，却漏了让整个后台能跑起来的那一个。
2. **改 RuoYi 原生路径的代价被低估**。05 §3.5 的 `/api/hr/auth/login` 意味着要改 RuoYi 的 `SysLoginController` 的 `@RequestMapping`，同时改前端 `src/api/login.js`、`src/store/modules/user.js`、`src/permission.js`、`src/utils/request.js` 的 401 跳转逻辑。这些是 RuoYi 前端框架的核心文件，改动会显著增加后续升级难度（呼应 C-08 的升级性讨论）。**而收益为零**——这四个接口只在内网可达，路径叫什么不影响安全。
3. **Nginx 黑名单漏洞（已在 N-01 指出）**：03 §3.2⑥ 的黑名单只覆盖 `/api/admin/`、`/api/system/`、`/actuator/`、`/druid/`、`/swagger`、`/v3/api-docs`。RuoYi 原生的 `/login`、`/getInfo`、`/getRouters`、`/captchaImage` **一条都没被拦住**，会落入 `location /` 被当作静态资源查找、404 或返回 index.html。虽然不会真的泄露后台功能（因为 `try_files` 不会代理到 8080），但**如果实现者为了让后台工作而在公网 vhost 加了 `/login` 的 proxy_pass，HR 登录接口就直接暴露公网了**——这是一个容易踩的坑。

#### 裁决结论

**HR 端的登录、用户信息、路由、图形验证码四个接口一律使用 RuoYi 原生路径，不做任何改造。同时补入 `getRouters` 接口文档，并在 Nginx 公网 vhost 显式 403 这四个路径。**

**裁决理由**：
1. RuoYi 基座的价值就在于"开箱即用覆盖 60% 系统管理端工作量"（裁决基线 00）。改动它的认证入口路径是**用零收益换取升级困难 + 4 个前端核心文件的改动**，与选型初衷背道而驰。
2. 03 §1.4 的"三前缀硬边界"约束的对象是**本项目新增的接口**，RuoYi 原生的固定路径是既成事实的例外。裁决：**把这四个路径显式登记为"第四类：RuoYi 原生固定路径"，在 Nginx 黑名单中逐条 403**，而不是强行改造它们去适配前缀规则。规则要适配现实，不是反过来。

#### 落地修改指令

| 文档 | 章节 | 改成什么 | 优先级 |
|---|---|---|---|
| **05** | §3.5 HR 端认证 **全节重写** | H-AUTH-001 `POST /api/hr/auth/login` → `POST /login`（RuoYi 原生，请求体 `{username, password, code, uuid}`，响应 `{code, msg, token}`）；H-AUTH-002 → `GET /getInfo`（响应 `{user, roles, permissions}`）；H-AUTH-003 → `POST /logout`；**新增 H-AUTH-004 `GET /getRouters`**（响应动态路由树，RuoYi 原生结构）；图形验证码 → `GET /captchaImage` | **必改（否则后台不可用）** |

### N-12　孤儿表与无接口支撑的能力（High）

#### 冲突描述

**逐表核对 04 的 20 张表是否有 05 的接口或定时任务使用**：

| 表 | 写入方 | **读取方** | 结论 |
|---|---|---|---|
| `audit_resume_access` | 03 §5.2.2 审计切面 | **无任何接口** | ❌ **孤儿表（只写不可读）** |
| `app_status_history` | 06 §4.1 状态变更 | **无任何接口** | ❌ **孤儿表（只写不可读）** |
| `ivw_schedule` | 无（P2） | 无 | ❌ **完全孤儿** |
| `ivw_feedback` | 无（P2） | 无 | ❌ **完全孤儿** |
| `not_message` | 06 §7.2 N1/N2/N3 | **无任何接口**（05 无站内消息接口） | ❌ **一期只写不可读** |
| `not_record` | 无（P1） | 无 | ⚠️ P1 预留，可接受 |
| `job_template` | 无（P1） | 无 | ⚠️ P1 预留，可接受 |
| `stu_internship`/`stu_certificate`/`stu_activity` | 无（P1） | 无 | ⚠️ P1 预留，可接受 |
| 其余 10 张 P0 表 | ✅ | ✅ | 正常 |

**反向核对：05 的接口是否都有表支撑**——已在 N-06 覆盖（`owner_user_id` 等字段缺失导致数据权限接口无表支撑）。补充发现：

| 05 接口 | 依赖 | 问题 |
|---|---|---|
| H-RESUME-004 添加/更新内部备注 | `app_hr_note` | ✅ 有表。但 05 响应体是**单条** `hrNote` 对象，04 的表是 **1:N**（`KEY idx_application_id`，可多条）。**语义不一致**：到底是"每个 HR 各留一条备注"还是"整个投递只有一条备注"？ |
| H-RESUME-002 简历详情响应 `hrNote` | 同上 | 单条 vs 多条同样存疑 |

#### 为什么会导致实现返工

1. **审计表只写不可读 = 审计能力形同虚设**。03 §5.2.2 用了整整一节论证审计的必要性，并明确列出审计要回答的问题："谁在何时看过某候选人的个人信息"、以及 PIPL 第 45 条的**查阅权**——"某学生要求查询其个人信息被谁处理过"。**没有查询接口，这个问题在系统里无法被回答**，只能让 IT 直接连数据库跑 SQL。合规检查时这是明确的缺陷。
2. **`app_status_history` 只写不可读 = 简历详情页看不到流转历史**。HR 打开一份简历，无法看到"这份简历什么时候被谁改成了什么状态"。而 06 §1.5 设计的"5 分钟撤销"功能需要读 `previous_status`，管理员回退需要看历史——**都没有接口**。
3. **`not_message` 只写不可读 = N1/N2/N3 三条 P0 站内信发了但没人能看**。06 §7.2 把 N1（学生收投递成功）、N2（HR 收新简历提醒）、N3（学生收筛选通过）列为 **P0 必做**，04 却把 `not_message` 标为 P1，05 完全没有站内消息接口。**三份文档在这里形成了一个闭环的荒谬：写入是 P0，表是 P1，读取接口不存在。**

#### 裁决结论

**四条处置：**

1. **补 2 个查询接口**：审计日志查询、投递状态历史查询。
2. **`not_message` 升为 P0，并补 3 个站内消息接口**（列表、未读数、标记已读）。
3. **删除 `ivw_schedule` 与 `ivw_feedback` 两张 P2 表**（见第五部分过度设计）。
4. **裁决 `app_hr_note` 为 1:N 语义**（每个 HR 可各留备注），05 响应体改为数组。

**逐条理由**：

- **审计查询接口**：这不是"锦上添花"，是 PIPL 第 45 条查阅权的落地载体，且 03 §7.2 M5 验收标准第②条明确要求"**审计表能查到**某 HR 在某时看了某候选人的简历"——"能查到"就是要有接口。
- **状态历史接口**：06 §1.5 的撤销功能、§1.4 的并发冲突提示（"该简历已被其他同事操作，请刷新后重试"）都依赖它。
- **`not_message` 升 P0**：06 的 P0 通知范围是三份文档中最具体的（N1/N2/N3 + 模板变量），且需求原文 S-015 站内消息虽标"可选"，但**投递成功给学生一个确认**是最基本的产品闭环——学生投完简历如果什么反馈都没有，会反复重投或打电话问 HR，恰恰放大了项目要解决的痛点。**成本极低**（一张已建好的表 + 3 个 CRUD 接口 + 一个消息中心页面）。
- **`app_hr_note` 取 1:N**：04 的表设计（`hr_user_id` 字段 + 非唯一索引）本就是 1:N。改成 1:1 需要加唯一约束并丢失"多个 HR 各自记录评价"的能力，而后者在多 HR 协作场景（需求 A-003"多 HR 协作必需"）中是有价值的。**以表设计为准，改接口。**

### N-14　数据保留期出现四套不同数值（Medium）

#### 冲突描述

| 来源 | 未录用/默认 | 已淘汰 | 已入职 |
|---|---|---|---|
| **04** §4.1/§4.3 DDL `data_retention_days` 默认值 | **730 天** | 730 天（同一默认值） | 730 天 |
| **04** §8.3 行业惯例对照 | 1–2 年 | **6 个月–1 年** | 转入员工档案 |
| **06** §6.2 T4 | — | **365 天** | **730 天** |
| **编排层 Q-05 默认建议** | **365 天** | **180 天** | — |

**四套数值，且 04 自身的 DDL 默认值（730）与自己的 §8.3 建议（淘汰 6 个月–1 年）就不一致。**

#### 为什么会导致实现返工

1. **`auto_cleanup_date` 在投递时就被计算写入**（04 §8.1："创建日期 + data_retention_days，由 `@Scheduled` 定时任务计算填充"）。若一期按 730 天写入，后续甲方（Q-05）确认为"淘汰 180 天"，**已写入的历史记录不会自动更新**——需要一个数据订正脚本。而 PIPL 要求的是"实现目的所需的最短时间"，超期保留本身就是违规。
2. **T4 dry-run（N-09 裁决）的巡检报告会给出错误结论**。按 730 天算，一期上线后两年内 T4 永远扫不到任何记录，报告永远是"命中 0 条"——**看起来一切正常，实际是保留期设错了**，等到两年后才暴露。

#### 裁决结论

**统一采用编排层 Q-05 的建议值：未录用 365 天 / 已淘汰 180 天。`data_retention_days` 不再作为投递时固化的字段值，改为运行时从 `sys_config` 读取。**

**关键设计修正**：把 `data_retention_days` 从"投递时写死在行上的字段"改为"**运行时按状态查配置**"。

- **原设计的缺陷**：投递时无法知道这份简历将来会是"淘汰"还是"未录用"，因此投递时写入的 `data_retention_days` 必然是一个笼统的默认值，无法体现"淘汰 180 天 / 未录用 365 天"的差异化策略。
- **修正后**：`auto_cleanup_date` **不在投递时计算**，而是在**状态变为终态时**计算（`ELIMINATED` → `+180天`；其他状态在一届校招结束时统一按 `+365天`）。T4 扫描时直接比较 `auto_cleanup_date`。
- 保留期天数存 `sys_config`：`retention.days.eliminated=180`、`retention.days.default=365`，**甲方可在系统管理端直接改**，无需改代码。

### N-15　批量上限与导出上限在 05 完全缺失（Medium）

#### 冲突描述

3. **批量下载附件无上限是真实的可用性缺陷**。ZIP 流式输出虽然不落盘，但读取 500 个文件、压缩、传输的过程中，Tomcat 线程会被长时间占用（2.5GB 在内网千兆下也要 25 秒以上，公网更久），且 Nginx 的 `proxy_read_timeout` 默认 60 秒会截断。

**三个上限全部写入 05 的接口契约与错误码；H-RESUME-006 响应体改为全回滚语义。批量下载附件上限定为 100 份。**

#### 为什么会导致实现返工

实体类按 05 定义两个字段，MyBatis-Plus 映射时 `gpa` 找不到对应列。若开启了 `map-underscore-to-camel-case`，`gpa` 会被静默忽略（不报错），**学生填写的 GPA 提交后消失**——这是一个静默的数据丢失，且只有学生自己回头看资料时才会发现。

#### 裁决结论

**采用 05 的两字段设计，04 补 `gpa` 列。**

**理由**：GPA（如 `3.8/4.0`）与排名（如 `前 10%`）是两个不同的量，HR 筛选时关注点也不同（GPA 可比较，排名反映相对位置）。合并成一个自由文本字段会让学生填写时无所适从（填哪个？还是都填？），也让 HR 无法从列表快速对比。两个字段的成本是一列 20 字节。

#### 落地修改指令

| 文档 | 章节 | 改成什么 | 优先级 |
|---|---|---|---|
| **04** | §4.1 `stu_education` DDL | 在 `gpa_rank` 前新增 `gpa VARCHAR(20) DEFAULT NULL COMMENT 'GPA/绩点（选填，文本格式兼容 3.8/4.0、88分 等写法）'`；`gpa_rank` 的 COMMENT 改为"专业排名（选填，如 前10%、5/120）"，长度从 VARCHAR(20) 放宽到 VARCHAR(50)（对齐 05 §7.3 的 ≤50 字校验） | 必改 |
| **04** | §2 ER 图 `STU_EDUCATION` | 补 `varchar gpa "GPA"` | 建议改 |
| **05** | §7.3 | 保持不变（本条以 05 为准） | — |

## 第五部分：过度设计与不足设计清单

### 5.1 审查标尺

本节的判定标准严格限定为设计简报第三节的三条硬约束：

1. **单机部署**，Windows 台式机，i5 / 16GB / SSD
2. **峰值 20 并发用户**，每届简历数百到数千份，岗位数十个
3. **无专职运维**，部署与备份需一条命令跑通

任何设计只要不能用这三条论证其必要性，即判定为过度设计。
