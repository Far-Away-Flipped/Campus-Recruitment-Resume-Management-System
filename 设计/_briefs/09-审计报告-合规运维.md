### 最严重的五个缺陷（不修则上线即违法或必然事故）

1. **【CL-04 全部个人权利响应机制缺失】** 个保法第 44–50 条赋予个人的**查阅、复制、更正、补充、删除、撤回同意、注销账号、要求解释**八项权利，在 58 个接口中**一个都没有**。学生注册后**没有任何途径删除自己的数据**——个保法第 47 条规定的删除权是**无条件法定义务**，缺失即违法，且是被投诉时监管第一个查的项目。
2. **【CL-01 隐私政策实体不存在】** 05 §3.1 只有一个 `agreePrivacy: true` 布尔字段，**《隐私政策》正文本身在全部设计文档中不存在**——没有页面、没有接口、没有存储表、没有版本管理。学生勾选的是一个**指向空内容的同意**。个保法第 17 条要求的八项告知要点一项都无法履行，这个"同意"在法律上**自始无效**，据此收集的全部个人信息处理均无合法性基础。
3. **【CL-03 匿名化方案是假匿名化】** 04 §8.2 的"匿名化"仅替换姓名/手机号/邮箱，**保留学校、专业、学历、入学毕业年份、GPA、实习公司、社团职务、简历附件原件**。凭"某校某专业2026届硕士 + 某公司实习"可在极小候选集内唯一识别到人；简历附件里更是完整姓名手机号。这属于个保法第 73 条定义的**去标识化**而非**匿名化**，**仍属个人信息，仍受个保法全部约束**——04 §8.2 把它当作"已脱离个保法"处理，是一个**法律定性错误**。
4. **【CL-05 户籍所在地字段无招聘必要性且构成就业歧视风险】** S-004 要求填写户籍所在地，且为**必填**。招聘场景下户籍与岗位胜任力无任何关联，违反个保法第 6 条最小必要原则；同时《就业促进法》第 3 条、第 31 条禁止基于户籍的就业歧视，**收集即构成歧视嫌疑的证据**。这是本项目最容易被举报、被查实的单点。
5. **【OP-01 备份方案三选一未定，且三套都不能无人值守运行】** 04 §10 的 `mysqldump -p`（无密码值）在任务计划中会**永久挂起**——每日备份**一次都不会执行**且不报错；`robocopy /MIR` 会把 T4 清理掉的附件**从备份端一起删除**，使"清理"变成"不可恢复的销毁"。N-08 已识别冲突，但**未给出可直接执行的脚本**。本报告第三部分给出。

## 1.1 告知同意（第 13、14、17 条）

### CL-01【缺失 · 阻塞上线】隐私政策实体在全部设计文档中不存在

**现状核查**：

| 位置 | 现状 |
|---|---|
| 05 §3.1 S-AUTH-002 注册请求体 | 只有 `"agreePrivacy": true` 一个布尔值 |
| 05 §5.1 页面清单第 2 行 | 注册页要素列出"隐私政策勾选"，**但无隐私政策页面** |
| 05 页面清单全表（9 页） | **无 `/privacy` 或 `/agreement` 页面** |
| 05 接口全表（58 个） | **无获取隐私政策正文的接口** |
| 04 全部 22 张表 | **无隐私政策正文存储表**；`sys_brand_config` 的 12 个 key 中无一项与政策相关 |
| 03 §5.1.7 隐私合规行 | 只要求"入库记录 `policy_version` 与同意时间戳" |

**结论：学生在注册页勾选的复选框，其链接目标不存在。**

**法条依据**：个保法第 17 条要求处理者在处理前**以显著方式、清晰易懂的语言真实、准确、完整**向个人告知：① 处理者名称与联系方式；② 处理目的、处理方式；③ 处理的个人信息种类；④ 保存期限；⑤ 个人行使权利的方式和程序；⑥ 法律法规规定应当告知的其他事项。第 14 条要求同意须在**充分知情**的前提下作出。

**违法风险**：告知内容不存在 ⇒ 同意不成立（第 14 条）⇒ 处理无合法性基础（第 13 条）⇒ 违反第 66 条，责令改正、警告、没收违法所得，拒不改正处 100 万元以下罚款，直接责任人 1–10 万元。**这是本项目最基础的合规缺口，且一次现场检查即可发现。**

**最小实现方案**（1.5 人日）：

1. **新增 1 张表** `sys_privacy_policy`：

```sql
CREATE TABLE `sys_privacy_policy` (
    `id`             BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
    `policy_type`    VARCHAR(32)  NOT NULL COMMENT '类型：PRIVACY-隐私政策, TERMS-用户协议',
    `version`        VARCHAR(32)  NOT NULL COMMENT '版本号，如 v1.0-20260901',
    `title`          VARCHAR(128) NOT NULL COMMENT '标题',
    `content`        MEDIUMTEXT   NOT NULL COMMENT '正文（HTML，由 Jsoup 清洗后入库）',
    `effective_time` DATETIME     NOT NULL COMMENT '生效时间',
    `is_current`     CHAR(1)      NOT NULL DEFAULT '0' COMMENT '是否当前生效版本：0-否, 1-是',
    `create_by`      VARCHAR(64)  DEFAULT NULL,
    `create_time`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_type_version` (`policy_type`, `version`),
    KEY `idx_type_current` (`policy_type`, `is_current`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='隐私政策与用户协议正文表（历史版本永不删除，供追溯"某学生同意的是哪一版"）';
```

> **历史版本永不删除**是硬约束：`stu_user.policy_version`（N-06 已补）只有在能取回对应正文时才有意义。删掉旧版本正文 = 无法证明当初告知了什么。

2. **新增 1 个匿名接口**：`GET /api/portal/policy/{type}`（`type` ∈ `privacy|terms`），返回当前生效版本的 `{version, title, content, effectiveTime}`。列入 N-10 的匿名白名单。
3. **新增 1 个页面**：`/policy/privacy` 与 `/policy/terms`（同一组件，路由参数区分）。注册页勾选文案改为：`我已阅读并同意《隐私政策》和《用户协议》`，两个书名号为新窗口链接。
4. **正文内容**：**由甲方法务/人文发展部提供，不由开发方拟写**。开发方提供包含以下**八项必备要素**的模板骨架，交甲方填充与用印：

| # | 告知要点 | 本项目应写明的内容 |
|---|---|---|
| 1 | 处理者身份与联系方式 | 遨天科技（北京）有限公司；地址；**个人信息保护负责人姓名与专用邮箱**（见 CL-14） |
| 2 | 处理目的 | 仅用于 2026 届（及后续届）校园招聘的简历接收、筛选、面试安排与录用决策；**不用于任何其他目的，不对外提供** |
| 3 | 处理方式 | 学生自主填写并上传；系统存储于公司自有服务器（境内）；HR 在授权范围内查阅、下载、导出 |
| 4 | 处理的信息种类 | **逐字段列出**：姓名、性别、出生日期、手机号、邮箱、现居住地、教育经历（学校/专业/学历/起止时间/GPA）、简历附件、实习经历、技能证书、社团经历、登录 IP 与设备信息 |
| 5 | **保存期限** | 已淘汰候选人 **180 天**；未录用候选人 **365 天**；到期后删除或匿名化（与 N-14 裁决值一致，**必须逐字对齐**，写不同的数就是虚假告知） |
| 6 | 个人权利行使方式 | 查阅/复制/更正/补充/删除/撤回同意/注销账号的**具体路径**（"个人中心 → 隐私与账号"）与**受理时限（15 个工作日）** |
| 7 | 投诉举报渠道 | 专用邮箱 + 电话 + **不满意时可向北京市网信部门投诉**的告知 |
| 8 | 政策更新机制 | 更新后如何通知、重新征得同意的规则 |

5. **政策更新时的重新同意机制**：学生登录后，若 `stu_user.policy_version` ≠ 当前生效版本，前端强制弹出新版政策并要求重新勾选，未同意则只能浏览岗位、不能投递。实现为 `PortalTokenFilter` 之后的一个拦截器，成本约 0.3 人日（已含在 1.5 内）。

**是否阻塞上线**：**是**。没有隐私政策正文，收集行为无合法性基础。

### CL-02【部分设计 · 阻塞上线】同意的"自愿、明确"要件与勾选交互

**现状核查**：03 §5.1.7 已要求"注册页必须有**独立勾选**的《隐私政策》与《用户协议》（默认不勾）"——**这一条设计是正确的，予以确认**。05 §3.1 的 `agreePrivacy` 字段也有服务端校验（05 §表：`agreePrivacy | 是 | boolean=true | "请阅读并同意隐私政策"`）。N-06 已补 `policy_version` 字段。

**剩余缺口 3 处**：

| # | 缺口 | 触发场景 | 违反 |
|---|---|---|---|
| a | **未区分《隐私政策》与《用户协议》的两个独立勾选** | 05 只有一个 `agreePrivacy` 布尔值。两份文件性质不同（一份是个人信息告知，一份是服务条款），捆绑为一个勾选属于"**以捆绑方式取得同意**" | 第 14 条"自愿、明确" |
| b | **同意记录缺少完整证据链** | `stu_user` 只有 `privacy_agreed`、`privacy_agreed_time`、`policy_version` 三个字段，**无同意时的 IP**。发生争议时无法证明"是本人在该时间该终端作出的" | 第 14 条举证责任 |
| c | **未记录同意行为到审计表** | 03 §5.2.2 的 11 类审计事件中**没有"同意/撤回同意"** | 第 51 条 |

**最小实现方案**（0.5 人日）：

1. 注册请求体 `agreePrivacy: true` 拆为 `agreePrivacy: true` + `agreeTerms: true`，两个复选框独立渲染、默认均不勾、缺一不可提交。
2. `stu_user` 补 2 列：

```sql
ALTER TABLE `stu_user`
  ADD COLUMN `terms_version` VARCHAR(32) DEFAULT NULL
      COMMENT '注册时同意的用户协议版本号' AFTER `policy_version`,
  ADD COLUMN `consent_ip` VARCHAR(64) DEFAULT NULL

```

3. `audit_resume_access.operation_type` 枚举新增 `CONSENT_GRANT`（同意）、`CONSENT_WITHDRAW`（撤回同意），注册与撤回时各写一条。

### CL-03【缺失 · 不阻塞，但必须写入约束】单独同意的情形识别

**个保法要求"单独同意"的五类情形**（第 23、25、26、29、39 条），逐条对照本项目：

| 情形 | 法条 | 本项目一期是否触发 | 处置 |
|---|---|---|---|
| 向**其他处理者提供**个人信息 | 第 23 条 | ❌ 一期不触发。但**P1 的短信通知会把手机号交给阿里云**——阿里云在此为**受托处理者**（第 21 条），不是"其他处理者"，无需单独同意，但**必须在隐私政策中披露委托处理关系与受托方名称** | 写入隐私政策要点 3 |
| **公开**个人信息 | 第 25 条 | ❌ 不触发 | — |
| 公共场所图像/身份识别设备 | 第 26 条 | ❌ 不触发 | — |
| 处理**敏感个人信息** | 第 29 条 | ⚠️ **需判定**（见下） | 见下 |
| 向**境外**提供 | 第 39 条 | ❌ 不触发（C-09 已明确排除境外/香港主机，理由正是数据出境合规）——**该裁决予以确认，是正确的** | 保持 |

**敏感个人信息判定（第 28 条）**：个保法列举的敏感个人信息包括生物识别、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹，以及**不满十四周岁未成年人的个人信息**。

- 本项目收集的字段中，**无一项落入法定列举范围**。
- **但需注意两个边界**：① `stu_profile.birth_date` 会暴露年龄，若出现不满 14 周岁的填报（校招场景下几乎不可能，但系统不禁止），则**全部信息升格为敏感个人信息**，需单独同意 + 监护人同意；② 简历附件（PDF/Word）是**学生自由上传的非结构化内容**，系统无法控制其中是否包含身份证号、健康状况、婚育状况、政治面貌等敏感信息——**实践中中国学生简历包含政治面貌（党员）、身份证号的比例很高**。

**处置方案**（0.2 人日）：

1. **注册/资料填写时对出生日期做硬校验**：`birth_date` 必须使当前年龄 ≥ 16 周岁（未满 16 周岁在中国不得就业，《劳动法》第 15 条），否则拒绝并提示。这**同时解决了未成年人敏感信息问题和用工合规问题**，是一行校验换两个合规点。
2. **简历附件上传页增加显著提示**：`为保护您的隐私，请勿在简历中填写身份证号、银行账号、健康状况、婚育状况等与应聘无关的敏感信息。` —— 这是处理者的**提示义务**，也是发生泄露时的责任切分依据。
3. 隐私政策中写明"我们不主动收集敏感个人信息；若您自行在附件中提供，视为您单独同意我们为招聘目的处理该信息"。

**是否阻塞上线**：否，但第 1 项校验必须随 M3 一起实现。

## 1.2 最小必要原则（第 6 条）—— 字段逐个审查

**法条依据**：个保法第 6 条"处理个人信息应当具有明确、合理的目的，并应当与处理目的**直接相关**，采取对个人权益影响最小的方式。收集个人信息，应当限于实现处理目的的**最小范围**，不得过度收集。"

### CL-04【缺失 · 阻塞上线】S-004~S-009 字段必要性逐项裁决

### CL-05【部分设计 · 不阻塞】`data_retention_days` 的落地状态

   —— 没有这个开关，"清理规则正确性"在一期**无法被验证**，只能等到第 181 天用真实数据赌一次。

### CL-06【缺失（法律定性错误）· 阻塞上线】"匿名化"方案实为去标识化，仍属个人信息

**这是本报告中定性最严重的一条。**

**现状核查（04 §8.2 清理策略表原文）**：

| 场景 | 04 的策略 | 04 的说明原文 |
|---|---|---|
| 已录用 | **匿名化** | "保留教育背景、技能等非标识数据供招聘分析，姓名/手机号/邮箱替换为匿名标识符" |
| 未录用 | 逻辑删除 | "保留1-2年作为人才库储备，到期后匿名化" |
| 已淘汰 | 物理删除 | "建议保留6个月-1年后物理删除个人标识数据" |
| 学生注销 | 逻辑删除 + 匿名化 | "个人标识字段清空" |

**法条依据**：

- 个保法**第 73 条第（四）项**：**匿名化**是指个人信息经过处理**无法识别特定自然人且不能复原**的过程。
- 第 73 条第（三）项：**去标识化**是指个人信息经过处理，**在不借助额外信息的情况下**无法识别特定自然人的过程。
- **第 4 条第 1 款**：个人信息**不包括匿名化处理后的信息**。
- 反推：**去标识化后的信息仍然是个人信息，仍受个保法全部约束**（包括保留期限、权利响应、泄露通知）。

**04 的方案属于哪一种？—— 去标识化。理由（三条，逐条可验证）**：

1. **准标识符组合可唯一识别**。清理后保留的字段包括：学校名称、专业、学历、入学年份、毕业年份、GPA、实习公司名、社团名称与职务。以本项目容量估算（每年 2000 名投递者、每年 30 个岗位）为背景：
   - 检索条件"北京航空航天大学 + 飞行器动力工程 + 硕士 + 2026 届"在全国范围内的匹配人数是**个位数到十位数**；
   - 叠加"曾在 XX 航天科技集团实习" + "GPA 3.8/4.0"后，**匹配人数基本为 1**。
   - 这正是学术界所称的 **quasi-identifier 重识别攻击**，且本场景的重识别成本极低——一次学校官网 + 领英检索即可完成。
2. **简历附件原件未被处理**。04 §8.2 全表**只字未提附件**。`stu_resume_file` 指向的 PDF/Word 原件中包含**完整姓名、手机号、邮箱、家庭住址、照片**——把数据库里的姓名替换成 `匿名用户_1024`，而磁盘上仍躺着 `张三_简历.pdf`，这不是匿名化，是**自欺**。
3. **快照未被处理**。C-01 裁决新增的 `app_snapshot` 表存有 `snapshot_profile` JSON（含姓名手机号），且被明确定义为"**不可变、仅追加、永不 UPDATE/DELETE**"（07 §C-01：`AppSnapshotMapper` 只允许 insert 与 select）。**这与"到期匿名化"直接冲突——一个永不更新的表，如何执行匿名化？** 07 报告的 C-01 裁决与 04 §8.2 的清理策略之间存在一处未被识别的矛盾。

**触发场景（具体、可复现）**：

> 上线第 400 天。学生 A（已淘汰，180 天前应清理）向公司发函要求删除其全部个人信息。HR 查询系统，发现 A 的记录已被 T4"匿名化"，回复"已删除"。A 不认可，向北京市网信办投诉。监管调取系统：
> ① `app_snapshot` 表中 A 的 `snapshot_profile` JSON 完整保留姓名"张三"、手机号"13800138000"——**因为该表被设计为永不修改**；
> ② `E:\atmoto-recruit\data\attachments\2024\09\{uuid}.pdf` 是 A 的原始简历，含全部信息；
> ③ 每日备份中保留着 30 天日备 + 12 周周备 + 12 月月备 + 8 份离线副本，**每一份都含 A 的完整信息**。
> **认定结果**：未履行删除义务（第 47 条），且此前声称的"匿名化"不成立（第 73 条），系统仍在处理 A 的个人信息而无合法性基础。

**最小实现方案**（0.8 人日）：

**方案核心：放弃"匿名化"这一说法，改为「去标识化 + 明确的最终物理删除」的两段式，并把附件与快照纳入处理范围。**

1. **修正 04 §8.2 全表**，改为：

```
  4) 若第 3 步失败：文件成为孤儿，由 T3 每日扫描 data\attachments\ 与 stu_resume_file
     的差集，删除无 DB 记录的孤儿文件（这也顺带解决了历史遗留孤儿）
反向顺序（先删文件后删 DB）会产生"DB 有记录但文件不存在"的脏态，HR 点击预览报 500。
```

4. **备份中的历史副本如何处理**——**这是必须向甲方明示、无法用技术手段完全解决的一条**：

> 已删除的个人信息仍存在于历史备份中，最长 12 个月（月备）+ 8 份离线副本。这是**行业普遍现实**，监管实践中的通行处置是：① 在隐私政策中告知"删除后备份介质中的副本将随备份轮转周期自然覆盖，最长 12 个月"；② 承诺**不从备份中恢复已删除个人的数据**；③ 若因故障从备份恢复，恢复后**必须重新执行一次 T4 清理**才能对外提供服务。第 ③ 条必须写入 `restore.ps1` 的执行清单与运维手册。

**是否阻塞上线**：**是**——不是因为一期就要真删（一期没有到期数据），而是因为 **04 §8.2 的错误定性会误导实现者和甲方**，且 C-01 与清理任务的矛盾若不在设计阶段解决，P1 实现时会发现"快照删不掉"而临时打补丁。

### CL-07【部分设计 · 不阻塞】查阅权的四处盲区

**法条**：第 45 条"个人有权向个人信息处理者**查阅、复制**其个人信息"，处理者应当**及时提供**。

**现有能力**：学生可在个人中心查看自己填写的基本资料与教育经历（`S-PROFILE-001`、`S-EDU-001`、`S-RESUME-002`）。

**四处盲区**：

| # | 看不到的内容 | 为什么必须能看 |
|---|---|---|
| 1 | **投递快照** `app_snapshot` | 这是 HR 实际看到的版本。学生有权知道"公司手上关于我的信息到底是什么"，尤其在重投多版后 |
| 2 | **状态变更历史** `app_status_history` | 第 45 条的"个人信息"包括处理记录。且 S-014"我的投递"在需求中是 P0/P1 争议项（07 §Q-08） |
| 3 | **谁查看过我的简历** `audit_resume_access` | 07 §N-12 已明确指出"PIPL 第 45 条查阅权——某学生要求查询其个人信息被谁处理过——没有查询接口，这个问题在系统里无法被回答"。**N-12 补的是 HR 端审计查询接口（`/api/system/audit/resume-access`，权限 `system:audit:list`），不是学生端**。学生仍然无法自查 |
| 4 | HR 内部备注 `app_hr_note` | ⚠️ **此项例外**：内部备注属于处理者的内部评价意见，实践中通常认定为不属于必须向个人提供的范围（类比员工绩效评语）。**判定：不提供，但必须在隐私政策中说明"HR 的内部评价意见不在查阅范围内"** |

**最小实现方案**（0.2 人日）：

新增 1 个学生端接口 `GET /api/portal/me/access-log` —— 返回**本人**被访问的审计记录，字段为 `{时间, 操作类型(查看/预览/下载/导出), 操作方="公司HR"}`。

> **关键设计约束**：**不返回具体 HR 的姓名与 ID**。理由：HR 个人也是自然人，其"在何时查看了谁的简历"同样是其个人信息与工作记录；向候选人披露具体经办人姓名可能引发骚扰。返回"公司HR"这一角色粒度即可满足第 45 条"知悉处理情况"的立法目的。**这一取舍必须写入隐私政策。**

新增接口 `GET /api/portal/applications/{id}/snapshot` 与 `/history`，复用 N-12 已补的 HR 端逻辑，加 owner 校验。

**是否阻塞上线**：否（现有个人中心已覆盖最核心的资料查阅）。

### CL-08【缺失 · 阻塞上线】复制权 —— 无任何个人数据导出能力

**法条**：第 45 条明确并列"查阅、**复制**"。"复制"的立法含义是个人能获得一份**可脱离该系统留存的副本**，仅在网页上看得见不构成复制。

**现状**：58 个接口中，导出功能只有 `H-RESUME-007`（HR 导出 Excel）与 `H-RESUME-008`（HR 批量下载附件）——**全部是 HR 侧的批量导出，学生侧一个都没有**。系统为 HR 提供了批量导出全部候选人信息的能力，却不为个人提供导出自己一份信息的能力。**这个对比本身在合规检查中就极不利。**

**最小实现方案**（0.5 人日）：

新增 1 个学生端接口：

```
GET /api/portal/me/export
权限：学生登录态（本人）
限流：同一 student_id 每 24 小时最多 3 次（防滥用打满磁盘/CPU）
响应：application/zip 流
```

ZIP 内容（4 项，全部为本人数据）：

| 文件 | 内容 |
|---|---|
| `我的个人信息.json` | `stu_user`（不含 `password_hash`）+ `stu_profile` + `stu_education` + `stu_internship` + `stu_certificate` + `stu_activity` 的完整 JSON |
| `我的投递记录.json` | `app_application` + 全部 `app_snapshot` 版本 + `app_status_history`（**不含 `app_hr_note`**，理由见 CL-07） |
| `简历附件/` | `stu_resume_file` 指向的全部原件，按原始文件名 |
| `说明.txt` | 导出时间、数据范围说明、"HR 内部评价意见不在导出范围"的说明、投诉渠道 |

**实现要点**：
- 复用 `H-RESUME-008` 已有的 ZIP 流式输出代码，只换数据源与鉴权（owner 校验），**边际成本很低**。
- 每次导出**写审计**（`operation_type='SELF_EXPORT'`）。
- 导出不落盘（流式），不进 `data\export\` 目录，避免产生新的泄露面。

**是否阻塞上线**：**是**。这是第 45 条的明文义务，且实现成本仅 0.5 人日、复用已有代码。

### CL-09【部分设计 · 不阻塞】更正权与快照不可变的冲突

**法条**：第 46 条"个人发现其个人信息**不准确或者不完整**的，有权请求更正、补充。"

**冲突点**：C-01 裁决"`app_snapshot` 行一旦写入永不 UPDATE"。若学生发现投递时填错了手机号（导致收不到面试通知），**按现有设计无法更正已投递的快照**——只能"更新简历后重新投递"，而重投**仅限 `PENDING_SCREEN` 状态**且**最多 3 次**（C-01）。若已被 HR 改为 `SCREEN_PASSED`，学生**永久无法更正**其错误的联系方式。

**这不是理论问题**：手机号填错在校招中是真实高频的（学生用小号注册、换号），且后果严重（错过面试）。

**最小实现方案**（0.3 人日）：

**区分"事实性信息"与"评价性信息"，只允许更正前者，且以追加而非修改的方式实现**：

1. **联系方式（手机号、邮箱）不进快照的"不可变"保护范围**。理由：HR 需要的是**当前可联系到的方式**，不是"投递那一刻的方式"——快照不可变的立法目的是"HR 决策依据不被事后篡改"，而联系方式**不是决策依据**。
2. 实现：HR 端简历详情页的联系方式**改为实时从 `stu_profile` 读取**，不读快照；快照中的联系方式仅作历史留档。这**同时修正了 C-06 的一个隐患**——`snapshot_phone_mask` 冗余列若与当前手机号不一致，HR 按掩码打不通电话。
3. **其他字段（学校、专业、GPA、经历）的更正**：走"申诉通道"——学生通过 CL-15 的权利申请入口提交更正请求，HR 在后台核实后，由**招聘主管**执行一次"允许重投"授权（复用 O-3 裁决已有的 `hr:resume:reset` 权限点，把状态重置回 `PENDING_SCREEN`），学生即可重投一版正确的。**零新增接口。**

**是否阻塞上线**：否。

### CL-10【缺失 · 阻塞上线】删除权与账号注销 —— 完全没有

**法条**：第 47 条列举五类**处理者应当主动删除**的情形，并规定"**个人请求删除的，个人信息处理者应当删除**"。这是**无条件义务**，处理者只能在"法律规定的保存期限未届满，或者删除技术上难以实现"时改为停止处理。

**现状**：
- `stu_user` 有 `del_flag` 逻辑删除标记，但**没有任何接口能触发它**——04 §8.2 提到"学生主动注销账号"场景，但 05 的 58 个接口中**没有注销接口，页面清单 9 个页面中没有账号设置页**。
- 学生一旦注册，其个人信息在系统中**永久存在**，直到 180/365 天后由 P1 的 T4 清理——而 T4 一期是 dry-run。**实际上是无限期保留。**

**触发场景**：

> 学生 A 在宣讲会上注册投递，回去后决定不去这家公司，希望删除自己的信息。A 在门户上找遍所有页面，没有任何删除或注销入口。A 发邮件给 `hr@atmoto.cn`（这是 04 §7.4 配置的联系邮箱），HR 收到后不知如何处理——**系统没有给 HR 提供删除学生账号的功能**（05 的 HR 端接口中只有 `H-JOB-006 删除岗位`，无删除学生）。最终 A 的信息被继续保留。A 向 12377 或网信办投诉。

**最小实现方案**（1.0 人日）：

**A. 学生端自助注销**（0.6 人日）

```
POST /api/portal/me/deactivate
权限：学生登录态
请求：{ "password": "***", "reason": "OTHER", "confirmText": "确认注销" }
```

设计约束：
1. **二次确认 + 密码校验**，防止 token 被盗后恶意注销。
2. **不设"冷静期"**。第 47 条无"延迟删除"的余地；且冷静期需要额外的定时任务与状态管理。**立即执行。**
3. 注销页面必须**显式列出将被删除的内容**与**不会被删除的内容**：

```
将被永久删除：
  · 您的账号与登录凭据
  · 基本资料、教育经历、实习经历、技能证书、社团经历
  · 全部简历附件原件与预览文件
  · 全部投递记录及其历史版本
将被保留（法律要求）：
  · 个人信息访问审计记录（保留 3 年，依据《个人信息保护法》第 55、56 条）
    该记录仅含您的姓名与被访问时间，用于证明我们合规处理了您的信息
  · 历史备份介质中的副本将在最长 12 个月内随备份轮转自然覆盖
注销后不可恢复。若您已被安排面试，请先与 HR 确认。
```

4. **删除范围与顺序**：完全复用 CL-06 定义的删除顺序与补偿机制（先审计 → DB 事务 → 磁盘 → 孤儿兜底）。
5. **审计**：写 `operation_type='ACCOUNT_DEACTIVATE'`，`audit_resume_access` 中保留姓名快照——**这是唯一被允许保留的痕迹**，且必须在上述文案中告知。
6. **已投递岗位的处理**：注销即删除投递记录。若 HR 已将其标为 `SCREEN_PASSED` 甚至已安排面试（P2），HR 端会突然"少了一个候选人"。**处置**：注销时若存在非 `PENDING_SCREEN` 状态的投递，向 HR 发一条站内信（复用 N-12 升 P0 的 `not_message`）："候选人（姓名）已注销账号并删除其个人信息，相关投递记录已移除。" **不阻断注销**——第 47 条不允许以业务便利为由拒绝。

**B. HR 端代为删除**（0.4 人日）

用于学生通过邮件/电话提出删除请求的场景（并非所有学生都会登录系统操作）。

```
DELETE /api/admin/students/{studentId}
权限：hr:student:delete（**新增权限点，仅"招聘主管"角色持有，招聘专员无此权限**）
请求：{ "reason": "学生本人邮件请求，工单号 XXX", "confirmName": "张三" }
```

设计约束：
- `confirmName` 必须与 `stu_profile.real_name` 完全一致才执行——防止误删。
- 强制填写 `reason`（≥10 字），写入审计。
- 复用与自助注销**完全相同**的删除逻辑（同一个 `AccountDeletionService`），避免两套代码产生行为差异。

**是否阻塞上线**：**是**。删除权是个保法个人权利中最刚性、最常被行使、最容易被认定违法的一条。

### CL-11【缺失 · 阻塞上线】撤回同意

**法条**：第 15 条"基于个人同意处理个人信息的，个人有权撤回其同意。个人信息处理者应当**提供便捷的撤回同意的方式**。"

**现状**：无任何撤回入口。

**关键设计问题：撤回同意 ≠ 注销账号，两者必须分别提供吗？**

**裁决：本项目可以合并，但必须在 UI 上明示等价性。** 理由：本系统处理个人信息的**唯一法律基础就是同意**（不存在"订立合同所必需"——投递简历阶段尚无合同关系；不存在法定义务基础）。同意一旦撤回，全部处理即失去合法性基础，处理者必须停止处理——在本系统的语境下，"停止处理"与"删除"无实质区别，因为系统不具备"保留但不处理"的技术形态（数据躺在库里被 HR 随时可查，就是在处理）。

**最小实现方案**（0.3 人日）：

1. 个人中心新增「隐私与账号」页面（这是 CL-08/CL-10/CL-11/CL-15 的共同载体，**一个页面承载四项权利，是成本最优解**），包含四个入口：
   - 「查看我的隐私政策同意记录」（版本号 + 时间）
   - 「导出我的全部数据」→ CL-08
   - 「撤回同意并删除我的全部信息」→ 与「注销账号」为**同一个按钮**，文案写明："撤回同意将导致我们无法继续为您提供投递服务，您的账号与全部数据将被删除。"
   - 「行使其他权利 / 投诉」→ CL-15
2. 撤回时写审计 `operation_type='CONSENT_WITHDRAW'`。

**是否阻塞上线**：**是**（但与 CL-10 共用实现，边际成本仅 0.3 人日）。

## 1.5 个人信息保护负责人与投诉渠道（第 50、52 条）

### CL-14【缺失 · 阻塞上线】个人信息保护负责人未指定、联系方式未公开

**法条**：
- **第 52 条**：处理个人信息达到国家网信部门规定数量的处理者应当指定个人信息保护负责人，**并公开负责人的联系方式**。
- **第 17 条第（一）项**：告知义务中包含"处理者的名称和**联系方式**"——**这一项不设数量门槛，任何处理者都必须履行**。

**数量门槛判定**：截至本报告日期，国家网信部门**尚未发布**第 52 条的具体数量标准（《个人信息保护合规审计管理办法》2025 年 5 月施行，以 100 万人为审计门槛）。本项目年处理约 2000 人、三年约 6000 人，**远低于 100 万**，因此：
- **第 52 条的"指定负责人"义务：法律上不强制触发。**
- **但第 17 条的"公开联系方式"义务：无条件适用，必须履行。**

**现状**：04 §7.4 配置了 `contact_email = hr@atmoto.cn`（且备注"需甲方确认"）。这是**招聘业务邮箱**，不是**个人信息保护专用联系方式**——学生发到这个邮箱的"我要删除数据"会混在几百封投递咨询里。

**最小实现方案**（0.2 人日）：

1. `sys_brand_config` 新增 3 个 key：

```sql
INSERT INTO sys_brand_config (config_key, config_value, config_type, config_group, description, create_by, create_time) VALUES
```

3. **向甲方的行动项**：
   - 开通 `privacy@atmoto.cn` 邮箱（或复用现有邮箱建规则），**指定专人（建议人文发展部/法务）负责**；
   - 建立**15 个工作日内响应**的内部工单流程（个保法第 50 条未规定具体时限，但《信息安全技术 个人信息安全规范》GB/T 35273 建议 30 日内，行业实践普遍承诺 15 个工作日）。

**是否阻塞上线**：**是**（第 17 条的联系方式公开是无条件义务，且成本仅 0.2 人日）。

### CL-15【缺失 · 阻塞上线】权利行使的申请受理机制与拒绝时的说明理由

**法条**：第 50 条"个人信息处理者应当建立**便捷的**个人行使权利的申请受理和处理机制。**拒绝个人行使权利的请求的，应当说明理由。**"

**现状**：无任何申请入口。学生只能靠猜一个邮箱地址。

**最小实现方案**（0.5 人日）：

**方案：轻量工单表 + 学生端提交页 + HR 端处理页。不做复杂工单系统。**

1. 新增 1 张表：

```sql
CREATE TABLE `req_privacy_request` (
    `id`            BIGINT       NOT NULL AUTO_INCREMENT COMMENT '申请ID',
    `student_id`    BIGINT       DEFAULT NULL COMMENT '学生ID（登录提交时填充；未登录提交时为NULL）',
    `contact`       VARCHAR(128) NOT NULL COMMENT '联系方式（手机号或邮箱，用于回复与身份核验）',
    `request_type`  VARCHAR(32)  NOT NULL COMMENT '请求类型：ACCESS-查阅, COPY-复制, CORRECT-更正, DELETE-删除, WITHDRAW-撤回同意, EXPLAIN-解释说明, COMPLAINT-投诉, OTHER-其他',
    `content`       TEXT         NOT NULL COMMENT '申请内容',
    `status`        VARCHAR(20)  NOT NULL DEFAULT 'PENDING' COMMENT '状态：PENDING-待处理, PROCESSING-处理中, DONE-已完成, REJECTED-已拒绝',
    `handler_id`    BIGINT       DEFAULT NULL COMMENT '处理人（sys_user.user_id）',
    `reply_content` TEXT         DEFAULT NULL COMMENT '处理结果或**拒绝理由**（第50条要求拒绝必须说明理由）',
    `reply_time`    DATETIME     DEFAULT NULL COMMENT '回复时间',
    `due_time`      DATETIME     NOT NULL COMMENT '承诺回复期限（创建时+15个工作日）',
    `source_ip`     VARCHAR(64)  DEFAULT NULL COMMENT '提交IP',
    `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '提交时间',
    PRIMARY KEY (`id`),
    KEY `idx_status_due` (`status`, `due_time`),
    KEY `idx_student_id` (`student_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='个人信息权利行使申请表（个保法第50条：便捷的申请受理机制 + 拒绝须说明理由）';
```

> **`status='REJECTED'` 时 `reply_content` 必须非空**——用数据库层的 CHECK 或应用层校验强制。这是把第 50 条"拒绝应当说明理由"从口头义务固化到数据结构的最低成本手段。

2. 接口 3 个：
   - `POST /api/portal/privacy-requests`（**匿名可提交**——已注销的人也要能申诉，需图形验证码防刷）
   - `GET /api/portal/privacy-requests/mine`（登录后查自己的申请进度）
   - `GET|PATCH /api/admin/privacy-requests`（HR 端列表与回复，权限 `hr:privacy:handle`，仅招聘主管）

3. **超期提醒**：并入 T3 定时任务，扫描 `status IN ('PENDING','PROCESSING') AND due_time < NOW()` 的记录，写入每日运营日报（03 §5.5 已有日报机制，零新增组件）。**这是"便捷机制"能真正运转的保证——否则工单会静静躺在库里。**

4. 门户页脚与个人中心「隐私与账号」页均提供入口。

**是否阻塞上线**：**是**。第 50 条是明文的机制建设义务，且此表同时承载了 CL-09（更正申诉）、CL-12（解释说明）、CL-13（近亲属）三项权利的落地通道——**一张表解决四条法条**，性价比极高。

## 1.6 数据泄露通知（第 57 条）

### CL-16【缺失 · 不阻塞上线（文档类，但必须随交付）】

**法条**：第 57 条"发生或者**可能发生**个人信息泄露、篡改、丢失的，个人信息处理者应当**立即采取补救措施**，并**通知**履行个人信息保护职责的部门和个人。"通知内容应包括：① 已经发生或可能发生的信息种类、原因和可能造成的危害；② 已采取的补救措施和个人可采取的减轻危害的措施；③ 处理者的联系方式。
> 例外：处理者采取措施能够**有效避免信息泄露造成危害**的，可以不通知个人；但监管部门认为可能造成危害的，有权要求通知。

**现状**：03 §5.5 有告警机制（邮件 + 短信给 IT），但**告警的是"服务宕机/磁盘将满/备份失败"，没有任何一条是"个人信息泄露"**。全部设计文档中**无泄露应急预案、无通知模板、无判定标准、无演练要求**。

**最小实现方案**（0.5 人日，纯文档 + 2 个告警规则）：

**A. 新增交付文档 `doc\个人信息安全事件应急预案.md`**，包含：

| 章节 | 内容 |
|---|---|
| 事件分级 | **P0**：数据库被拖库、备份介质丢失/被盗、勒索软件加密、`E:` 盘被非授权访问 → 立即启动全流程<br>**P1**：单个 HR 账号被盗用、异常大批量导出（>1000 条/日）、附件被越权访问 → 24 小时内评估<br>**P2**：单条记录的越权访问尝试（已被系统拦截） → 记录并月度复盘 |
| 判定标准 | 明确"可能发生"的触发信号：审计表中单个操作人 24 小时导出 >2000 条；非工作时间（22:00–06:00）的批量下载；同一账号异地 IP 登录；`error.log` 出现大量 403/401 后突然成功 |
| **通知时限** | 发现后 **24 小时内**向北京市网信办报告（个保法未定时限，但《网络数据安全管理条例》2025年1月施行，第 12 条要求重要事件 24 小时内报告）；**72 小时内**通知受影响个人 |
| 通知渠道 | 站内信（`not_message`，N-12 已升 P0）+ 短信 + 邮件三通道并发；若受影响人数 >500 或联系方式已失效，在门户首页 Banner（`sys_banner`）公告 |
| 通知模板 | 预置文案，含第 57 条要求的三项内容，留空处仅需填事件事实 |
| 责任人 | 个人信息保护负责人（CL-14）主责；IT 负责技术处置；HR 负责人负责对外沟通 |
| **演练要求** | **每年一次桌面推演**，与季度恢复演练合并做一次，记录于 `doc\恢复演练记录.md` |

**B. 新增 2 条自动告警规则**（并入 `healthcheck.ps1`，03 §5.5 已有框架，边际成本极低）：

```
规则 A（异常导出）：查询 audit_resume_access，若单个 operator_id 在过去 24 小时内
  EXPORT_EXCEL 的累计 record_count > 2000，或 DOWNLOAD_ATTACHMENT 次数 > 200
  → 邮件告警给个人信息保护负责人 + HR 负责人（不是给 IT——这是管理事件不是技术事件）

规则 B（非工作时间访问）：若 22:00–06:00 之间出现 EXPORT_EXCEL 或
  DOWNLOAD_ATTACHMENT 操作 → 记入次日运营日报的"需关注"栏
```

> **为什么规则 A 的收件人是 HR 负责人而不是 IT**：内部人员批量导出是本项目**最可能的泄露形态**（见第二部分 DL-01），而 IT 无法判断"张三导出 3000 条"是否是正常工作。只有 HR 负责人知道当天有没有这个业务需要。

**是否阻塞上线**：否（可与部署文档一并交付），但**必须在上线前交付**，不可推迟到 P1。

## 2.2 DL-01【Critical】H-007 批量导出 Excel —— 最大泄露口

### 现状核查

| 管控手段 | 现状 |
|---|---|
| 单次条数上限 | ⚠️ N-15 已补 **1000 条**（05 原文无任何上限） |
| 字段可选 | ✅ `fields` 参数支持（05 §3.7 H-RESUME-007） |
| **审批流** | ❌ 无 |
| **水印** | ⚠️ N-15 提到"Excel 末行写入导出人与时间水印"（来自 03 §8 R5④），**但只在末行写一行文字——删掉这一行即无痕迹** |
| 审计留痕 | ⚠️ `audit_resume_access.operation_type='EXPORT_EXCEL'` 有，**但 DDL 中无"导出条数""筛选条件""字段集""文件 SHA256"字段**（DL-07） |
| 频次限制 | ❌ 无 |
| 数据范围 | ✅ 招聘专员仅本人负责岗位（N-06 补 `owner_user_id`） |

### 触发场景（具体）

> 招聘主管账号（数据范围＝全部）在 2027 年 3 月某个周五 19:40，连续执行 6 次导出，每次 1000 条，覆盖三届全部 6000 名候选人的姓名、手机号、邮箱、学校、专业、学历、GPA。
> **现有设计下会发生什么**：
> ① 每次导出都在 1000 条上限内，**系统不会拒绝任何一次**；
> ② 审计表留下 6 条 `EXPORT_EXCEL` 记录，但**记录里没有"导出了多少条""导出了哪些字段"**（04 的 `audit_resume_access` 只有 `operation_detail VARCHAR(512)` 一个自由文本字段），事后无法证明泄露规模；
> ③ 没有任何告警——`healthcheck.ps1` 检查的是磁盘、证书、备份，不看审计表；
> ④ Excel 末行的"导出人：李四 2027-03-05"被删掉后，文件与任何一份普通简历汇总表无异；
> ⑤ 日报（03 §5.5）统计的是"新注册数、投递数、HR 登录次数"，**不含导出量**。
> **结果**：6000 人的完整个人信息以一个 Excel 文件的形式离开公司，公司在事发前无从知晓，事发后无法界定范围。

**N-15 的 1000 条上限确实提高了成本——从 1 次点击变成 6 次点击。这个提升幅度不足以构成实质障碍。**

### 管控方案（0.6 人日）

**分四层，按成本效益排序：**

**层 1：审计记录结构化（0.2 人日，必做）** —— 见 DL-07，`audit_resume_access` 补 4 列，让"导出了什么"可被精确回答。

**层 2：日频次上限 + 累计条数上限（0.2 人日，必做）**

```
在 1000 条/次 之上，追加两条：
  · 同一 operator_id 每日最多 EXPORT_EXCEL 10 次
  · 同一 operator_id 每日累计导出记录数最多 2000 条
  超限返回：50010 今日导出额度已用尽（2000条/10次），如确有需要请联系招聘主管
实现：查 audit_resume_access 当日聚合（该表已有 idx_operator_time 索引，
      单日行数 <100，聚合成本可忽略），不引入任何新组件。
```

> **为什么是 2000 条而不是更多**：单次校招的一个岗位投递量约 60–70 份（2000人/30岗位），2000 条 = 一次性导出约 30 个岗位的全部候选人，**已远超任何单日正常业务需要**。定得再高就失去意义。

**层 3：单元格级水印（0.1 人日，必做）**

**放弃"末行写一行"的做法**，改为三处冗余：

```
① 文件属性（EasyExcel 支持写 POI 的 DocumentSummaryInformation）：
   作者 = {HR用户名}，标题 = 遨天科技校招简历导出，备注 = {operator_id}|{时间戳}|{审计记录ID}
② 每个 Sheet 的页眉/页脚（打印时可见）：
   "遨天科技内部资料 · 导出人 {姓名} · {时间} · 仅限招聘用途，禁止外传"
③ 首行冻结行上方插入一行合并单元格，浅灰色字：同上文案
三处都删干净需要专门操作，而普通转发/截图会保留至少一处。
```

> **不做隐写/像素级水印**：Excel 是结构化数据不是图片，隐写在另存为 CSV 时即失效，成本与收益不成比例。

**层 4：审批流（0.0 人日 —— 明确不做，改为管理措施）**

**裁决：不实现导出审批流。** 理由：
- 招聘主管本身就是最高审批人，向谁审批？引入"CEO 审批"在 HR 日常场景中不现实，最终会演变为"先斩后奏"或"永久授权"，形同虚设。
- 实现成本（审批表 + 状态机 + 通知 + 待办页）约 2 人日，与本项目 P0 的其他缺口相比优先级明显更低。
- **替代措施**：把导出量放入**每日运营日报**（03 §5.5 已有机制，边际成本 0）——"昨日导出：李四 3 次共 480 条"。HR 负责人每天看得到，异常自然浮现。**这比事前审批更有效，因为它不可绕过且不增加日常摩擦。**

**层 5：导出量进日报 + 异常告警（0.1 人日，必做）** —— 见 CL-16 的规则 A/B，与本项复用同一实现。

## 2.3 DL-02【Critical】H-008 批量下载附件 —— 比 Excel 更危险却管控更少

### 为什么它比 DL-01 更严重

Excel 导出的是**结构化字段**（可选字段、可脱敏）；ZIP 下载的是**简历原件 PDF**——包含姓名、手机号、邮箱、家庭住址、照片、身份证号（若学生自填）、以及一切学生写进简历的内容。**一份原件的信息量大于 Excel 一整行，且完全不可控。**

而现状是：N-15 只补了"单次 100 份上限"，**其他管控为零**——无水印（PDF 原件无法加水印而不破坏原件）、无字段裁剪（原件是整体）、无频次限制。

### 触发场景

> HR 专员离职前一周，对其负责的 5 个岗位分 4 次下载 ZIP，共 380 份简历原件（≈1.9GB）。全部在权限范围内、全部在 100 份/次上限内、审计表留下 4 条记录。这 380 份 PDF 可直接转卖给猎头或竞争对手——**每份都是完整可用的候选人档案，无需任何加工**。

### 管控方案（0.3 人日）

| 措施 | 方案 | 成本 |
|---|---|---|
| 维持 100 份/次 | N-15 已定 | 0 |
| **日累计上限 200 份** | 同 DL-01 层 2 的实现，查审计表当日聚合 | 0.1 |
| **ZIP 内附 README** | ZIP 根目录写入 `重要提示.txt`：导出人、时间、审计记录ID、"本压缩包含 N 名候选人个人信息，依据《个人信息保护法》，您对其安全负有直接责任，禁止转发、上传网盘、留存超过 30 天" | 0.05 |
| **ZIP 加密码**（关键） | ZIP 设置密码 = **该 HR 的工号/用户名 + 当日日期**（如 `hr_lisi_20270305`），密码在下载响应头 `X-Zip-Password` 与站内信中告知本人。**作用不是防破解，而是让文件无法被随手转发即用**——转发时必须连同密码一起给，构成一次明确的、有意识的泄露行为，在事后追责时可排除"误发"抗辩 | 0.15 |
| **降级选项** | 若甲方认为密码影响效率，可改为**仅对 >20 份的批量下载加密**，小批量不加 | — |

> **为什么不给 PDF 加水印**：给 PDF 逐页盖水印需要引入 PDFBox 并重写文件，① 会破坏原件完整性（HR 可能需要原件转发给面试官）；② 对 .doc/.docx 原件无法处理；③ 增加 CPU 与转换失败面。**ZIP 层加密是成本/收益最优解。**

**是否阻塞上线**：**是**（日累计上限与 README 必做；ZIP 密码建议做，可与甲方确认后决定）。

## 2.4 DL-03【High】审计留痕的完整性 —— 三条原则不足以保证不可篡改

### 现状核查

03 §5.2.2 的三条原则**方向完全正确，予以确认**：
1. 不可删除（无删除接口、下线 RuoYi 的"清空日志"按钮）；
2. 独立事务（`REQUIRES_NEW`）；
3. 不重复记录敏感原文。

N-12 补了查询接口且明确"**本接口只读，无删除接口**"。

### 但仍有四条绕过路径（应用层管不住）

| # | 绕过路径 | 现有设计能否阻止 |
|---|---|---|
| 1 | **直接连数据库执行 `DELETE FROM audit_resume_access`** | ❌ 不能。03 §5.1.7 规定"应用账号只授 SELECT/INSERT/UPDATE/DELETE on recruit.*"——**应用账号本身就有 DELETE 权限**。而 root 账号更是无限制，且 IT 有 root 密码（备份脚本要用） |
| 2 | **`TRUNCATE` / `DROP TABLE`** | ❌ 不能 |
| 3 | **恢复一份旧备份，把审计表回退到较早状态** | ❌ 不能。`restore.ps1` 恢复的是全库 |
| 4 | **删除 `logs\audit\` 下的文本副本** | ❌ 不能（文件系统权限未做区分） |

**判定**：对一个**无专职运维、单机部署**的系统，做到"技术上绝对不可篡改"（如区块链/WORM 存储）是不现实的。但当前设计连**最低成本的两道**都没做。

### 管控方案（0.3 人日）—— 三道低成本措施

**措施 1：应用账号剥夺审计表的 DELETE/UPDATE 权限（0.1 人日）**

```sql
-- 应用账号对审计表只能 INSERT 与 SELECT，不能 UPDATE/DELETE
-- 这使得"通过应用漏洞删审计"在数据库层面即不可能
REVOKE DELETE, UPDATE ON `recruit`.`audit_resume_access` FROM 'recruit_app'@'localhost';
REVOKE DELETE, UPDATE ON `recruit`.`app_status_history`  FROM 'recruit_app'@'localhost';
-- 注意：MySQL 需先按表授权再按表回收；若原授权为库级 recruit.*，
-- 正确做法是改为"库级只授 SELECT,INSERT,UPDATE,DELETE 排除审计表"不可行，
-- 故改为：库级授 SELECT,INSERT,UPDATE,DELETE，再对两张审计表单独授权覆盖：
GRANT SELECT, INSERT ON `recruit`.`audit_resume_access` TO 'recruit_app'@'localhost';
GRANT SELECT, INSERT ON `recruit`.`app_status_history`  TO 'recruit_app'@'localhost';
-- MySQL 表级授权优先于库级，上述两条会使应用账号在这两张表上失去 UPDATE/DELETE
FLUSH PRIVILEGES;
```

> **副作用检查**：T4 数据保留清理（CL-06）需要删除业务数据，但**不删审计记录**（审计保留 3 年独立轮转），因此不受影响。**唯一需要注意**：3 年后的审计归档删除必须由**运维脚本用 root 账号**执行，不能由应用执行——这反而是正确的职责划分。

**措施 2：审计文本副本的哈希链（0.15 人日）**

```
logs\audit\audit-2026-08.log 每日追加后，由 rotate-log.ps1（已有，周日 04:00）
计算当日文件的 SHA256，追加到 logs\audit\chain.txt：
    2026-08-06 | sha256(audit-2026-08.log) | sha256(前一行)
chain.txt 每周随周备进入离线移动硬盘（离线副本不可被在线篡改）。
篡改任何一天的审计文本 → 哈希链断裂 → 季度演练时校验即可发现。
```

> 这不能**阻止**篡改，但能**发现**篡改——对合规而言，"可发现"已经改变了作案成本，因为篡改者无法确信自己不被察觉。

**措施 3：审计保留期与轮转的明确定义（0.05 人日）**

03 §5.2.1 定义审计保留 **3 年**（依据 PIPL 第 55/56 条），但 **04 的 T4 清理任务与审计表无关，没有任何任务负责审计的 3 年轮转**——即审计表**永久增长**。虽然容量估算显示 3 年仅 50MB（04 §11.2），**但"永久保留"与"保留 3 年"是两个不同的合规承诺**：隐私政策中若写"保留 3 年"而实际永久保留，是虚假告知。

**处置**：`rotate-log.ps1` 增加一步——`DELETE FROM audit_resume_access WHERE create_time < DATE_SUB(NOW(), INTERVAL 3 YEAR)`，用 **root 账号**执行（应用账号已无 DELETE 权限，措施 1）。删除前先导出为 CSV 存入离线副本，保留 7 年（会计凭证级留存，应对超长诉讼时效）。

**是否阻塞上线**：**是**（措施 1 必做，成本 0.1 人日且纯 SQL）。

## 2.6 DL-05【High】导出文件落盘且被备份带走

### 现状核查

- 04 §5 决策五定义 `export/{yyyy}/{MM}/{dd}/{timestamp}_{job_name}_简历汇总.xlsx`（N-07 裁决改为 `E:\atmoto-recruit\data\export\`）。
- 03 §4 目录结构：`data\export\` —— "Excel 导出临时文件，24 小时后由 TempCleanTask 清理"。
- **03 §5.3.1 备份策略**：`robocopy E:\atmoto-recruit\data F:\...\files /E /XO` —— **备份的是整个 `data\` 目录，包含 `export\`**。

### 问题（两个，均未被任何文档识别）

1. **导出文件进了备份，且 `/XO` 模式下永不删除**。`/XO`（只复制更新的源文件）意味着源端删除的文件在目标端**永久保留**——这正是 N-08 裁决选择 `/XO` 而非 `/MIR` 的目的（防误删）。但对 `export\` 目录，效果是：**每一份曾经导出过的 Excel 都永久留在 F: 盘和每一份离线副本里**。三年后 F: 盘上躺着几百份历史简历汇总表，且**没有任何清理机制**（T3 只清 `E:` 盘的源目录）。
2. **`data\temp\` 同理**——上传暂存目录也会被备份带走。

**这直接放大了备份介质丢失的后果**：一块离线移动硬盘丢失，泄露的不只是数据库，还有历年全部导出文件。

### 管控方案（0.2 人日）

**方案 A（推荐）：导出不落盘，流式输出。**

```
H-RESUME-007 / H-RESUME-008 改为流式响应，不写入 data\export\：
  · EasyExcel 支持直接写 HttpServletResponse.getOutputStream()
  · ZIP 用 ZipOutputStream 包裹 response 流
  · 1000 条 Excel 约 200KB、100 份 ZIP 约 500MB —— 前者完全无压力；
    后者需设置 response 不缓冲（Nginx: proxy_buffering off; proxy_request_buffering off）
收益：① 服务器上不留任何导出副本；② 备份不带走导出文件；
      ③ 省掉 T3 的清理逻辑与 data\export\ 目录本身
成本：0.15 人日（改造两个接口的输出方式）
```

**方案 B（若必须落盘，如需支持断点续传）**：备份排除该目录。

```
robocopy 增加排除参数：
    /XD "E:\atmoto-recruit\data\export" "E:\atmoto-recruit\data\temp" "E:\atmoto-recruit\data\loprofile"
（loprofile 是 LibreOffice 的临时 profile，同样不应备份——纯垃圾数据，且体积可观）
```

**裁决：采用方案 A + 方案 B 的 `/XD` 参数同时实施**（即使不落盘，`temp\` 与 `loprofile\` 也必须排除）。

**是否阻塞上线**：**是**（`/XD` 参数必须写进备份脚本，见第三部分）。

## 2.7 DL-06【High】测试环境脱敏方案的三处漏洞

```sql
  ADD COLUMN `record_count`  INT          NOT NULL DEFAULT 1

      AFTER `operation_type`,
  ADD COLUMN `filter_condition` VARCHAR(512) DEFAULT NULL
      COMMENT '导出时的筛选条件JSON（岗位/状态/时间范围），供事后界定泄露范围',
  ADD COLUMN `export_fields` VARCHAR(512) DEFAULT NULL
      COMMENT '导出的字段集（逗号分隔），用于判定是否含明文联系方式',
  ADD COLUMN `file_sha256`   CHAR(64)     DEFAULT NULL
```

## 3.2 无人值守的密码问题 —— 两种方案与裁决

**04 §10.2 的 `mysqldump ... -u%DB_USER% -p ...` 是致命错误**：`-p` 后不带值时，mysqldump 会向 stdin 索要密码。在 Windows 任务计划中（无交互式控制台），该进程**永久挂起**，任务显示"正在运行"但实际死锁，**每日备份一次都不会执行且不报错**。

| 方案 | 说明 | 裁决 |
|---|---|---|
| `-p明文密码` 写在脚本里 | 密码对同机任何用户的进程列表可见（`wmic process get commandline`），且脚本可能被误提交到 Git | ❌ **禁用** |
| **`--defaults-extra-file`（选项文件）** | 密码存独立文件，NTFS ACL 限制访问；**命令行中不出现密码** | ✅ **采用**（03 §5.3.3 已指明方向，本报告给出完整步骤） |
| `mysql_config_editor` / `--login-path` | 加密存储于 `%APPDATA%\MySQL\.mylogin.cnf`。**但绑定到运行用户的 profile**——任务计划以 `SYSTEM` 账号运行时，读取的是 `C:\Windows\System32\config\systemprofile\AppData\`，与手工配置时的用户 profile 不同，**是本方案在 Windows 任务计划下最常见的失败原因** | ⚠️ 不采用（Windows 服务账号下易踩坑） |

### `.my.cnf` 的完整配置步骤（可直接执行）

```powershell
# 步骤 1：创建选项文件（UTF-8 无 BOM，MySQL 不识别 BOM）
$cnfPath = 'E:\atmoto-recruit\app\config\.my.cnf'
$content = @"
[mysqldump]
user=backup_user
password=<在此填入备份专用账号密码>
host=127.0.0.1
port=3306
default-character-set=utf8mb4

[mysql]
user=backup_user
password=<同上>
host=127.0.0.1
port=3306
"@
[System.IO.File]::WriteAllText($cnfPath, $content, (New-Object System.Text.UTF8Encoding($false)))

# 步骤 2：NTFS ACL —— 只允许 SYSTEM 与 Administrators 读取，移除继承
icacls $cnfPath /inheritance:r
icacls $cnfPath /grant "SYSTEM:(R)"
icacls $cnfPath /grant "Administrators:(F)"
# 验证：icacls $cnfPath  应只显示这两条
```

### 备份专用数据库账号（不用 root，最小权限）

```sql
-- 备份账号：只需要读取与锁表相关的最小权限集
CREATE USER 'backup_user'@'127.0.0.1' IDENTIFIED BY '<强随机密码>';
GRANT SELECT, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER, RELOAD, REPLICATION CLIENT
    ON *.* TO 'backup_user'@'127.0.0.1';
-- 说明：
--   SELECT/LOCK TABLES/SHOW VIEW  → 导出表、视图
--   EVENT/TRIGGER                  → --events --triggers 需要
--   RELOAD                         → --single-transaction 下刷新与一致性快照
--   REPLICATION CLIENT             → 记录 binlog 位点（时间点恢复的前提）
-- 明确不授予：DROP / GRANT / FILE / SUPER —— 备份账号泄露也无法破坏数据
FLUSH PRIVILEGES;
```

> **为什么不用 root**：备份脚本是本系统中**唯一持有数据库凭据的常驻文件**，也是最可能被翻出来的凭据。用 root 意味着这份文件泄露 = 全库可删；用 `backup_user` 意味着泄露 = 全库可读（已经很糟，但至少不可破坏，且配合 DL-03 措施 1 无法删审计）。

## 3.4 `backup.ps1`（**UTF-8 with BOM**，中文输出正常）

> 保存要求：UTF-8 **with BOM**。无 BOM 会被 PowerShell 5.1 按 ANSI 读取，中文乱码并触发"表达式或语句中包含意外的标记"语法错误。
> 写入 BOM 的方法见项目全局规范：`[System.IO.File]::WriteAllText($path, $content, (New-Object System.Text.UTF8Encoding($true)))`

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
$OutputEncoding           = [System.Text.Encoding]::UTF8
$ErrorActionPreference    = 'Stop'

param([switch]$Offline)

# ===== 配置 =====
$ROOT       = 'E:\atmoto-recruit'
$MYSQL_BIN  = 'C:\mysql-8.0\bin'
$SEVENZIP   = 'C:\Program Files\7-Zip\7z.exe'
$CNF        = "$ROOT\app\config\.my.cnf"
$DB         = 'recruit'
$BK_LOCAL   = "$ROOT\backup"
$BK_REMOTE  = 'F:\atmoto-recruit-backup'
$DATA_DIR   = "$ROOT\data"
$LOG_DIR    = "$ROOT\logs\task"
$OFFLINE_DRV= 'G:\atmoto-offline'          # 移动硬盘盘符，插入后确认
# 备份包加密口令：从独立文件读取，不硬编码（NTFS ACL 同 .my.cnf）
$ZIP_PWD    = (Get-Content "$ROOT\app\config\.backup-pass" -Raw).Trim()

$today  = Get-Date -Format 'yyyyMMdd'
$logFile= "$LOG_DIR\backup-$today.log"

function Write-Log($msg, $level='INFO') {
    $line = "[{0}] [{1}] {2}" -f (Get-Date -Format 'yyyy-MM-dd HH:mm:ss'), $level, $msg
    Write-Host $line
    Add-Content -Path $logFile -Value $line -Encoding UTF8
}

function Send-Alert($subject, $body) {
    # 复用 healthcheck.ps1 的告警函数（SMTP 企业邮箱 + P0 级短信）
    & "$ROOT\scripts\lib\send-alert.ps1" -Subject $subject -Body $body -Level 'P0'
}

# ===== 离线副本模式 =====
if ($Offline) {
    Write-Log "离线副本模式：检查移动硬盘 $OFFLINE_DRV"
    if (-not (Test-Path $OFFLINE_DRV)) {
        Write-Log "移动硬盘未插入，离线副本未执行" 'ERROR'
        exit 2
    }
    $latestWeekly = Get-ChildItem "$BK_LOCAL\weekly" -Directory |
                    Sort-Object Name -Descending | Select-Object -First 1
    Copy-Item $latestWeekly.FullName "$OFFLINE_DRV\" -Recurse -Force
    # 保留滚动 8 份
    Get-ChildItem "$OFFLINE_DRV" -Directory | Sort-Object Name -Descending |
        Select-Object -Skip 8 | Remove-Item -Recurse -Force
    Write-Log "离线副本完成：$($latestWeekly.Name) → $OFFLINE_DRV"
    exit 0
}

# ===== 1. 数据库全量备份 =====
$dailyDir = "$BK_LOCAL\daily\$today"
New-Item -ItemType Directory -Force -Path $dailyDir, $LOG_DIR | Out-Null
$sqlFile = "$dailyDir\db.sql"

Write-Log "开始数据库备份：$DB"
$dumpArgs = @(
    "--defaults-extra-file=$CNF"     # ★ 密码不出现在命令行
    '--single-transaction'           # InnoDB 一致性快照，不锁表
    '--routines' '--triggers' '--events'
    '--hex-blob'
    '--set-gtid-purged=OFF'
    '--source-data=2'                # ★ 记录 binlog 位点为注释（时间点恢复的起点）
    '--default-character-set=utf8mb4'
    '--databases' $DB
)
& "$MYSQL_BIN\mysqldump.exe" @dumpArgs | Out-File -FilePath $sqlFile -Encoding utf8
if ($LASTEXITCODE -ne 0) {
    Write-Log "mysqldump 失败，退出码 $LASTEXITCODE" 'ERROR'
    Send-Alert '【P0】校招系统数据库备份失败' "mysqldump 退出码 $LASTEXITCODE，请立即检查"
    exit 3
}

# ===== 2. 完整性校验（三重，缺一不可）=====
# ① 尾部标记
$tail = Get-Content $sqlFile -Tail 5 -Encoding UTF8
if (($tail -join "`n") -notmatch 'Dump completed') {
    Write-Log "校验失败：dump 文件尾部无 'Dump completed' 标记，备份不完整" 'ERROR'
    Send-Alert '【P0】备份完整性校验失败' '备份文件不完整，可能在导出中途中断'
    exit 4
}
# ② 大小对比上一次（防止表被误删后备份出一个空库还显示成功）
$size = (Get-Item $sqlFile).Length
$prev = Get-ChildItem "$BK_LOCAL\daily" -Directory | Where-Object { $_.Name -ne $today } |
        Sort-Object Name -Descending | Select-Object -First 1
if ($prev -and (Test-Path "$($prev.FullName)\db.sql.7z")) {
    $prevSize = (Get-Item "$($prev.FullName)\db.sql.7z").Length
    # 压缩前后不可直接比，故与上一日的压缩包比压缩后大小，见第 3 步之后
}
Write-Log "dump 完成，大小 $([math]::Round($size/1MB,2)) MB"

# ===== 3. 加密压缩（★ 备份含全部简历数据，泄露等同拖库）=====
Write-Log "开始 AES-256 加密压缩"
& $SEVENZIP a -t7z "-p$ZIP_PWD" -mhe=on -mx=5 "$dailyDir\db.sql.7z" $sqlFile | Out-Null
if ($LASTEXITCODE -ne 0) { Write-Log "压缩失败" 'ERROR'; Send-Alert '【P0】备份压缩失败' ''; exit 5 }
Remove-Item $sqlFile -Force        # ★ 删除未加密的明文 dump
# -mhe=on：连文件名一起加密（否则能看到文件列表）

# 大小对比（与上一日的加密包比）
$newSize = (Get-Item "$dailyDir\db.sql.7z").Length
if ($prev -and (Test-Path "$($prev.FullName)\db.sql.7z")) {
    $prevSize = (Get-Item "$($prev.FullName)\db.sql.7z").Length
    if ($newSize -lt $prevSize * 0.8) {
        Write-Log "校验失败：本次备份 $newSize 字节 < 上次 $prevSize 的 80%" 'ERROR'
        Send-Alert '【P0】备份体积异常缩小' "本次 $newSize / 上次 $prevSize —— 可能有表被删除或导出不完整"
        # 不 exit —— 备份文件保留供人工判断，但必须告警
    }
}

# ③ SHA256
$hash = (Get-FileHash "$dailyDir\db.sql.7z" -Algorithm SHA256).Hash
"$hash  db.sql.7z" | Out-File "$dailyDir\sha256.txt" -Encoding UTF8
Write-Log "SHA256: $hash"

# ===== 4. 附件增量备份（★ 禁用 /MIR）=====
Write-Log "开始附件增量同步"
$rcArgs = @(
    "$DATA_DIR", "$BK_REMOTE\files"
    '/E'                                  # 含子目录（含空目录）
    '/XO'                                 # ★ 只复制比目标新的源文件；目标端已有的不动、已删的不删
    '/XD', "$DATA_DIR\export", "$DATA_DIR\temp", "$DATA_DIR\loprofile"   # ★ DL-05：排除临时目录
    '/R:3' '/W:10' '/NP' '/NFL' '/NDL'
    "/LOG+:$LOG_DIR\robocopy-$today.log"
)
& robocopy.exe @rcArgs
# robocopy 退出码：0-7 为成功（0=无变化, 1=有复制, 2=有额外文件, 4=有不匹配…），>=8 为错误
if ($LASTEXITCODE -ge 8) {
    Write-Log "robocopy 失败，退出码 $LASTEXITCODE" 'ERROR'
    Send-Alert '【P0】附件备份失败' "robocopy 退出码 $LASTEXITCODE"
    exit 6
}
Write-Log "附件同步完成（robocopy 退出码 $LASTEXITCODE，<8 为正常）"

# ===== 5. 同步 DB 备份到异盘 F: =====
robocopy "$BK_LOCAL\daily" "$BK_REMOTE\daily" /E /XO /R:3 /W:10 /NP /NFL /NDL | Out-Null

# ===== 6. 周备（周日）=====
if ((Get-Date).DayOfWeek -eq 'Sunday') {
    $wk = "$BK_LOCAL\weekly\$(Get-Date -UFormat '%Y-W%V')"
    New-Item -ItemType Directory -Force -Path $wk | Out-Null
    & $SEVENZIP a -t7z "-p$ZIP_PWD" -mhe=on -mx=5 "$wk\full.7z" "$dailyDir\*" "$DATA_DIR\attachments" "$DATA_DIR\brand" | Out-Null
    (Get-FileHash "$wk\full.7z" -Algorithm SHA256).Hash | Out-File "$wk\sha256.txt" -Encoding UTF8
    robocopy "$BK_LOCAL\weekly" "$BK_REMOTE\weekly" /E /XO /NP /NFL /NDL | Out-Null
    Write-Log "周备完成：$wk"
}

# ===== 7. 月备（每月1日）=====
if ((Get-Date).Day -eq 1) {
    $mo = "$BK_LOCAL\monthly\$(Get-Date -Format 'yyyyMM')"
    New-Item -ItemType Directory -Force -Path $mo | Out-Null
    Copy-Item "$dailyDir\*" $mo -Force
    robocopy "$BK_LOCAL\monthly" "$BK_REMOTE\monthly" /E /XO /NP /NFL /NDL | Out-Null
    Write-Log "月备完成：$mo"
}

# ===== 8. 轮转清理 =====
Get-ChildItem "$BK_LOCAL\daily"   -Directory | Sort-Object Name -Descending | Select-Object -Skip 30 | Remove-Item -Recurse -Force
Get-ChildItem "$BK_LOCAL\weekly"  -Directory | Sort-Object Name -Descending | Select-Object -Skip 12 | Remove-Item -Recurse -Force
Get-ChildItem "$BK_LOCAL\monthly" -Directory | Sort-Object Name -Descending | Select-Object -Skip 12 | Remove-Item -Recurse -Force

# ===== 9. 回写审计（03 §5.2.2 要求"备份与恢复执行"必须审计）=====
$auditSql = @"
INSERT INTO audit_resume_access
  (operator_id, operator_name, target_student_id, target_student_name,
   operation_type, record_count, operation_detail, ip_address, result, create_time)
VALUES (0,'SYSTEM',0,'-','BACKUP_EXEC',0,
        '每日备份完成 sha256=$hash size=$newSize','127.0.0.1','SUCCESS',NOW());
"@
$auditSql | & "$MYSQL_BIN\mysql.exe" "--defaults-extra-file=$CNF" $DB
Write-Log "备份全流程完成"
exit 0
```

### 脚本中五个关键决策的说明

| # | 决策 | 理由 |
|---|---|---|
| 1 | `--source-data=2` | 在 dump 文件中以**注释形式**记录 binlog 文件名与位点。这是**时间点恢复的起点坐标**——没有它，binlog 只能全量重放，RPO≤15 分钟无法达成。MySQL 8.0.26+ 用 `--source-data`，更早版本用 `--master-data`（部署时按实际版本确认） |
| 2 | `/XO` 而非 `/MIR` | N-08 已裁决。补充说明：`/XO` = "只复制源比目标新的文件"，效果是**目标端只增不减**。这正是备份该有的语义——T4 清理删掉的附件仍在备份中可恢复（**恢复后需重跑 T4，见 CL-06 第 4 条**） |
| 3 | `/XD` 排除三个目录 | DL-05。`export\` 与 `temp\` 是临时文件（备份它们等于永久保存历史导出的简历汇总表）；`loprofile\` 是 LibreOffice 的 UserInstallation 垃圾目录，体积可观且完全可重建 |
| 4 | `robocopy` 退出码 `>= 8` 才算失败 | **这是最常见的脚本 bug**：robocopy 成功复制文件时返回 1，`if ($LASTEXITCODE -ne 0)` 会把正常备份判为失败并疯狂告警，两周后所有人都开始忽略备份告警 |
| 5 | 先 dump 后加密再删明文 | 明文 `db.sql` 在磁盘上存在的时间窗口约几十秒。**若追求零窗口**，可改为 `mysqldump \| 7z a -si`（管道直入压缩），但 PowerShell 管道传二进制流有编码陷阱，**在本项目规模下（dump < 200MB）不值得冒这个险** |

## 3.5 OP-03【Critical，本报告新增】备份文件必须加密 —— 备份泄露等同拖库

**这是 03 §5.3 与 04 §10 都完全没有考虑的一条。**

**现状**：03 §5.3.1 的备份产物是 `db.sql.gz`（gzip 仅压缩不加密）+ `F:\` 盘上的附件明文镜像 + **每周拔下带走的离线移动硬盘**。

**触发场景**：

> IT 按流程每周插入移动硬盘执行 `backup.bat -Offline`，拔下带回家/放抽屉。某次硬盘遗失（或员工离职未归还）。硬盘内含：
> ① 8 份周备，每份是完整数据库 gzip —— **解压即得全部学生的姓名、手机号、邮箱、教育经历、快照 JSON**；
> ② 附件全量镜像 —— **几千份简历 PDF 原件**。
> 拾得者无需任何技术能力，双击即可查看。
> **法律定性**：这构成个保法第 57 条的"个人信息泄露"，必须向网信部门报告并通知全部受影响个人（数千人）。而**离线副本恰恰是 03 为防勒索软件而专门设计的措施**——一个安全措施制造了另一个更大的风险敞口。

**判定**：在**未加密**的前提下，"每周把全公司三年的简历库装进一块移动硬盘带出办公室"这个动作，其泄露风险显著高于它所防御的勒索软件风险。

**方案（0.3 人日，已内置于 §3.4 脚本）**：

| 措施 | 实现 | 说明 |
|---|---|---|
| DB 备份 AES-256 | `7z a -t7z -p<pwd> -mhe=on` | 7-Zip 的 AES-256 是经过广泛验证的实现；`-mhe=on` 连**文件名**一起加密，否则能看到"recruit_db.sql"这样的目录列表 |
| 口令管理 | 存 `E:\atmoto-recruit\app\config\.backup-pass`，NTFS ACL 同 `.my.cnf`；**同时用密封信封线下保存一份于公司保险柜** | ★ **口令丢失 = 备份全部作废**。这是加密引入的新风险，必须用线下副本对冲。**写入运维手册第一页** |
| 离线副本 | 只复制**已加密的周备包**（脚本已如此实现） | 硬盘丢失时，拾得者面对的是 AES-256 加密档 |
| 附件镜像（`F:\` 在线盘） | **不加密** | 理由：`F:\` 是在线盘，加密会使 robocopy 增量同步失效（每次都要全量解密再比对）。`F:\` 的保护靠 BitLocker 全盘加密（见 RK-03） |
| 恢复演练 | **每季度演练必须实测解密流程** | 否则"口令能不能用"要等到真出事时才知道 |

**是否阻塞上线**：**是**。离线副本机制在上线首周即启用，未加密则首周即产生风险敞口。

## 3.6 OP-04【High】勒索软件场景的真实抗性评估

### 逐层推演（不是"有备份就安全"）

| 保护层 | 勒索软件能否穿透 | 分析 |
|---|---|---|
| `E:\` 生产数据 | ✅ **必然加密** | 主目标 |
| `F:\` 在线备份盘 | ✅ **必然加密** | 03 §5.3.1 自己已指出"在线的 F: 盘会和 E: 一起被加密"。**只要盘符可见、有写权限，勒索软件就会加密它**——它不区分"这是备份" |
| MySQL binlog（`E:\mysql-data\binlog\`） | ✅ **必然加密** | 与数据同盘 |
| 本机 `backup\daily\` | ✅ **必然加密** | 同 E: 盘 |
| **离线移动硬盘** | ❌ **不能**（拔下状态） | ✅ **唯一有效防线** |
| Windows 卷影副本（VSS） | ✅ 通常被删除 | 主流勒索软件的标准动作是 `vssadmin delete shadows /all`。**不能依赖** |

**结论：单机 + 本地双盘（E:/F:）对勒索软件的抗性为零。**唯一有效的是离线副本，而离线副本是**每周人工插拔一次**——意味着**最坏情况下丢失 7 天数据**（RPO 从 15 分钟劣化为 7 天）。

### 03 现有设计的评价

03 §8 R1 已识别勒索风险并给出离线副本方案，**方向正确**。缺口在于：
1. **未量化勒索场景下的真实 RPO**——文档中 RPO≤15 分钟的承诺**只在硬件故障场景成立**，勒索场景下是 7 天。这个差异必须向甲方明示。
2. **依赖人工每周插拔**，无专职运维（本项目的核心约束），**漏做几乎是必然的**。

### 低成本增强方案（三选一或组合，0.2–0.5 人日）

| 方案 | 成本 | 抗勒索 | 评价 |
|---|---|---|---|
| **A. 提高离线频率到每周二次 + 日报提醒** | 0.05 人日 | RPO 3–4 天 | `daily-report.ps1` 增加一行："距上次离线备份已 N 天"，N>7 时标红。**零成本、必做** |
| **B. 云对象存储异地副本（推荐）** | 0.4 人日 + 约 10 元/月 | **RPO 24 小时** | 阿里云 OSS 低频访问型，每日上传加密后的 `db.sql.7z`（约 30MB/天，一年约 11GB，**年费不足 150 元**）。关键：使用**只写不删的 RAM 子账号**（`oss:PutObject` 允许，`oss:DeleteObject` 拒绝）+ **开启版本控制与 Bucket 保留策略**，勒索软件即使拿到 AK 也无法删除历史版本。<br>**注意**：上传的是**已 AES-256 加密**的包，云端只有密文，不构成"向第三方提供个人信息"（阿里云为受托存储方，且无法解密），**无需单独同意**，但须在隐私政策中披露委托关系 |
| C. NAS / 第二台机器 | 1.0 人日 + 硬件 | 视配置 | 若 NAS 以 SMB 挂载且有写权限，**同样会被加密**；需配置 NAS 端快照与只读共享才有效。**成本与复杂度超出本项目"无专职运维"约束，不推荐** |

**裁决：A + B 组合。** 
- A 是零成本的管理增强，必做。
- B 用不到 150 元/年和 0.4 人日，把勒索场景的 RPO 从 **7 天**压到 **24 小时**，是本项目性价比最高的一项运维投入。**且它同时解决了"办公室火灾/被盗/断电损毁"这类离线硬盘也在同一栋楼的场景**——离线副本防勒索，异地副本防物理灾难，两者不可互相替代。

> **对"单台台式机部署"硬约束的说明**：OSS 是对象存储，不是计算节点，不运行任何业务逻辑。这与 C-09 方案 C 中"云主机仅做 L4 转发不违反单机约束"是同一逻辑，**予以确认不违反**。

### 勒索发生时的处置顺序（写入应急预案）

```
1. 立即物理断网（拔网线，不是关防火墙）——阻止横向扩散与数据外传
2. 不关机、不重启——内存中可能有解密密钥，且重启可能触发二次加密
3. 拍照记录勒索页面（勒索家族识别，部分家族有公开解密工具）
4. 拔下并隔离离线硬盘，确认其未被连接过被感染的机器
5. 全新安装操作系统（不在被感染系统上恢复）
6. 从离线副本 + OSS 副本中取较新者恢复
7. 恢复后立即重跑 T4 数据保留清理（CL-06 第 4 条）——
   备份中含已被删除的个人信息，不清理即为重新开始违规处理
8. 按 CL-16 判定是否构成个人信息泄露事件（勒索软件通常伴随数据外传，
   应按"可能发生泄露"处理，即需要报告与通知）
```

## 3.7 恢复演练与 RTO/RPO 的真实承诺

### 分场景的 RTO/RPO（03 只给了一组数字，实际因场景而异）

| 场景 | RPO（丢多少数据） | RTO（多久恢复） | 依赖 |
|---|---|---|---|
| 应用崩溃 / JVM OOM | **0** | **< 5 分钟** | WinSW 自动重启（03 §5.5） |
| MySQL 服务异常 | 0 | < 15 分钟 | healthcheck.ps1 探测 + 重启 |
| **误删数据**（如误删一个岗位的全部投递） | ≤ 15 分钟 | 1–2 小时 | 日备 + binlog 时间点恢复 |
| **单块硬盘（E:）物理损坏** | ≤ 15 分钟 | **2–4 小时** | F: 盘备份 + binlog。**注意：若 E: 盘损坏，binlog 也在 E: 上一并损坏 → RPO 实际劣化为 24 小时**（见下方修正项） |
| **整机损坏 / 被盗 / 火灾** | 24 小时（OSS）或 7 天（仅离线盘） | **1–3 天**（需采购或征用新机、重装全部软件栈） | 见下 |
| **勒索软件** | 24 小时（OSS）或 7 天 | 1–3 天 | 同上 |

### 两处必须修正的承诺

**修正 1：binlog 与数据同盘，E: 盘损坏时 RPO 不是 15 分钟**

03 §4 目录规划中 MySQL datadir 为 `E:\mysql-data\`，binlog 也在其中。**E: 盘物理损坏 = 数据与 binlog 同时丢失 = 只能用 F: 盘上昨日 02:00 的全量备份 = RPO 24 小时**，而非承诺的 15 分钟。

**修正方案（0.1 人日）**：binlog 每小时同步到 F: 盘。

```powershell
# 并入 healthcheck.ps1（每 5 分钟运行）或独立任务（每小时）
robocopy "E:\mysql-data\binlog" "F:\atmoto-recruit-backup\binlog" /E /XO /R:1 /W:5 /NP /NFL /NDL
# 增量同步，每次仅复制新产生的 binlog 段（通常几 MB），耗时 < 2 秒
```

同步后，E: 盘损坏场景的 RPO 恢复为 **≤ 1 小时**（而非 15 分钟——因为同步是每小时一次）。若要真正达成 15 分钟，把同步频率提到每 15 分钟即可（成本相同）。**建议每 15 分钟，与承诺值对齐。**

**修正 2：整机损坏的 RTO 不可能是 2 小时**

03 §5.3.2 承诺 RTO ≤ 2 小时，但这只在"有一台可用的、已装好软件栈的机器"前提下成立。整机损坏时需要：采购/征用机器（半天–数天）→ 安装 Windows/JDK/MySQL/Nginx/LibreOffice/7-Zip（2–4 小时）→ 恢复数据（1 小时）。

**处置（文档类，0 人日）**：把 RTO 承诺拆为两个数字写入交付说明：

> **RTO 承诺**：
> - **软件级故障**（应用/数据库异常、误删数据、单盘损坏）：**≤ 2 小时**
> - **硬件级灾难**（整机损坏、被盗、火灾、勒索软件）：**1–3 个工作日**，取决于替代硬件的可得性
>
> 03 §8 R1⑦ 已提出"校招高峰期准备一台冷备笔记本"作为应急预案。**本报告建议将其从"写入运维手册的建议"升级为"校招季（每年 9–11 月、3–4 月）的强制准备项"**——在这两个窗口期，一台预装好软件栈的笔记本可把硬件级灾难的 RTO 从 1–3 天压回 4 小时。成本为零（用一台闲置办公笔记本，每季度演练时顺便更新一次软件栈）。

### 恢复演练的强制清单（03 §5.3.2 已要求每季度一次，本报告补充具体动作）

```
□ 1. 在测试实例（8090 端口 / recruit_test 库）执行 restore.ps1
□ 2. ★ 实测 7-Zip 解密——用保险柜中的密封口令副本，不用配置文件里的
      （目的：验证线下口令副本是有效的，而不是验证脚本能跑）
□ 3. 验证 binlog 时间点恢复：恢复到"昨天 14:30"这个具体时刻，
      确认该时刻之后的数据不存在、之前的存在
□ 4. 跑冒烟用例：学生登录 → 投递 → HR 查看 → 预览附件 → 导出 Excel
□ 5. 校验附件文件数与 stu_resume_file 行数一致（防止只恢复了数据库）
□ 6. ★ 恢复后执行一次 T4 dry-run，确认输出的待清理记录数符合预期
      （CL-06 第 4 条：恢复会把已删除的个人信息带回来）
□ 7. 记录实测 RTO 到 doc\恢复演练记录.md
□ 8. ★ 同时执行本报告第五部分"运行期合规检查清单"10 项（CL-17，合规审计与演练合并）
□ 9. 演练结束后销毁测试库中的恢复数据（TRUNCATE 或 DROP DATABASE）
```

# 第四部分　等保合规判断与单机固有风险

## 4.1 等保结论（明确判断 + 法规依据）

### 结论

> **本系统触发《网络安全法》第 21 条的网络安全等级保护义务，应定为「第二级」并履行定级备案与测评。**
> **但本报告裁决：将其列为「上线后 3 个月内完成」的合规义务，不阻塞一期上线**（理由与降级路径见下）。
> 该事项必须由**甲方信息安全负责人书面决策**（对应 07 §交付-3 的 Q-07），开发方不能代为决定。

### 法规依据链（逐条）

| # | 依据 | 要点 | 对本项目的适用 |
|---|---|---|---|
| 1 | 《网络安全法》**第 21 条** | 国家实行网络安全等级保护制度，**网络运营者应当按照要求履行安全保护义务** | 遨天科技运营本系统即为"网络运营者"，义务**无条件适用** |
| 2 | 《网络安全法》**第 76 条**(三) | "网络运营者"指网络的所有者、管理者和网络服务提供者 | 甲方自建自营，属之 |
| 3 | **GB/T 22240-2020**《网络安全等级保护定级指南》 | 定级要素＝受侵害客体 + 侵害程度。**涉及公民个人信息且通过互联网提供服务**的系统，一般不低于**第二级** | 本系统公网提供服务（方案 B）+ 处理数千人个人信息 → **二级** |
| 4 | 公安部《信息安全等级保护管理办法》第 15 条 | 二级以上系统应在确定等级后 **30 日内**向公安机关备案 | 备案义务 |
| 5 | 《网络安全法》第 21 条(三) | **网络日志留存不少于六个月** | 03 §5.2.1 已设计 Nginx access.log 保留 **180 天** ✅ **该项已合规** |
| 6 | 《个人信息保护法》第 51 条 | 采取加密、去标识化等安全技术措施 | 与等保二级要求高度重叠，见 §4.2 |

### 为什么是二级而不是三级

| 定级要素 | 本系统情形 | 判定 |
|---|---|---|
| 受侵害客体 | **公民、法人的合法权益**（学生个人信息） | 未触及"社会秩序和公共利益"，更未触及"国家安全" |
| 侵害程度 | 造成**一般损害**（个人信息泄露，可通过维权与通知补救） | 未达"严重损害社会秩序" |
| 用户规模 | 数千人（三年约 6000） | 远低于三级常见的百万级门槛 |
| 业务重要性 | 内部招聘辅助系统，**非生产经营核心**，中断不影响主营业务 | — |
| **结论** | | **第二级** |

> **关于"商业航天 + 国家级专精特新小巨人"是否拉高定级**：**不拉高。** 等保定级看的是**该信息系统本身**承载的业务与数据，不是企业的行业属性。本系统是招聘管理系统，**不承载任何航天技术数据、设计图纸、涉密信息**（需求文档全文无此类内容，已核查）。
>
> **但有一个必须在 Gate-0 确认的边界**：若甲方内部另有涉军、涉密资质要求，其保密管理制度可能对"公司内网接入公网的任何系统"有**独立于等保的内部审批要求**。这属于甲方内部管理事项，开发方无从判断。**本报告将其列为新增的 Gate-0 第四项前置条件**——否则可能出现"技术上做完了，内部审批过不去"的局面。

### 二级等保的增量成本（相对现有设计）

现有设计已覆盖相当多的二级要求（03 的安全设计质量较高）。逐项差距分析：

| 等保二级要求项 | 现有设计 | 差距 | 增量成本 |
|---|---|---|---|
| **安全物理环境** | ❌ 台式机置于办公室 | **最大差距**：机房环境、门禁、防盗、温湿度、消防、UPS、防静电。**办公室台式机在测评中此项必然失分** | 见下方"关键矛盾" |
| 安全通信网络 | ✅ HTTPS/TLS 全程 | 无 | 0 |

### 路径裁决与理由

**裁决：采用路径 2（先备案，暂缓测评），并将完整测评列为 P1 事项。**

理由（四条）：

1. **备案与测评是两件事，法律后果不同**。《网络安全法》第 59 条对"未履行安全保护义务"的处罚是**责令改正、警告**，拒不改正才罚款（1–10 万元，直接责任人 0.5–1 万元）。**实践中监管的典型路径是"先责令整改"**——已备案且能出示安全措施清单的单位，整改期通常充裕；未备案的则直接构成违法状态。**备案的边际成本极低（2–4 周、近乎零费用），却把法律状态从"违法"变为"合规进行中"**，这是本项目性价比最高的合规动作。
2. **物理环境项在当前部署形态下无法通过测评**（见下方"关键矛盾"），现在做测评必然不合格。先备案、待物理环境改善后再测评是务实路径。
3. **二级系统的测评不是年度强制**。三级要求每年一次，二级在多数地方实践中为"每两年一次"或"按需"。时间窗口允许。
4. **甲方是国家级专精特新企业**，大概率已有其他系统的等保经验与合作测评机构，本系统可**并入既有等保体系一并处理**，边际成本远低于单独走一遍。**这一点必须在 Gate-0 向甲方 IT 确认——如果他们已有二级备案的"办公网"，本系统可能可以作为其中一个子系统备案。**

### 关键矛盾：物理环境与"单台办公室台式机"的硬约束不可调和

> **必须向甲方明示的一句话**：
>
> 等保二级的"安全物理环境"控制项要求信息系统主机置于**具备门禁、防盗、防火、防水防潮、温湿度控制、电力供应保障的专用机房**。**一台放在办公室的台式机，此项在测评中无法通过，且无法通过软件手段弥补。**
>
> 若甲方要求完整通过二级测评，**必须二选一**：
> - **选项 A**：将主机迁入公司机房或机柜（若有），成本取决于现有设施；
> - **选项 B**：改为云主机部署（阿里云/腾讯云等已通过等保三级的 IaaS，可复用其物理环境与部分基础设施合规结论，显著降低测评难度）——**但这将推翻"单台台式机"的项目硬约束，属于重大方案变更，需重新评估成本与数据出域（出内网）的合规影响**。
>
> **本报告不推荐选项 B**：设计简报第四节确立的"数据不出内网"取向（C-09 裁决亦据此排除境外主机）是本项目在个人信息保护上的核心优势，为通过测评而放弃它并不划算。**推荐选项 A + 路径 2**：先备案，同时把台式机迁入带锁机柜（见 RK-03），逐步改善物理条件后再择机测评。

### RK-01【High】单点故障：RTO 与校招高峰期的业务影响

**分场景 RTO（已在第三部分 §3.7 给出，此处只做业务影响映射）**：

| 故障 | RTO | 校招高峰期（宣讲会当周 / 投递截止前 48 小时）的业务影响 |
|---|---|---|
| 应用崩溃 | < 5 分钟 | 可忽略（WinSW 自愈） |
| MySQL 异常 | < 15 分钟 | 学生看到"系统繁忙"，少量投递失败重试即可 |
| 硬盘损坏 | 2–4 小时 | **中等**：若发生在截止日当天，可能有数百名学生投递失败。**处置：截止日期自动顺延**（见下） |

```
本项为纯流程补充，写入运维手册，成本 0.2 人日（文档）。
```

**修正 2：冷备笔记本从"建议"升级为"校招季强制"**（已在 §3.7 说明，此处不重复）。

### RK-02【Critical】物理安全：物理接触即可拖库

**这是全部设计文档中完全未涉及的一个维度。**

**现状**：一台 Windows 台式机放在办公室。全部设计的安全措施——四层网络边界收敛、双 SecurityFilterChain、JWT 双密钥、RBAC、审计——**全部建立在"攻击者只能通过网络访问"这一前提上**。

**触发场景（三个，均不需要任何技术能力）**：

> **场景 1（最简单）**：晚上 20:00，办公室仅剩数人。某人走到该台式机前，插入 U 盘，把 `E:\atmoto-recruit\data\attachments\` 整个目录复制走。耗时 5 分钟（30GB × USB3.0）。**系统日志中没有任何记录**——文件复制不经过应用层，`audit_resume_access` 一片空白，Nginx 日志也没有。**这次泄露在技术上完全不可见。**
>
> **场景 2**：整机（或仅拆走硬盘）被搬走。硬盘接到任何一台电脑上，NTFS 分区直接可读——**Windows 的文件权限（ACL）在换机后完全失效**，因为 ACL 依赖的是本机 SID。数据库文件 `E:\mysql-data\` 同样直接可拷，用同版本 MySQL 挂载即可读取全部数据（InnoDB 表空间文件默认不加密）。
>
> **场景 3**：从 U 盘启动 WinPE，绕过 Windows 登录密码，读取 `E:\atmoto-recruit\app\config\application-prod.yml` —— 其中含**数据库密码、JWT 双密钥、阿里云 AK/SK**。拿到 JWT 密钥后可**离线伪造任意学生或 HR 的 token**，此后即使物理归还，攻击者仍可长期通过网络越权访问，且伪造的 token 验签合法、审计日志显示为"正常登录"。

**判定**：在物理访问未受控的前提下，全部网络层安全设计的实际保护强度**上限就是物理防护的强度**。而当前物理防护为**零**。

**最低限度防护方案（0.4 人日 + 少量硬件费用）**：

| # | 措施 | 防御场景 | 成本 | 优先级 |
|---|---|---|---|---|
| 1 | **BitLocker 全盘加密**（E: 数据盘 + F: 备份盘 + C: 系统盘） | 场景 2、3 | 0.2 人日 + 0 元 | **必做** |
| 2 | **BIOS 密码 + 禁用 U 盘启动 + 启动顺序锁定** | 场景 3 | 0.05 人日 | **必做** |
| 3 | **Windows 登录密码 + 15 分钟自动锁屏（组策略强制）** | 场景 1 | 0.05 人日 | **必做** |
| 4 | **禁用 USB 存储设备**（组策略 `USBSTOR` 启动类型改 4，或用 Defender 设备控制） | 场景 1 | 0.1 人日 | **必做** |
| 5 | **机箱锁 / 硬盘锁 / 钢缆锁** | 场景 2 | 约 50–200 元 | 建议 |
| 6 | **迁入带锁机柜或独立房间** | 场景 1、2 | 取决于现有条件 | **强烈建议**（同时是等保物理环境项的最低改善） |
| 7 | 办公室摄像头覆盖该位置 | 事后追溯 | 通常已有 | 建议 |

**BitLocker 的三个实施要点（必须写入部署手册，否则会踩坑）**：

```
① 恢复密钥的保管：
   BitLocker 恢复密钥（48 位数字）必须打印后存入公司保险柜，
   并在甲方 IT 与个人信息保护负责人处各留一份密封件。
   ★ 与备份加密口令（OP-03）存放于不同位置——避免一次失窃全丢。
   ★ 绝不存在被加密的这台机器上（这是最常见的错误）。

② TPM 与无人值守重启的冲突（关键）：
   若台式机有 TPM 2.0：使用「仅 TPM」模式，重启无需人工输入，
       服务可自动启动 —— 这与"无专职运维、断电后 5 分钟内自愈"（03 §8 R1④）兼容。
   若无 TPM：只能用「启动密码/USB 密钥」模式，则每次重启都需要人到场输入，
       与"开机自启自愈"直接冲突。
   ★ 部署前必须先确认硬件是否有 TPM 2.0。无 TPM 时的处置：
       仅对 E: 与 F: 数据盘启用 BitLocker（数据盘可配置为"自动解锁"，
       依赖已解锁的系统盘），系统盘不加密，用 BIOS 密码 + 禁用 U 盘启动兜底。
       此配置下场景 2（拆硬盘）仍被防御，场景 3（WinPE 读配置文件）防御减弱。

③ 性能影响：
   BitLocker 使用 AES-XTS 硬件加速，对本项目负载（20 并发、数据库 <200MB）
   的性能影响 <3%，可忽略。不构成拒绝理由。
```

**关于"禁用 USB 存储"的副作用检查**：离线备份（§3.4 的 `-Offline` 模式）需要插移动硬盘。**处置**：组策略配置为"禁用 USB 存储的写入与读取"但**通过白名单放行特定硬盘的硬件 ID**（`Device Installation Restrictions` 策略），或采用更简单的做法——**仅禁用写入（`WriteProtect=1`）**，这样阻止了"拷贝数据出去"（场景 1 的核心动作），而备份是"写入到移动硬盘"…… 注意方向：备份是**从本机写到 U 盘**，与拷贝数据出去是同一动作。

> **裁决**：USB 存储采用**硬件 ID 白名单**方式，只放行指定的那块离线备份硬盘。若甲方 IT 不熟悉组策略配置，**降级方案**：不禁用 USB，改为在 `healthcheck.ps1` 中监控 USB 存储设备的插入事件（读取系统事件日志 `Microsoft-Windows-DriverFrameworks-UserMode/Operational`），发现非白名单设备插入即邮件告警。成本 0.15 人日，防御强度较低但零配置风险。

**是否阻塞上线**：**是**（措施 1–4 必须在上线前完成，合计 0.4 人日，且几乎不需要额外费用）。

### RK-03【High】无专职运维的现实风险：谁看日志、谁打补丁、谁验证备份

**这是本项目最容易被忽视、却最可能在半年后真正出事的一条。**

**问题的实质**：03 的设计中包含大量"定期人工动作"——每季度恢复演练、每月巡检 Nginx 日志的 4xx/5xx 聚集、每季度跑 `mvn dependency-check`、每周插拔离线硬盘、每日看运营日报、证书到期处理、Windows 补丁。**这些动作全部依赖"有一个人会去做"，而项目明确定义为"甲方无专职运维"。**

**现实推演**：

> 交付后第 1 个月：IT 小 A 每天看日报，一切正常。
> 第 3 个月：日报每天都是"一切正常"，小 A 开始只在标题栏扫一眼。
> 第 5 个月：小 A 被调去做别的项目，没有交接。日报进入邮件归档规则，无人查看。
> 第 7 个月：离线备份连续 8 周未做（没人记得）。证书还有 15 天到期，告警邮件发到了小 A 的邮箱。
> 第 8 个月：**证书过期，公网门户全站 HTTPS 报错，学生无法访问**。此时正值春招。
> 第 8 个月 + 3 天：有人报修，发现问题。同时发现备份已两个月未验证，最近一次成功的离线副本是 5 个月前。

**这个推演不是悲观假设，而是无专职运维环境下的默认结局。**

**最小可行的运维责任设计（0.5 人日，本报告新增）**：

**原则：把"需要人主动去做的事"压缩到最少，剩下的全部变成"不做就会被打扰"的推送式提醒。**

| # | 措施 | 说明 |
|---|---|---|
| 1 | **指定两名责任人，写入交付文档并要求签字** | **主责：甲方 IT 一人**（技术动作）；**副责：人文发展部一人**（合规动作，兼个人信息保护负责人 CL-14）。**两人制的目的是避免单点离职导致责任真空**。责任清单必须具体到"每周几做什么"，不能写"负责系统运维" |
| 2 | **把"定期动作"全部转为日报中的待办项** | `daily-report.ps1`（03 §5.5 已有）扩展一个"**需要您处理**"区块，只在有事项时出现：<br>· 距上次离线备份 > 7 天<br>· 距上次恢复演练 > 90 天<br>· HTTPS 证书剩余 < 20 天<br>· Windows 更新待重启 > 14 天<br>· 昨日导出量异常（DL-01）<br>· 权利申请工单超期未回（CL-15）<br>**无事项时该区块不出现**——这是关键，避免"每天都有一堆提醒"导致的告警疲劳 |
| 3 | **升级机制：超期未处理则升级收件人** | 同一待办项连续出现 3 天未消除 → 日报抄送 HR 负责人；连续 7 天 → 抄送总经理。**这是唯一能对抗"日报没人看"的低成本手段**——它把技术问题转化为管理可见的问题 |
| 4 | **Windows 补丁策略** | 不做人工打补丁。配置为"**自动下载并安装，但仅在每月第二个周日 04:00 重启**"（组策略活动时间 + 计划重启）。理由：无人值守环境下，"自动更新但不自动重启"会导致补丁堆积不生效；固定窗口重启的风险可控（凌晨 + 服务开机自启 + WinSW 自愈） |
| 5 | **依赖漏洞扫描降频** | 03 要求"每季度跑 `mvn dependency-check`"。**无专职运维下这不会发生**。改为：**在每季度恢复演练的清单里加一项**（演练是有人到场的固定动作，附加成本近零），且由**开发方在质保期内负责**（写入合同） |
