## 一、核心技术栈（已锁定）

| 层次 | 选型 | 版本 | 裁决理由（一句话） |
|---|---|---|---|
| 后端框架 | Spring Boot | 3.4.x（Java 17 LTS） | 国内人才最易得、后台生态最全、单体部署最简单 |
| 后台基座 | **RuoYi-Vue** | 最新稳定版 | **MIT 协议，完全免费商用**；RBAC/部门/字典/操作日志开箱即用，覆盖系统管理端约 60% 工作量 |
| 前端 | Vue 3 + Vite | Vue 3.4+ | HR 端表格密集操作必须 SPA；公司官网即 Vite 技术栈，团队无接手障碍 |
| UI 组件库 | Element Plus | 最新稳定版 | 中文文档最完善、国内用户群最大、后台组件最全 |
| 数据库 | MySQL | 8.0.x | ngram 全文索引直接满足关键词搜索；备份一条 mysqldump |
| 文件存储 | **本地文件系统** | — | GB 级数据 + 20 并发，MinIO/OSS 均为过度设计 |
| 部署 | **Windows 裸机 + .bat 运维脚本** | — | 不引入 Docker Desktop，避免 WSL2 依赖与 1–2GB 额外内存 |

## 二、中间件裁决（全部「不引入」）

| 组件 | 裁决 | 不引入的后果论证 |
|---|---|---|
| Redis | ❌ 不要 | Caffeine 本地缓存 + MySQL 足够；20 并发无缓存压力。**唯一例外**：短信验证码有效期存储，用 Caffeine 带 TTL 的本地缓存即可，单机无一致性问题 |
| 消息队列 | ❌ 不要 | 无跨服务异步解耦需求；通知类操作用 Spring `@Async` 线程池 |
| Elasticsearch | ❌ 不要 | 岗位数量数十个，MySQL FULLTEXT + ngram 分词完全覆盖 S-011 关键词搜索 |
| Quartz / XXL-Job | ❌ 不要 | 仅 2 个定时任务（岗位到期下架、简历数据清理），Spring `@Scheduled` 足够 |
| Nginx | ⚠️ 按需 | 若学生端需公网访问，用 Nginx 做反向代理 + 静态资源 + HTTPS 终结；纯内网可省略。**架构师需给出内外网两种部署拓扑** |

## 三、关键难点方案（已锁定）

### 3.1 简历附件在线预览（S-007 / H-005，P0 难点）
**方案**：PDF 用 **pdf.js** 纯前端渲染；Word（doc/docx）由后端 **LibreOffice Headless** 转 PDF 后同样交给 pdf.js 渲染。
- 转换时机：**上传时异步转换并缓存 PDF**，不在预览请求时同步转换（避免 HR 点开等待数秒）
- 兜底：转换失败或未完成时，前端用 **mammoth.js** 做 docx 快速降级预览；.doc 老格式转换失败则提示下载原件
- LibreOffice 为唯一需额外安装的系统级软件（约 600MB），免费、还原度最高
- 演进路径：后期如需支持更多格式，可无缝升级到 kkFileView

### 3.2 短信验证码（S-001 / S-002）
**服务商**：阿里云短信，约 0.045 元/条，年费用预计不超过 100 元。
⚠️ **项目管理风险**：企业实名认证 + 短信签名运营商报备需预留 **15 个工作日**，必须在项目启动时即刻并行推进，否则阻塞学生端注册功能联调。

## 四、明确排除项（不得选用）

| 被排除 | 排除原因 |
|---|---|
| JeecgBoot | Apache 2.0 **附加竞业限制条款**（禁止开发"可能被认为与本软件竞争的软件"），存在法律风险；且组件严重过重 |
| OpenCATS | PHP 栈 + 英文 UI + 界面老旧，汉化适配成本接近自研 |
| Odoo Recruitment | 需完整 Odoo 实例，对单机 20 并发严重过度设计 |
| Gitee 上各类"招聘系统" | 均为毕设/课设级别，不可用于生产 |
| 第三方云预览服务 | 简历含个人信息，外传存在合规风险；且内网部署场景不适用 |
| SQLite | 库级写锁，多 HR 并发写入场景不适用 |
| PostgreSQL | Windows 平台运维门槛高于 MySQL（本项目无专职运维） |
| Docker Desktop | Windows 上依赖 WSL2，额外 1–2GB 内存，增加故障面 |

## 五、性能基线（架构师据此论证，不必再测算）

在 i5 / 16GB / SSD 台式机上，推荐栈理论并发上限 200+，**20 并发下余量约 50 倍**。结论：**无需任何性能优化设计**（不做缓存预热、不做读写分离、不做连接池调优之外的任何优化）。任何以"性能"为由增加复杂度的设计一律驳回。

## 六、需求文档之外、经调研建议纳入的功能

| 建议项 | 建议优先级 | 理由 | 一期最低要求 |
|---|---|---|---|
| **渠道来源追踪** | P1 | 投递链接带 `?source=宣讲会/官网/内推`，HR 后期必然要问"哪个渠道学生质量最高" | **一期表结构必须预留字段**，成本极低 |
| **HR 键盘快捷键** | P1 效果 / P0 成本 | 简历列表 J/K 上下切换、P 通过、R 淘汰、E 导出；纯前端零后端改动，HR 效率提升显著 | 交互设计中给出键位定义 |
| **简历数据保留与自动清理** | P1（合规刚需） | 《个人信息保护法》要求保存期为"实现目的所需最短时间"；行业惯例：未录用保留 1–2 年，已淘汰 6 个月–1 年 | **一期数据字典必须含** `data_retention_days`、`auto_cleanup_date` 字段 |
