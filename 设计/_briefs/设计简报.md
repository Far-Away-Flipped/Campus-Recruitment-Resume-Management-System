1. 这是一家**硬科技制造企业**，不是互联网公司。校招规模是"每年一届、几十到几百份简历"量级，**不是**日均万级投递的招聘平台。系统必须朴素、可靠、易维护，而非高并发架构。

## 二、需求基线（来源：《校园招聘简历管理系统_开发需求文档 V1.0》2026-08-05）

### 2.1 三端范围
- **学生端（前台门户）**：注册登录、个人信息、岗位浏览、简历投递、消息通知
- **HR 端（管理后台）**：岗位管理、简历管理、面试管理
- **系统管理端**：基础配置、组织架构、权限管理

明确**不含**：社会招聘、内部推荐。

### 2.3 候选人状态流转（附录 4.1）
```
投递 → 待筛选 → 筛选通过 → 待面试 → 面试中 → 面试通过 → 待录用
     → 已发 Offer → 已接受/已拒绝 → 已入职
```
各阶段均可标记"淘汰"。
**一期只需实现**：`待筛选 → 筛选通过 / 已淘汰`（对应 H-006），其余状态值在数据字典中预置但不做流程约束。

## 三、硬性技术约束（**不可协商**）

| 约束 | 具体要求 | 设计含义 |
|---|---|---|
| **部署形态** | 单台**台式机**（Windows 或 Linux），非云、非集群、非 K8s | 禁止微服务、禁止服务网格、禁止分布式中间件集群 |
| **并发规模** | 峰值约 **20 并发用户** | 单进程/单实例足矣；禁止为并发引入 Redis 集群、MQ、读写分离 |
| **数据规模** | 每届校招量级：岗位数十个、简历数百到数千份、附件 ≤10MB/份 | 单库单表即可；总数据量 GB 级 |
| **技术成熟度** | 必须选用**成熟稳定、社区活跃、文档齐全、招得到人**的技术 | 禁止小众框架、禁止未 GA 的技术、禁止实验性方案 |
| **设计简洁** | 组件数量最小化，能不加就不加 | 每引入一个组件必须写明"不引入会怎样"的论证 |
| **可维护性** | 无专职运维；部署、升级、备份需脚本化/一条命令 | 优先 Docker Compose 或单可执行包 |
| **网络环境** | 需支持内网部署；学生端可能需公网可访问 | 考虑内外网分离或反向代理方案，但不得复杂化 |
| **中文环境** | Windows 中文系统（GBK 控制台），全中文界面与文档 | 脚本编码遵循用户全局规范：.bat 纯 ASCII 或 GBK 无 BOM；.ps1 UTF-8 with BOM |

## 四、合规与安全基线（硬科技企业 + 个人简历数据）

1. **个人信息保护**：简历含姓名、手机号、身份信息、教育经历，属《个人信息保护法》下的个人信息。需设计：传输加密、存储访问控制、操作审计、数据保留策略、注册时的隐私政策告知与勾选。
2. **附件安全**：上传文件需类型白名单（PDF/DOC/DOCX）、大小限制 10MB、内容嗅探校验、存储路径不可被直接遍历访问、下载需鉴权。
3. **账号安全**：密码加盐哈希、登录失败限流、短信验证码防刷（频率+图形验证码）。
4. **越权防护**：HR 只能看本人/本部门授权范围内的简历（权限模型需支持）；学生只能看自己的投递。
5. **公司性质**：商业航天涉密敏感行业，系统内不承载任何涉密信息，但需在文档中明确"本系统仅处理公开招聘信息与候选人自愿提交的个人信息"。
