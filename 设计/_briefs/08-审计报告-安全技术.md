### 最严重的三个问题

**1. S-06　HR 间数据级越权完全没有实现路径（高危，阻塞）**

03 §5.1.3 声称用 `job_position.owner_user_id` + RuoYi `@DataScope` 实现"招聘专员仅见本人负责岗位的简历"，但三处同时断裂：

- 该字段在 04 的 DDL 中**不存在**（07 的 N-06 已指出，本报告确认其安全后果）；
- **05 全文 0 次出现 `@DataScope`、"数据范围"、"数据权限"、`owner`**（已用 grep 核实）——H-RESUME-001/002/003/007/008 这 5 个直接返回简历个人信息的接口，没有任何一个标注数据范围约束，全部只标了 `hr:resume:list` / `hr:resume:query` 这类**功能权限点**；
- 6 个报表接口同样无约束（07 的 U-6 已识别报表侧，但未识别列表/详情/导出侧）。

**后果**：当前设计等价于"任何持有 `hr:resume:*` 权限点的账号可读取全部简历"。权限管理只做到菜单/按钮级，**数据级隔离为零**。需求 A-003 要求的多 HR 协作权限模型不成立，且 03 §7.2 M5 验收标准第③条（"招聘专员看不到他人负责岗位的简历→403"）必然失败。

**2. S-11　附件预览/下载的 URL token 是完整会话凭据，可复用可传播（高危，阻塞）**

05 §4.5/§4.6 用 `?token={jwt-token}` 传递 access token。07 的 N-01 已要求补三条约束（只接受 access token、Nginx 不记 query、`Cache-Control: no-store`），但**遗漏了最关键的一条：这个 token 就是调用方的完整会话凭据，不是单文件的一次性授权**。

**后果**：HR 把预览页 URL 粘贴给同事/贴进工单/发到微信群，接收方在 access token 剩余有效期内（最长 2 小时）可用该 token 调用**任意** `/api/admin/**` 接口——包括 H-RESUME-007 导出全部简历 Excel。一次"分享一份简历"变成一次完整的会话移交。学生端同理（泄露完整档案 + 全部投递）。

**3. S-14　LibreOffice 转换的攻击面在全部设计文档中零覆盖（高危，阻塞）**

03 §8 R2、06 §5.1.4、01 §R1 都只讨论 LibreOffice 的**稳定性**（超时、profile 锁、僵死进程），**没有一行讨论它的安全性**。而这是本系统唯一一处"接受公网匿名注册用户上传的任意二进制文件，并用服务端进程主动解析它"的位置——攻击面模型上等同于把一个文档解析器暴露在公网。

**后果**：学生上传特制 .doc/.docx，触发 LibreOffice 的外部实体/OLE 链接加载（SSRF + 内网探测 + NTLM 哈希外泄）、DDE/Basic 宏执行、已知解析器内存破坏 CVE。由于转换进程继承 Spring Boot 服务账号权限（03 未定义降权），一次成功利用即拿到对 `E:\atmoto-recruit\data\`（全部简历原件）与 `app\config\application-prod.yml`（DB 密码、JWT 双密钥、阿里云 AK/SK）的读权限。

## 一、认证与会话安全

### S-01　refresh token 无轮换、无被盗用检测（高危，阻塞）

**风险描述**：07 的 C-04 裁决为 access 2h + refresh 7d 落库可吊销，并明确写了"refresh token 本身不轮换，降低实现复杂度"。这个取舍在本场景不成立。

**具体攻击场景**（可复现）：
1. 学生在宣讲会现场用公用笔记本登录门户，投递后关闭浏览器但未点登出（C-04 裁决理由第 1 条自己论证了这是真实高频场景）。
2. 下一位使用者打开 DevTools → Application → localStorage，读取 `refresh_token` 值，复制走。
3. 攻击者在自己的机器上 `POST /api/portal/auth/refresh`，得到新 access token（2h）。
4. 由于 refresh token 不轮换、`expire_time` 固定为签发时 +7 天，攻击者可在 **7 天内每 2 小时刷新一次**，持续读取该学生的姓名、手机号、出生日期、户籍地、教育经历、简历附件原件。
5. 学生本人正常使用完全无感——同一条 refresh token 行在双方手里都有效，无任何冲突信号。

C-04 提供的补救是"个人中心的『在其他设备退出登录』按钮"，但它依赖学生**先察觉异常**，而本场景下学生察觉不到任何异常。

**影响**：单个学生完整个人信息集合泄露，持续 7 天不可发现。在机房/图书馆可规模化收集。

**修复方案**：
1. **refresh token 轮换**：`/api/portal/auth/refresh` 每次成功后删除旧行、插入新行、返回新 refresh token；前端 axios 拦截器同步更新 localStorage。
2. **重放检测**：`stu_refresh_token` 增加 `rotated_at DATETIME DEFAULT NULL`。轮换时不删除旧行而是置 `rotated_at=NOW()`。若收到一个 `rotated_at` 非空且超出宽限窗口的 token（说明同一条链被两方持有）→ **删除该 `student_id` 的全部 refresh token 行** + 写审计 + 站内信通知"检测到异常登录，已强制全部设备登出"。这是 OAuth2 BCP 的标准 rotation + reuse detection，实现只需一列 + 一个 if 分支。
3. **绝对上限**：轮换时 `expire_time` 沿用原值，不因活跃而延长——refresh 链总寿命自首次登录起 7 天。**该语义必须写入 DDL 注释**（C-04 的 DDL 未定义此语义，实现者极可能写成"每次刷新顺延 7 天"，等于永久会话）。
4. **UA 变更留痕**：刷新时若 `device_info` 摘要不匹配，不拒绝（换网络是常态），但写 `log_student_login` 一条 `REFRESH_UA_MISMATCH`，供事后追查。

**修复成本**：0.4 人日（DDL 加列 0.05 + 轮换与重放检测 0.2 + 前端同步 0.1 + 测试 0.05）
**是否阻塞上线**：**是**

### S-02　并发刷新竞态：S-01 的修复若不配套会把学生自己踢下线（高危，与 S-01 同批）

**风险描述**：这是 S-01 修复方案的直接副作用。若不同时处理，安全修复反而制造必现可用性事故。

**具体场景**：
1. 学生的 access token 在 14:00:00 过期。
2. 个人中心页同时发起 3 个请求（05 §5.1 的页面设计确实会并发调 profile、educations、resume/files）。
3. 三个请求同时收到 401，axios 拦截器**同时**发起 3 次 `/refresh`，都携带同一个 refresh token。
4. 服务端：第 1 次成功并轮换；第 2、3 次拿到已轮换的旧 token → 命中 S-01 的重放检测 → **删除全部 refresh token 并强制登出**。
5. 学生刚打开个人中心就被踢回登录页，且每次都重现。**这是必现 bug，不是偶发**。

07 的 U-9 已提出前端"Promise 队列合并"，但那只是前端约束；服务端仍必须容忍竞态，否则任何前端逻辑退化（新页面、第三方组件、多标签页）都会触发强制登出。

**修复方案**：
1. **前端**（U-9 已定，此处强制执行）：单例刷新 Promise，并发 401 全部 await 同一个 Promise。
2. **服务端宽限窗口（关键）**：收到 `rotated_at` 非空的 token 时——
   - `NOW() - rotated_at <= 30 秒` → 判定并发竞态，**幂等返回轮换后的那个新 token**，不触发重放检测；
   - `> 30 秒` → 判定真实重放，执行 S-01 的全家族吊销。
3. 已轮换行的清理并入 T3 定时任务：`DELETE FROM stu_refresh_token WHERE rotated_at < NOW() - INTERVAL 1 HOUR`。

**修复成本**：含在 S-01 的 0.4 人日中
**是否阻塞上线**：**是**（与 S-01 同批）

### S-03　HR 端无登录失败锁定设计，且失败计数未列入去 Redis 化改造清单（高危，阻塞）

**风险描述**：04 的 `stu_user` DDL 有 `login_fail_count` 与 `lock_until` 两列（已核实 04:304-305），**学生端锁定有数据支撑**。HR 端用 RuoYi 原生 `sys_user`，而：

- 03 §5.1.2 只写了"HR 初始密码随机生成 + 首次登录强制修改"，**没有任何失败锁定设计**；
- 03 §8 R3 缓解措施⑤只写"**学生**登录失败 5 次锁定 15 分钟"——HR 端不在其中；
- "5 次失败锁定 15 分钟"仅出现在 03 §3.2② 的"**若甲方坚持暴露后台的最小加固包**"中，即被定位为可选项，默认方案不含；
- **最关键**：RuoYi 原生的失败计数存在 Redis（`SysLoginService` 用 `redisCache` 存 `pwd_err_cnt:{username}`），而 03 §2.3 的去 Redis 化改造清单 7 项中**没有一项提到失败计数**。07 的 C-08 逐点量化了 7 处改造，同样遗漏。若实现者只按清单改造，`SysLoginService` 会通过 `CaffeineCache` 门面类工作但**语义未经验证**（Caffeine 的 `expireAfterWrite` 与 Redis 的按 key 独立 `expire` 行为不同，RuoYi 用的是"设置时带 TTL"的调用方式，门面类若只实现 `setCacheObject(key, value)` 而丢弃 TTL 参数，计数将永不过期或永不生效）。

**具体攻击场景**：
1. 攻击者已在内网（承包商 Wi-Fi、被钓鱼的员工机、离职 HR 的 VPN 账号未及时禁用）。
2. 访问 `http://192.168.10.50:8000`，用 RuoYi 原生 `/login` 接口爆破。
3. 图形验证码由 Kaptcha 生成，`/captchaImage` 无限流，攻击者每次先取新验证码用 OCR 识别（开源 ddddocr 对 Kaptcha 默认配置识别率 >90%）——**图形验证码不构成有效阻挡**。
4. 无锁定或锁定失效时可持续爆破。HR 账号约 10 个、用户名可猜（`admin`、姓名拼音），弱口令命中概率不低。
5. 命中即获得**全部简历库**（因 S-06，任一 HR 账号都能读全部）。

**影响**：简历库整体失窃。这是本系统的最高价值目标。

**修复方案**：
1. **在 03 §2.3 改造清单增加第 8 项**：`SysLoginService` 的失败计数（`pwd_err_cnt:{username}`）明确改用 Caffeine，`expireAfterWrite(15min)`，并要求 `CaffeineCache` 门面类**必须实现带 TTL 参数的 `setCacheObject(key, value, timeout, unit)` 重载**（RuoYi 原 `RedisCache` 有此重载，C-08 的 11 个方法清单里已含，但未点名它承载着失败计数这一安全语义）。改造后**必须单独测试**：连续 5 次错误密码 → 第 6 次即使密码正确也被拒 → 15 分钟后自动解锁。
2. **HR 端锁定策略写入 03 §5.1.2**（当前完全缺失）：连续失败 **5 次锁定 15 分钟**；锁定事件写 `sys_logininfor` 并触发告警邮件给 IT（复用 03 §5.5 的 SMTP 通道）。**从 §3.2② 的"可选加固包"移入 §5.1.2 的基线设计**。
3. **HR 密码策略强化**：07 的 N-16 已裁决统一"8–20 位含字母与数字"。安全侧追加——HR 端额外要求含大写或特殊字符，并做弱口令字典包含匹配（200 行常见弱口令 + `atmoto`/`recruit`/`2026` 等项目相关词根）。理由：HR 账号是拖库首要目标，学生账号泄露只影响本人，两者不应同策略。
4. **会话固定**：已核实 03 §5.1.7 明确"全程 JWT + Authorization 头，不使用 Cookie 承载会话"，RuoYi 侧亦为纯 JWT。**架构上免疫会话固定，无需额外措施，此项已闭环。**
5. **并发登录**：裁决**不做单点登录限制**（HR 在工位 PC 与笔记本同时登录是正常工作方式）。但**必须**在 03 §5.5 的每日 08:30 日报中增加一行"昨日 HR 登录 IP 去重列表 + 首次出现的新 IP 标红"——异常 IP 靠人眼在日报里发现，成本为零，且这是本项目唯一现实可行的入侵检测手段。

**修复成本**：0.3 人日
**是否阻塞上线**：**是**

### S-04　登出的残留窗口在 URL token 场景被放大（中危）

**风险描述**：C-04 裁决承认"登出后最长 2 小时内旧 access token 仍有效，这是可接受的残留窗口"。在纯 Header 传输场景该判断成立（token 只在 localStorage，登出即清）。但**叠加 S-11 的 URL token 后不成立**：access token 会进入浏览器历史记录、Referer 头、书签，以及被粘贴的任何地方，登出无法清除这些副本。

**具体场景**：HR 在公用会议室电脑预览简历（URL 含 token）→ 点登出 → 离开。下一位使用者 Ctrl+H 打开历史记录，点那条预览 URL → **仍可访问该简历**，且可把 token 从 URL 抠出来调其他 admin 接口，直到自然过期。

**影响**：登出这一安全动作在最需要它的场景（公用设备）失效。

**修复方案**：随 S-11 一并修复（改为一次性短效签名 URL 后此问题自动消失）。若 S-11 因故不改，退而求其次是预览页 `beforeunload` 时 `history.replaceState` 抹掉 query——**这是脆弱补丁，不作为最终方案**。

**修复成本**：0（含在 S-11）
**是否阻塞上线**：随 S-11 阻塞

### S-05　短信防刷"六层"的实际有效层数是 3 层，且第 6 层为空（中危，含 1 个阻塞子项）

**风险描述**：03 §5.1.6 列了六层防刷。逐层核实：

| 层 | 措施 | 核实结论 |
|---|---|---|
| 1 | 图形验证码（RuoYi Kaptcha） | ⚠️ **可绕过**。Kaptcha 默认字符/算术验证码 OCR 识别率高；`/captchaImage` 本身无限流，可无限获取。**有效性：低** |
| 2 | 同手机号 60 秒 1 条 | ✅ 有效。但只防单号高频，不防**号码轮换** |
| 3 | 同手机号 24h 10 条 | ✅ 有效，同上局限 |
| 4 | 同 IP 24h 20 条 | ⚠️ **部分有效**。4G 拨号或代理池换 IP 即绕过。且对**校园网 NAT 出口是误伤** |
| 5 | Nginx `limit_req zone=sms_api rate=1r/m burst=2` | ⚠️ 同源同缺陷。`$binary_remote_addr` 受 NAT 影响，1r/m 对校园网出口是灾难性误伤 |
| 6 | 手机号正则 + **黑名单表** | ❌ **黑名单表在 04 的全部表中不存在**（已 grep 核实：仅 03 §5.1.6 提及，04 无对应 DDL，07 的 N-03 补建的 2 张日志表也不含它）。**这一层当前是空的** |

**真实有效层数**：第 2、3 层（手机号维度）+ 第 4/5 层的部分效果 = **实质 3 层**，不是六层。

**具体攻击场景（短信炸弹 / 成本攻击）**：
1. 准备 10000 个真实手机号（号段遍历即可）。
2. 用 ddddocr 自动识别图形验证码（第 1 层失效）。
3. 用 4G 代理池轮换 IP（第 4、5 层失效）。
4. 每个手机号只发 1 条——**第 2、3 层完全无法阻止，因为每个号的行为都完全合规**。
5. 结果：10000 条短信，按 0.04 元/条 = **400 元**直接损失 + 10000 个陌生人收到遨天科技短信（品牌损害 + 被投诉到运营商导致**签名被封**，而签名报备需 15 工作日，封了就等于注册功能停摆半个月）。
6. 03 的"最后防线——阿里云控制台日发送量上限"确实是有效止损，但它把后果从"花光余额"降级为"当天正常学生也发不出验证码"，在宣讲会当天等于系统瘫痪。

**同时存在的可用性缺陷（危害更大，必须一并解决）**：目标院校校园网出口 IP 数量有限，宣讲会当天数百学生集中注册时，Nginx `rate=1r/m` 意味着**该校园网每分钟只有 1 个学生能发出验证码**，其余全部 503。这是必然发生的。

**修复方案**：
1. **第 1 层强化**：Kaptcha 改为干扰线 + 扭曲 + 6 位混合字符，或直接换阿里云验证码 2.0（与短信同厂商，无新增常驻组件）。**推荐后者**：OCR 绕过成本从"免费"升到"需打码平台"，配合第 2/3 层后攻击经济性归零。
2. **第 4/5 层改分级限流，解决 NAT 误伤**：
   - Nginx `sms_api` 的 `rate` 从 `1r/m` 放宽到 `10r/m burst=20 nodelay`，精确控制交给应用层；
   - 应用层 IP 维度改双阈值：单 IP **24h 50 条**（放宽覆盖 NAT）+ 单 IP **10 分钟 10 条**（收紧防脚本）；
   - 新增**联合规则**：同一 IP 24h 内出现 >30 个不同手机号 **且** 该 IP 的"发码后完成注册率" < 30% → 拒绝并告警。正常 NAT 出口学生号码同样分散，但他们发了就会用；攻击者只发不用。这一条精确打击号码轮换模式且不误伤校园网。
3. **补建黑名单表**（第 6 层当前为空）：新增 `log_sms_blacklist`（`target_type` ENUM(PHONE,IP) / `target_value` / `reason` / `expire_time` / `create_time`），命中上述规则时自动写入，24h 自动过期，T3 定时任务清理。并入 07 的 N-03 已裁决新建的 `log_` 日志域。
4. **阿里云侧硬止损（03 已提，此处升级为部署清单强制勾选项）**：日发送量上限 = 预估峰值 ×3（如预估 300 条/日则设 1000），余额告警阈值 200 元。
5. **`scene` 参数**：07 的 U-7 已裁决（区分 `REGISTER`/`RESET_PWD`），本报告确认必要且同批实施——同时用于**分场景独立计数**，防止攻击者用找回密码流程耗尽注册流程的配额。

**修复成本**：0.5 人日（行为验证码 0.1 + 分级限流 0.2 + 黑名单表与规则 0.15 + 测试 0.05）
**是否阻塞上线**：**部分**——整体属中危可后续优化，但**第 4/5 层的 NAT 误伤修复（0.2 人日）必须上线前完成**，否则宣讲会当天注册大面积失败。

### S-07　附件 ID 可遍历，且归属校验无统一强制点（高危，阻塞）

**风险描述**：
- 04 的全部表主键为"BIGINT AUTO_INCREMENT"（04 §4 建表约定原文），`stu_resume_file.id` 因此是连续自增整数。
- 05 §4.6 声称"不支持直接 URL 猜测下载（存储路径为 UUID 命名，不可遍历）"——**这句话是错的**。不可遍历的是**磁盘存储路径**，而 API 暴露的是**数据库自增 ID**（`/api/portal/attachment/{id}`）。攻击者遍历的是后者，磁盘路径命名与此无关。这是设计文档中一处实质性的错误推理，必须纠正。
- 05 §3.2 中 `fileId` 的示例值写成 `"f3a2b1c4d5e6..."`（形如 UUID），与 04 的 `BIGINT` 主键**类型不一致**——实现者会二选一，若选 BIGINT 则可遍历，若选 UUID 则需在 DDL 增列。**当前两份文档在这一点上没有一致结论。**

**具体攻击场景**（可复现步骤）：
1. 学生 A 正常注册登录，上传自己的简历，记下返回的 `fileId`（假设 = 137）。
2. 用自己的合法 access token，循环请求 `GET /api/portal/attachment/{1..500}?mode=download`。
3. 若归属校验有任何一处遗漏（见下方"为什么会遗漏"），即可批量下载他人简历原件。
4. 即使归属校验全部生效，攻击者仍可通过**响应差异**枚举出系统内附件总数与 ID 分布（403 vs 404 的差异），进而推断投递规模——属信息泄露，危害较低但应一并处理。

**为什么会遗漏（这是真实风险而非理论风险）**：03 §5.1.3 定义了 `PortalOwnershipGuard.assertOwn(entityType, entityId)` 并要求"凡返回学生私有数据的 Service 方法第一行必须调用"，但这是**约定式防护**——依赖每个实现者在每个方法记得写一行。05 中有 6 个接口需要归属校验，07 又新增 4 个（S-10），共 10 处；只要有一处漏写即形成漏洞，且**漏写不会导致任何测试失败**（正常用户永远访问自己的数据，功能测试全绿）。

**影响**：任意学生批量下载全体学生简历原件。这是本系统最严重的水平越权后果。

**修复方案**：
1. **把归属校验从"约定"改为"结构性强制"**——三选一，推荐第一种：
   - **（推荐）Mapper 层强制**：所有 `stu_*` 与 `app_*` 表的学生侧查询走 MyBatis-Plus 拦截器，自动为 SQL 追加 `AND student_id = #{当前学生ID}`（从 `PortalUserHolder` 取）。类似 RuoYi 的 `@DataScope` 但更简单——**学生端只有一条规则，无需可配置**。漏写归属校验时 SQL 天然查不到他人数据，返回 404 而非泄露。成本 0.3 人日，一次性覆盖全部 10 处。
   - 备选 A：AOP 切面拦截 `biz.portal.controller` 包下所有带 `@PathVariable` 的方法，强制要求方法上有 `@OwnerCheck(entity=...)` 注解，无注解则**启动时报错**（`ApplicationContext` 初始化阶段扫描，把漏写变成启动失败而非运行时漏洞）。
   - 备选 B：维持 03 的手写 Guard，但增加一条 ArchUnit 单元测试断言"`biz.portal.service` 下所有接收 Long 型 ID 参数的 public 方法的第一条语句必须是 `assertOwn`"。**较脆弱，不推荐**。
2. **附件 ID 改为不可遍历**：`stu_resume_file` 增加 `file_uuid CHAR(36) NOT NULL` 列 + 唯一索引，API 路径用 `file_uuid` 而非自增 ID。这同时消解了 05 与 04 的类型不一致（05 的示例值本就是 UUID 形态）。**注意**：这只是纵深防御的一层，**不能替代归属校验**——不可遍历的 ID 若泄露一次仍可被使用。
3. **响应统一化**：归属校验失败与对象不存在**一律返回 404 + 相同响应体**，不返回 403。理由：403 会向攻击者确认"该 ID 存在但不属于你"，是有效的枚举信号。（注：03 §7.2 的 M3 验收标准第④条写的是"学生 A 的 token 请求学生 B 的档案返回 403"——**该验收标准需同步改为 404**。）

**修复成本**：0.4 人日（Mapper 拦截器 0.3 + `file_uuid` 列与路径改造 0.1）
**是否阻塞上线**：**是**

### S-08　H-RESUME-003 的 applicationId 与 fileId 无绑定校验（高危，阻塞）

**风险描述**：05 §3.7 的 H-RESUME-003 路径为 `GET /api/hr/resumes/{applicationId}/preview/{fileId}`，权限仅标 `hr:resume:query`。路径中同时出现两个 ID，但**没有任何文档要求校验二者的从属关系**。

**具体攻击场景**：
1. 招聘专员 HR-B 只负责"结构设计工程师"岗位，其数据范围内有投递记录 `applicationId=500`（合法可见）。
2. HR-B 想看 HR-A 负责的"电源研发工程师"岗位的某份简历，该简历附件 `fileId=137`（HR-B 无权访问）。
3. HR-B 请求 `GET /api/admin/resumes/500/preview/137`。
4. 若实现只校验 `applicationId=500` 在数据范围内（这是最自然的实现方式，因为数据范围规则挂在 application 上），而直接用 `fileId=137` 去取文件流 → **越权成功**。
5. 更严重：即使 S-06 的数据范围修复到位，这个漏洞依然存在——因为数据范围校验的对象是 `applicationId`，而实际返回的资源是 `fileId` 指向的文件。**这是典型的"校验对象与操作对象不一致"漏洞。**

**影响**：数据范围隔离被绕过，招聘专员可读取任意简历附件。使 S-06 的修复失去意义。

**修复方案**：
1. **首选：删除该接口**。07 的 N-01 已将附件访问统一到 `/api/admin/attachment/{id}?mode=preview|download`，H-RESUME-003 与之重复。删除后只保留一个附件入口，校验逻辑收敛到一处。
2. 若保留，则**必须**在 Service 层增加绑定校验：`SELECT 1 FROM app_snapshot s JOIN app_application a ON s.id=a.current_snapshot_id WHERE a.id=#{applicationId} AND JSON_EXTRACT(s.snapshot_resume_file,'$.fileId')=#{fileId}`——即校验该附件确实是该投递快照所引用的那一个。
3. **通用原则写入 05 §2**：「**任何路径中出现两个及以上资源 ID 的接口，必须显式校验它们之间的从属关系**；无法校验时应重构为单 ID 接口。」这条原则同样适用于 H-RESUME-004（`{applicationId}/note`）等。

**修复成本**：0.2 人日
**是否阻塞上线**：**是**

### S-09　归属校验依赖人工约定，无自动化验证手段（高危，与 S-07 同批修复）

**风险描述**：见 S-07 的"为什么会遗漏"。此处补充**验收侧**的缺口：

- 03 §7.2 M3 验收标准第④条只有一条越权测试："学生 A 的 token 请求学生 B 的档案返回 403"。
- **只测了档案（profile）一个对象**。而需归属校验的对象共 5 类：教育经历、简历附件、投递记录、投递快照、站内消息。**其余 4 类无任何验收覆盖**。
- 03 §5.1.3"越权测试"行同样只写了两条（学生 A 请求学生 B 的附件、招聘专员请求他人岗位简历详情）。

**影响**：即使实现者写对了 8 处、漏了 2 处，验收也发现不了。

**修复方案**：
1. 实现层修复见 S-07（Mapper 拦截器）。
2. **验收层**：编写一个越权测试矩阵脚本（见本报告第五节验收清单 A-3），对**每一个**接收资源 ID 的学生端接口，用学生 A 的 token 请求学生 B 的对象，断言全部返回 404。这个脚本是可复用资产，成本约 0.2 人日，且必须作为 M3/M4/M5 三个里程碑的强制验收项而非仅 M3。

**修复成本**：含在 S-07 的 0.4 人日 + 验收脚本 0.2 人日（计入验收清单成本）
**是否阻塞上线**：**是**

### S-10　07 报告新增的 4 个学生端接口全部漏标归属校验（中危，阻塞）

**风险描述**：07 报告在裁决过程中新增了学生端接口，但落地指令中均未标注归属校验要求：

| 新增接口 | 出处 | 归属校验风险 |
|---|---|---|
| `POST /api/portal/applications/{id}/resubmit` | C-01 落地指令 | 学生 A 可用学生 B 的 `applicationId` 触发重投——虽然重投会用 A 自己的资料生成快照，但**会篡改 B 的投递记录状态**（重置为 `PENDING_SCREEN`）并消耗 B 的 3 次重投配额，是**越权写**操作 |
| `GET /api/portal/messages` | N-12 落地指令 | 列表接口无 ID 参数，需强制 `WHERE receiver_id=当前学生`，07 未写明 |
| `PATCH /api/portal/messages/{id}/read` | N-12 落地指令 | 学生 A 可标记学生 B 的消息为已读（危害低但是越权写） |
| `GET /api/portal/messages/unread-count` | N-12 落地指令 | 同列表 |

`resubmit` 的越权写危害最大：攻击者遍历 `applicationId` 批量触发重投，可**把全体候选人的状态重置为待筛选**，抹掉 HR 已完成的筛选结果（C-01 裁决限定"仅 `PENDING_SCREEN` 状态可重投"能挡住已决状态，但对尚未筛选的记录仍可反复触发，消耗配额并刷新 `apply_time`，扰乱 HR 列表排序）。

**修复方案**：
1. 这 4 个接口纳入 S-07 的 Mapper 拦截器统一覆盖范围（`app_application` 按 `student_id`、`not_message` 按 `receiver_id`）。
2. 在 05 的接口文档中为这 4 个接口显式补标"+数据归属校验"，保持与其余接口的标注一致性。
3. `resubmit` 额外增加**幂等与频次保护**：同一 `applicationId` 60 秒内只接受 1 次重投请求（防止即使归属校验生效，学生对自己的记录反复刷 `apply_time` 把自己顶到列表最前——C-01 已用"最多 3 次"限制总量，但未限制频率）。

**修复成本**：0.1 人日（含在 S-07 拦截器覆盖范围内，仅文档标注与频次保护）
**是否阻塞上线**：**是**（`resubmit` 的越权写）

### S-11　附件预览/下载的 URL token 是完整会话凭据（高危，阻塞）

**风险描述**：05 §4.5/§4.6 用 `?token={jwt-token}` 传 access token，理由是"pdf.js 的 `<iframe>` 嵌入不便于自定义请求头"。07 的 N-01 已要求补三条约束（只接受 access token 不接受 refresh、Nginx `log_format` 用 `$uri` 不记 query、响应 `Cache-Control: no-store`），这三条都必要但**都没有触及核心问题**：

**这个 token 是调用方的完整会话凭据，不是针对单个文件的一次性授权。**

**具体攻击场景 A（HR 侧，危害最大）**：
1. HR 在简历详情页预览候选人简历，地址栏/iframe src 为 `https://.../api/admin/attachment/137?mode=preview&token=eyJhbGci...`。
2. HR 想让部门经理看一眼，直接复制该 URL 发到企业微信群 / 粘进面试评价工单。
3. 群里任何人（包括非 HR 员工、外部顾问）在 2 小时内用该 token 调用 `POST /api/admin/resumes/export`，**导出全部简历 Excel**（含姓名手机号邮箱）。
4. 审计表记录的操作人是**原 HR**，真实操作者无法追溯——审计链被污染。

**具体攻击场景 B（学生侧）**：
1. 学生在公共电脑预览自己的简历，URL 进入浏览器历史。
2. 下一位使用者从历史记录取出 token，读取该学生全部档案与投递记录。
3. 叠加 S-01（refresh 无轮换），若 localStorage 也未清，可持续 7 天。

**具体攻击场景 C（Referer 泄露）**：pdf.js viewer 页面若加载任何外部资源（字体 CDN、错误上报），`Referer` 头会带上完整 URL 含 token。03 的 CSP 已限制 `default-src 'self'`（已核实 03:570），**这一条被 CSP 挡住了**——但 CSP 是配置，一次误改即失效，不应作为唯一防线。

**影响**：一次"分享一份简历"等于一次完整会话移交；审计溯源失效。

**修复方案**（推荐第一种，成本相近但彻底）：
1. **（推荐）一次性签名 URL**：
   - 前端先调 `POST /api/{portal|admin}/attachment/{id}/ticket`（Header 带 token，走正常鉴权 + 归属校验 + 数据范围 + 写审计），服务端返回一个 `ticket`（32 字节随机串）。
   - `ticket` 存 Caffeine，**TTL 60 秒、一次性核销**（取用后立即失效），value 存 `{fileId, 请求者ID, mode}`。
   - iframe src 用 `/api/{portal|admin}/attachment/stream?ticket=xxx`。该 URL 泄露的最大后果是"60 秒内被别人看到同一份简历一次"，**且完全无法用于调用任何其他接口**。
   - 无需 Redis（Caffeine 足够，60 秒 TTL 下重启丢失只影响正在打开的预览，用户重试即可）。
   - **审计在发 ticket 时写，不在 stream 时写**——保证审计记录的是"谁请求了这份简历"，而非"谁的 ticket 被谁用了"。
2. 备选：pdf.js 改用 `fetch` + `Blob URL` 加载（`pdfjsLib.getDocument({data: arrayBuffer})`），token 走 Header，URL 中不出现任何凭据。**技术上完全可行**（05 §4.5 的"不便于自定义请求头"结论只在 `<iframe src>` 直连场景成立，pdf.js 本身支持传 `ArrayBuffer`）。缺点：10MB PDF 需先完整下载到内存再渲染，失去流式加载体验；HR 端可接受，学生端手机浏览器有内存压力。
3. **无论选哪种**，07 的 N-01 三条约束（不接受 refresh token、Nginx 不记 query、`no-store`）仍需保留作为纵深防御。

**修复成本**：0.5 人日（ticket 接口 + Caffeine 存储 + 前后端改造 + 测试）
**是否阻塞上线**：**是**

### S-12　批量下载与导出接口对 ID 数组无归属与数量校验（高危，阻塞）

**风险描述**：
- H-RESUME-007 导出 Excel：`POST /api/hr/resumes/export`，请求体 `{"applicationIds": [42,43,45,47], "fields": [...]}`。
- H-RESUME-008 批量下载附件：`POST /api/hr/resumes/download-attachments`，请求体 `{"applicationIds": [42,43,45]}`。
- 05 §4.8 描述的后端流程是："① 从请求体获取 `applicationIds` 列表 → ② 查询每个投递记录的 `fileId` → ③ 逐个读取文件 → ④ 打包 ZIP"。**第 ① 到 ② 之间没有任何鉴权步骤**。
- 07 的 N-15 已裁决"批量 100 条、导出 1000 条"的**数量**上限，但**没有涉及归属校验**。

**具体攻击场景**：
1. 招聘专员 HR-B（数据范围内只有 30 份简历）用浏览器 DevTools 直接构造请求：
   ```
   POST /api/admin/resumes/download-attachments
   Authorization: Bearer <HR-B 的合法 token>
   {"applicationIds": [1,2,3,...,100]}
   ```
2. 服务端按 05 §4.8 的流程逐个读文件打包 → **HR-B 拿到全部 100 份简历原件**。
3. 导出接口同理，且更严重：`fields` 数组由前端指定，若无白名单可请求非展示字段。
4. **审计记录显示"HR-B 导出了 100 条"，看起来像正常操作**——因为审计只记条数不记数据范围校验结果（03 §5.2.2 的审计字段中确实有"影响条数"但无"越权尝试标记"）。

**为什么这是最容易漏的一类**：数据范围（`@DataScope`）在 RuoYi 中是通过 AOP 在 **Mapper 查询的 WHERE 子句**注入实现的。而批量接口的模式是"前端给一批 ID → 后端按 ID 取"，若实现者写成 `selectBatchIds(ids)`（MyBatis-Plus 内置方法），**`@DataScope` 的 SQL 注入点根本不会生效**——因为那是 MP 的内置 SQL，不经过项目的 Mapper XML。这是一个 RuoYi + MyBatis-Plus 组合下的经典陷阱。

**影响**：数据范围隔离在两个"数据外流的最主要途径"（03 §5.2.2 原话）上完全失效。

**修复方案**：
1. **批量接口一律不接受裸 ID 数组作为唯一入参**。改为：ID 数组 **必须** 与当前用户的数据范围做交集，交集外的 ID **静默丢弃并在响应中返回 `skippedCount`**（不报错，避免成为存在性探测通道）。实现方式：`SELECT id FROM app_application a JOIN job_position j ON a.job_id=j.id WHERE a.id IN (...) AND (#{isAdmin} = 1 OR j.owner_user_id = #{currentUserId})`。
2. **禁止使用 `selectBatchIds`** 等绕过 Mapper XML 的 MP 内置方法处理简历数据。写入 03 §2.2 的 Code Review 检查项。
3. **`fields` 字段白名单**：导出字段必须在服务端枚举白名单内（`studentName`/`phone`/`email`/`schoolName`/`major`/`degree`/`gpa`/`jobName`/`status`/`applyTime` 共 10 个，即 05 示例中的那组），非白名单字段直接忽略。防止实现者用反射按字段名取值导致意外暴露（如 `password_hash`）。
4. **审计增强**：导出/批量下载的审计记录增加 `requested_count` 与 `granted_count` 两个数值。二者不等时（有 ID 被数据范围过滤掉）**触发一条 WARN 日志 + 计入日报**——这是发现内部越权尝试的唯一信号。
5. 数量上限沿用 07 的 N-15 裁决（批量 100 / 导出 1000）。

**修复成本**：0.3 人日
**是否阻塞上线**：**是**

### 2.2 垂直越权：学生 token 访问 HR 接口

**核实结论**：**结构性阻断在应用层成立，但在 Nginx 层有缺口。**

**应用层（成立）**：已逐项核实 03 §5.1.1 的四条隔离——独立用户表（`stu_user` vs `sys_user`）、独立 JWT 密钥（`jwt.portal.secret` vs `jwt.admin.secret`，且 03 §6.4 要求首次部署时随机生成、不同环境不同值）、独立 SecurityFilterChain（`portalFilterChain` @Order(1) `securityMatcher("/api/portal/**")` + `adminFilterChain` @Order(2) 兜底）、`aud` claim 区分。学生 token 到 `adminFilterChain` 上**验签即失败**（密钥不同），不依赖任何 `@PreAuthorize` 注解写对。**这一设计是本方案安全性最强的部分，判定为有效闭环。**

**但有三个前提必须在验收时实测确认**（否则闭环只存在于文档）：
- 两个密钥确实不同且非示例值（S-24）；
- `portalFilterChain` 的 `securityMatcher` 确实只匹配 `/api/portal/**`——若写成 `/api/**` 则学生 token 会接管全部接口（S-13）；
- `adminFilterChain` 确实是兜底链（无 `securityMatcher`），否则未匹配任何链的请求会**直接放行**（Spring Security 6 的多链模式下，无链匹配 = 无安全约束）。

### S-13　双过滤链的兜底行为未定义，存在"无链匹配即放行"风险（中危）

**风险描述**：Spring Security 6 的多 `SecurityFilterChain` 模式下，请求按 `@Order` 依次匹配 `securityMatcher`，**若无任何链匹配，该请求不经过 Spring Security 过滤器，直接到达 Controller**。

03 §5.1.1 描述 `adminFilterChain` 为"其余全部，`@Order(2)`"，这个表述**可以**被实现为无 `securityMatcher`（真兜底），也**可以**被误实现为 `securityMatcher("/api/admin/**", "/api/system/**")`（显式列举）。后者会导致：

**具体场景**：07 的 N-11 裁决 HR 端认证用 RuoYi 原生路径 `/login`、`/getInfo`、`/getRouters`、`/captchaImage`——这四个路径**既不在 `/api/portal/**` 也不在 `/api/admin/**` 或 `/api/system/**`**。若 `adminFilterChain` 用显式列举，这四个路径**不匹配任何链** → 无认证约束 → `/getInfo` 可匿名调用返回当前用户信息（虽然无用户上下文时会 NPE，但 `/getRouters` 可能直接返回完整菜单树，**泄露全部后台功能结构与权限点标识**）。

**影响**：后台菜单结构、权限点命名、功能清单泄露，为进一步攻击提供侦察信息。

**修复方案**：
1. 在 03 §5.1.1 明确写死：「`adminFilterChain` **不配置 `securityMatcher`**，作为真正的兜底链，捕获所有未被 `portalFilterChain` 匹配的请求，包括 RuoYi 原生的 `/login`、`/getInfo`、`/getRouters`、`/captchaImage` 及任何未来新增的非 `/api/portal/**` 路径。」
2. **默认拒绝**：`adminFilterChain` 的 `authorizeHttpRequests` 必须以 `.anyRequest().authenticated()` 结尾，白名单只放行 `/login`、`/captchaImage`。
3. 验收实测：用无 token 的 curl 请求 `/getRouters`、`/getInfo`、`/actuator/health`、以及一个不存在的路径 `/foobar`，断言全部返回 401（而非 200 或 404）。

**修复成本**：0.1 人日（配置 + 验收）
**是否阻塞上线**：否（中危），但**验收清单必须包含实测项**

### S-06　HR 间数据级越权完全没有实现路径（高危，阻塞，本次最严重）

**风险描述**：三处同时断裂，任一处都足以使数据级隔离失效：

**断裂 1：字段不存在。** `job_position.owner_user_id` 在 04 的 DDL 中不存在（07 的 N-06 已指出并给出 ALTER 补丁）。本报告确认其安全后果——**没有这个字段，"谁负责哪个岗位"这个数据在系统中根本不存在**，数据范围规则无判定依据。

**断裂 2：接口层零约束（07 未识别）。** 已 grep 核实：**05 全文 0 次出现 `@DataScope`、"数据范围"、"数据权限"、`owner`**。逐个接口核实：

| 接口 | 标注的权限 | 数据范围约束 | 泄露内容 |
|---|---|---|---|
| H-RESUME-001 简历列表 | `hr:resume:list` | ❌ **无** | 全部候选人姓名/学校/专业/学历/岗位/状态 |
| H-RESUME-002 简历详情 | `hr:resume:query` | ❌ **无** | 完整个人信息（含手机号、邮箱、出生日期、户籍地、现居地） |
| H-RESUME-003 附件预览 | `hr:resume:query` | ❌ **无** | 简历附件原件 |
| H-RESUME-004 内部备注 | `hr:resume:edit` | ❌ **无** | 可读写他人岗位的 HR 评价 |
| H-RESUME-005/006 状态变更 | `hr:resume:edit` | ❌ **无** | **可改他人岗位候选人的筛选结果**（越权写） |
| H-RESUME-007 导出 Excel | `hr:resume:export` | ❌ **无** | 批量个人信息外流（见 S-12） |
| H-RESUME-008 批量下载 | `hr:resume:export` | ❌ **无** | 批量简历原件外流（见 S-12） |
| H-REPORT-001~006 | `hr:report:view` | ❌ **无** | 07 的 U-6 已识别 |
| H-JOB-001~005 岗位管理 | `hr:job:*` | ❌ **无** | 可编辑/下架他人负责的岗位 |

**断裂 3：角色与权限点的分配关系未定义。** 03 §5.1.3 说 P0 实现"招聘主管（全部简历）/ 招聘专员（仅本人负责岗位）"两级，但 05 §3.8 的 SYS-USER-001（HR 账号管理）**没有定义这两个角色分别持有哪些权限点**，也没有定义"数据范围"这个角色属性如何配置。RuoYi 的 `sys_role.data_scope` 字段有 5 个取值（全部/自定义/本部门/本部门及以下/仅本人），但**本项目需要的"仅本人负责的岗位"不是这 5 个中的任何一个**——`data_scope=5`（仅本人）在 RuoYi 中是按 `create_by` 判定，而岗位负责人 ≠ 岗位创建人（岗位可由主管创建后指派给专员）。**必须自定义第 6 种数据范围规则**，而这一点 03 只写了"`@DataScope` 的自定义规则分支"一句，没有任何落地定义。

**具体攻击场景**：
1. 招聘专员 HR-B 入职，被分配 `招聘专员` 角色，负责"结构设计工程师"岗位。
2. HR-B 登录后台，打开"简历管理"页面 → `GET /api/admin/resumes?pageNum=1&pageSize=100`。
3. 由于无数据范围注入，返回**全部岗位的全部候选人**——包括核心岗位（如"卫星总体设计师"）的候选人名单。
4. HR-B 点击任一简历 → 完整个人信息 + 简历原件。
5. HR-B 导出 Excel → 全部候选人的姓名 + 手机号 + 邮箱 + 学校，可直接用于竞业挖角或出售。
6. **全程无任何异常信号**：权限点校验通过、审计记录显示"HR-B 查看了简历"（看起来是正常工作）、无告警。

**影响**：
- 需求 A-003 的权限管理需求名义实现、实质落空；
- 03 §7.2 M5 验收标准第③条（"招聘专员看不到他人负责岗位的简历→403"）**必然失败**；
- 内部数据泄露的最主要通道，且是最难事后追责的一种（操作全部"合规"）。

**修复方案**（这是本报告成本最高的一项，必须完整执行）：
1. **补字段**：执行 07 的 N-06 DDL 补丁中的 `job_position.owner_user_id BIGINT NOT NULL` + `idx_owner_status` 索引。**追加要求**：该字段必须 `NOT NULL`，岗位创建接口（H-JOB-002）必须强制指定负责人（默认为创建者本人，但可改），否则会出现"无主岗位"——无主岗位在"仅本人负责"规则下**对所有专员都不可见**，成为数据孤岛。
2. **定义自定义数据范围规则**（03 §5.1.3 必须补全）：
   - 在 `sys_role` 上使用 RuoYi 的 `data_scope='2'`（自定义）或新增取值 `'6'`（岗位负责人），并在 Mapper XML 的 `${params.dataScope}` 占位处注入 `AND j.owner_user_id = #{currentUserId}`。
   - **明确写出受该规则约束的全部 SQL 位置清单**：简历列表、简历详情、附件访问、状态变更、备注读写、导出、批量下载、6 个报表、岗位列表、岗位编辑 = **共 17 处**。这份清单是 Code Review 的检查依据。
3. **角色权限点分配表**（05 §3.8 必须补）：

| 角色 | 数据范围 | 持有权限点 |
|---|---|---|
| 超级管理员（`admin`） | 全部 | 全部，含 `system:*` 与 `system:audit:list` |
| 招聘主管 | **全部** | `hr:job:*`、`hr:resume:*`（含 `export`、`reset`）、`hr:report:view`、`system:audit:list` |
| 招聘专员 | **仅本人负责岗位** | `hr:job:list`/`query`（**不含 `add`/`edit`/`remove`**）、`hr:resume:list`/`query`/`edit`、`hr:report:view`；**不含 `hr:resume:export`** |

> **关键裁决**：`hr:resume:export`（Excel 导出与批量下载附件）**只授予招聘主管，不授予招聘专员**。理由：这是 03 §5.2.2 认定的"数据外流的最主要途径"，而专员是人数最多、流动性最高的角色。专员如需导出，走主管代为操作。这条限制成本为零（只是不勾选一个权限点），收益是把批量外流的可操作人数从"全体 HR"压到"1–2 名主管"。

4. **越权写的额外防护**：H-RESUME-005/006（状态变更）除数据范围外，还需在 Service 层二次校验"该 application 所属岗位的 `owner_user_id` = 当前用户 或 当前用户是主管"，**不能只依赖 Mapper 层的 WHERE 注入**——因为 UPDATE 语句的数据范围注入比 SELECT 更容易被实现者遗漏。
5. **岗位负责人变更的处置**：07 的 U-3 已裁决"按当前值实时判定，不做历史快照，变更本身写审计"。本报告确认该裁决合理并追加一条：**负责人变更接口必须只对招聘主管开放**（权限点 `hr:job:assign`），否则专员可自行把岗位改到自己名下，数据范围形同虚设。**这一点 07 未覆盖，是该裁决的一个漏洞。**

**修复成本**：0.6 人日（DDL 与索引 0.05 + 自定义数据范围规则与 17 处 SQL 0.3 + 角色权限点配置与初始化数据 0.15 + 越权写二次校验 0.1）
**是否阻塞上线**：**是**

### S-16　审计日志无法区分"正常访问"与"越权尝试"（中危）

**风险描述**：03 §5.2.2 的审计字段包含"结果(成功/失败)"，但：
- 越权被拒的请求，在 `AccessDeniedException` 分支写审计（03 §5.4 异常表已定义"403 → 同时写审计"）；
- **但数据范围过滤掉的记录不会抛异常**——SQL 的 WHERE 注入使得查询结果为空，返回的是"查无此记录"，走的是正常路径，**不写任何审计**。

**具体场景**：HR-B 遍历 `applicationId` 探测他人岗位的简历，每次都返回 404/空。系统日志中这与"用户点了一个已删除的链接"完全无法区分。**内部人员的横向探测行为不可见。**

**修复方案**：
1. 数据范围过滤导致的空结果，Service 层区分两种情况：`SELECT COUNT(*) FROM app_application WHERE id=?`（无数据范围）> 0 但带数据范围查询为空 → **判定为越权尝试**，写审计 `operation_type='ACCESS_DENIED'` + WARN 日志。这需要多一次查询，但只在"查不到"时才执行，正常路径零开销。
2. 日报（03 §5.5 第 3 项）增加一行"昨日越权尝试次数 + Top 3 操作人"。连续 3 天有同一人的越权尝试 → 邮件告警 IT。
3. S-12 的 `requested_count` vs `granted_count` 差值同样计入此指标。

**修复成本**：0.2 人日
**是否阻塞上线**：否（可后续优化，但强烈建议随 S-06 一起做）

### S-14　LibreOffice 转换的攻击面在全部文档中零覆盖（高危，阻塞，本报告最严重的技术缺陷）

**风险描述**：这是本系统唯一一处"**接受公网匿名注册用户上传的任意二进制文件，并由服务端进程主动深度解析它**"的位置。已逐份核实：

- 03 §8 R2：7 条缓解措施，全部关于**稳定性**（超时、串行队列、独立 profile、僵死进程清理、降级、下载原件、重试）；
- 06 §5.1.4：整节标题是"LibreOffice **并发安全**问题"，内容是 profile 锁争抢；
- 01 §R1：同样只谈"转换稳定性"；
- 03 §5.1.5 第五道校验后的注释："即便攻击者上传了可执行内容也无法通过 HTTP 触发执行——这是最终防线"。

**这句"最终防线"的推理有一个致命缺口**：它假设攻击者需要"通过 HTTP 触发执行"。但本系统**自己会主动执行解析**——LibreOffice 在上传后数秒内自动打开这个文件。攻击者不需要 HTTP 触发，系统会替他触发。

**五道校验挡不住这类攻击**：恶意文档是**完全合法的 .docx/.doc**——正确的魔数、正确的 ZIP 结构、包含 `word/document.xml`、扩展名与内容一致。五道校验全部通过，因为攻击载荷在文档的**语义层**而非格式层。

**具体攻击场景**（按危害递增，均可复现）：

**场景 A：外部实体/OLE 链接加载 → SSRF + 内网探测 + NTLM 哈希外泄**
1. 攻击者构造一个 .docx，在 `word/_rels/document.xml.rels` 中插入一个指向 `\\attacker.com\share\x.dotx` 的外部模板引用（或 `word/settings.xml` 的 `attachedTemplate`）。
2. 学生账号（公网可自由注册）上传该文件并投递。
3. LibreOffice 转换时解析外部引用，Windows 上的 SMB 客户端会**自动发起认证**，将运行 Spring Boot 的服务账号的 **NTLMv2 哈希**发送到攻击者服务器。
4. 攻击者离线爆破该哈希，或直接做 NTLM Relay。若服务账号是本机 Administrator（03 未定义服务账号权限，WinSW 默认以 LocalSystem 运行），后果是**整机沦陷**。
5. 变体：外部引用指向 `http://192.168.10.1/`、`http://127.0.0.1:8080/api/system/user/list` 等内网地址 → 服务端代替攻击者探测内网、访问被 Nginx 403 掉的后台接口（**因为请求来自 127.0.0.1，绕过了 Nginx 的全部白名单**）。这是本系统四层防御的一个完整穿透路径。

**场景 B：Basic 宏 / DDE 自动执行 → RCE**
1. LibreOffice 的宏安全级别若为默认或被 profile 配置降低，含 `Document_Open` 事件的 Basic 宏可能被执行。
2. .doc（OLE2）格式还支持 DDE 字段，历史上在 Office 与 LibreOffice 上都有自动执行案例。
3. 03/06 **没有任何一处配置宏安全级别**——而每次转换用的是**全新的空 profile**（`-env:UserInstallation=file:///.../loprofile/{taskId}`），即**每次都是 LibreOffice 的出厂默认配置**。出厂默认是否禁用宏取决于版本，不能假设。

**场景 C：解析器内存破坏 CVE → RCE**
LibreOffice 的 .doc/.rtf/.docx 解析器历史上有多个 RCE 级 CVE。本项目将安装 LibreOffice 24.8 并**长期不升级**（03 无任何组件升级机制，只有 §8 R3⑨的"依赖库每季度跑 `mvn dependency-check`"——**那只覆盖 Java 依赖，不覆盖 LibreOffice 这个外部 exe**）。三年运行期内出现可利用 CVE 的概率不低。

**一旦转换进程被控制，攻击者能拿到什么**（这决定了危害等级）：
- `E:\atmoto-recruit\data\attachments\` —— **全部简历原件**；
- `E:\atmoto-recruit\app\config\application-prod.yml` —— **DB 密码 + JWT 双密钥 + 阿里云 AK/SK**（03 §6.4 确认这些都在这个文件里）。拿到 JWT admin 密钥即可**自签任意 HR 身份的 token**，全部权限校验失效；拿到阿里云 AK/SK 可发短信、可能可访问其他云资源；
- `F:\atmoto-recruit-backup\` —— 全部备份（若服务账号可写，可加密勒索）；
- 127.0.0.1:3306 的 MySQL 与 127.0.0.1:8080 的应用 —— 绕过全部网络层防护。

**影响**：**从"公网匿名注册"到"整机与全部数据沦陷"的完整攻击链，且不需要任何 0day（场景 A 用的是文档格式的正常功能）。** 这是本次审计发现的最严重技术缺陷。

**修复方案**（六条，缺一不可，按重要性排序）：

1. **降权运行（最重要，成本最低）**：
   - 创建专用本地账号 `svc-recruit-lo`，**不属于 Administrators**，仅授予：`E:\atmoto-recruit\data\temp\` 与 `data\loprofile\` 的读写、`data\attachments\` 的**只读**、`data\preview\` 的写入、LibreOffice 安装目录的读取执行。
   - **明确拒绝**该账号对 `app\config\`（配置密钥）与 `F:\`（备份）的任何访问。
   - 转换用 `ProcessBuilder` 启动时以该账号身份运行（Windows 上通过预先创建的受限令牌，或最简做法：把 WinSW 服务本身的运行账号设为一个非管理员的专用账号 `svc-recruit`，再对 `app\config\` 单独授权读取——这样即使 Java 进程被控，也不是 SYSTEM 权限）。
   - **03 §4 的目录结构与 §5.3.3 的 NTFS ACL 说明中，当前只定义了 `.my.cnf` 与 `config\` 的 ACL，没有定义服务运行账号本身。必须补。**

2. **禁用外部内容加载（针对场景 A，成本极低）**：
   - 每次转换的独立 profile 目录中，预置一份 `registrymodifications.xcu`，显式设置：
     - `/org.openoffice.Office.Common/Security/Scripting/MacroSecurityLevel` = **3**（Very High，只允许受信任位置的已签名宏，实际等于全禁）
     - `/org.openoffice.Office.Common/Security/Scripting/DisableMacrosExecution` = **true**
     - `/org.openoffice.Office.Common/Security/Scripting/BlockUntrustedRefererLinks` = **true**
     - 关闭 `AutoUpdate`、关闭在线更新检查、关闭崩溃报告上传
   - 实现方式：把这份 xcu 作为项目资源文件，每次创建 `loprofile/{taskId}` 时复制进去（**这与 06 §5.1.4 第 3 点"每次转换传独立 profile"完全兼容，只是把'空 profile'换成'预置了安全配置的 profile'，增量成本约 0.1 人日**）。
   - 命令行追加 `--norestore --nolockcheck --nodefault --nofirststartwizard`，避免恢复上次会话与首次启动向导。

3. **网络层阻断（针对场景 A 的纵深防御，成本极低）**：
   - Windows 防火墙**出站**规则：拒绝 `soffice.exe` / `soffice.bin` 的**全部出站连接**。转换是纯本地操作，不需要任何网络访问。
   - 这一条能挡住场景 A 的全部变体（SMB 哈希外泄、HTTP SSRF、DNS 外带），且不影响任何正常功能。**必须写入 `deploy.bat` 的防火墙规则注册环节**（03 §3.2⑤ 的防火墙表当前只有入站规则，无出站规则）。

4. **资源限制（防 DoS）**：
   - 已有：60 秒硬超时（07 的 C-02 裁决）+ `destroyForcibly()`；
   - **需补**：Windows Job Object 限制转换进程的内存上限（如 1GB）与子进程数。最简替代方案：`OrphanProcessTask`（07 的 N-09 已裁决为 T5，每小时）的判定条件除"运行超 5 分钟"外，**增加"内存占用 > 1.5GB"**一条，立即 kill。
   - **需补**：单个文件解压后大小限制（防 ZIP 炸弹）——docx 本质是 ZIP，10MB 的 ZIP 可解压出数 GB。第 3 道魔数校验在检查 `word/document.xml` 条目时，**同时读取 ZIP 条目声明的解压后总大小，> 100MB 直接拒绝**（这是在校验环节就能免费拿到的信息）。

5. **版本管理（针对场景 C）**：
   - 03 §8 R3⑨ 的季度依赖扫描**明确扩展到 LibreOffice 本体**：运维手册增加一条季度动作"检查 LibreOffice 是否有安全更新，有则在测试实例验证后升级生产"。
   - 部署清单记录当前安装版本号，写入 `doc\部署手册.md`。

6. **失败即安全**：转换失败时，`preview_status=FAILED` 的降级路径已完备（mammoth.js / 下载原件）。**追加一条**：若同一学生上传的文件连续 3 次触发转换进程异常退出（非超时的崩溃），**将该学生账号标记并告警**——这是场景 C 的探测行为特征。

**修复成本**：1.2 人日（专用账号与 ACL 0.4 + 安全 profile 预置 0.2 + 防火墙出站规则 0.1 + 资源限制与 ZIP 炸弹校验 0.3 + 文档与运维手册 0.2）
**是否阻塞上线**：**是**

### S-15　转换进程与应用进程共享权限上下文（中危，阻塞，与 S-14 配套）

**风险描述**：即使 S-14 的第 1 条降权做了，仍存在一个前置问题：**03 从未定义 Spring Boot 服务本身以什么账号运行**。

已核实 03 §5.5 第 4 项："Spring Boot 注册为 Windows 服务，配置 `onfailure restart`、开机自启、日志轮转"，以及 §4 的 `recruit-service.xml`（服务定义：自动重启、JVM 参数）——**没有一处提到服务账号**。WinSW 默认以 `LocalSystem` 运行，这是 Windows 上权限最高的账号（高于 Administrator）。

**具体后果**：
- LibreOffice 作为 Java 进程的子进程，继承 `LocalSystem` 权限；
- 即使按 S-14 配置了 ACL，`LocalSystem` 可以绕过大部分 ACL（它对本机几乎无限制）；
- 任何 Java 层的 RCE（依赖库 CVE、反序列化）后果同样是整机沦陷；
- MySQL 若也以默认账号运行，同理。

**修复方案**：
1. `recruit-service.xml` 显式配置 `<serviceaccount>` 为专用本地账号 `svc-recruit`（非 Administrators 成员），并授予：
   - `E:\atmoto-recruit\` 全目录读写（业务数据与日志）；
   - `E:\atmoto-recruit\app\config\` **只读**；
   - `F:\atmoto-recruit-backup\` **无权限**（备份由任务计划以另一账号执行，防勒索横向）；
   - "作为服务登录"权限（`SeServiceLogonRight`）。
2. MySQL 服务同样使用专用账号（官方 MSI 安装时默认创建 `NT SERVICE\MySQL80`，已足够，只需确认未改为 LocalSystem）。
3. Nginx 的 WinSW 包装同样指定专用账号。
4. **写入 03 §4 目录结构的"三条硬约束"之后，新增第 4 条硬约束**：「三个 Windows 服务（Spring Boot / MySQL / Nginx）**一律不得以 LocalSystem 或 Administrator 运行**，各自使用专用受限账号。部署验收必须用 `sc qc` 与任务管理器"用户名"列实测确认。」

**修复成本**：0.3 人日

### S-18　MIME 校验依赖客户端提供的 Content-Type，是无效校验（中危）

**风险描述**：05 §4.2 的第 2 道校验是"请求头 `Content-Type` 校验"。multipart 上传中，每个 part 的 `Content-Type` **完全由客户端指定**，攻击者用 curl 可任意设置。这一道校验对攻击者的成本是零。

03 §5.1.5 的表述更准确（第 4 道"三者（声明扩展名、Content-Type、magic）必须一致"），把 Content-Type 作为**一致性交叉验证**的一个因子而非独立防线，这是正确用法。

**影响**：不构成独立漏洞（因为魔数校验才是真防线），但会给实现者与验收者**虚假的安全感**——"我们有 MIME 校验"。若魔数校验因故弱化，MIME 校验不会提供任何补偿。

**修复方案**：05 §4.2 的校验表中，"MIME"一行的说明改为「**Content-Type 由客户端提供，不可信，仅作为一致性交叉验证的一个因子。真正的类型判定以第 3 道魔数嗅探为准**」，并把 03 的第 4 道（三者一致性）补入 05。同时把 05 的第 3 道升级为 03 的完整版（含 ZIP 条目检查）。

**修复成本**：0.1 人日（文档修正 + docx 的 ZIP 条目检查实现）
**是否阻塞上线**：否（但**必须以 03 的五道为准而非 05 的四道**，这一点需写入 07 的修改指令）

### S-19　Nginx 12m 与业务 10MB 之间的 2MB 缝隙（低危）

**风险描述**：03 §5.1.5 第 1 道：Nginx `client_max_body_size 12m` + Spring `max-file-size=10MB` + 业务层再判。12m 的余量是为 multipart 边界预留的，合理。但意味着 **10–12MB 的请求会被 Nginx 放行、由 Spring Boot 接收并缓冲后才拒绝**。

**场景**：攻击者持续发送 11.9MB 的上传请求。每个请求都要经过 TLS 解密 + Nginx 缓冲 + 代理转发 + Spring multipart 解析后才被拒。20 个并发即可占满带宽与磁盘 IO（Spring 的 multipart 默认超过 `file-size-threshold` 会写临时文件到磁盘）。

**影响**：轻量 DoS。在家宽/办公宽带上行带宽有限的场景下，几个并发即可影响正常学生上传。

**修复方案**：
1. `spring.servlet.multipart.file-size-threshold` 显式设为 `0`（全部走磁盘，避免堆内存放大），并把临时目录指向 `E:\atmoto-recruit\data\temp\`（03 §4 已有该目录，但未与 Spring 配置关联）。
2. Nginx 侧 `client_max_body_size` 从 12m 降到 **11m**（multipart 边界开销实际只有几百字节，2MB 余量过大）。
3. 上传接口单独限流：`location ^~ /api/portal/resume/upload { limit_req zone=upload_api rate=6r/m burst=3; limit_conn perip 2; }`——正常学生一次投递上传 1–2 个文件，6 次/分钟绰绰有余。**当前 03 §3.2⑥ 只有 `portal_api` 一个 10r/s 的通用区，上传接口未单独限流。**

**修复成本**：0.1 人日
**是否阻塞上线**：否

### S-20　上传目录 Nginx 隔离与路径穿越（S-25 见公网章节；此处核实路径构造）

**核实结论**：**路径穿越的根本防护是有效的。** 已核实 03 §5.1.4："URL 中只出现附件的数据库 ID，永不出现文件路径或文件名。防目录穿越的根本手段是'路径由服务端从 DB 拼装'，而非'过滤 `..`'。" 以及第五道校验"存储名 = UUID + 规范化扩展名（从内容嗅探结果推导，不用用户提供的）"。

**但有两个残留点需要补**：
1. **DB 中的路径值本身可能被污染**。07 的 N-07 裁决"DB 中存储的路径为相对路径 `attachments/2026/08/{uuid}.pdf`"。若未来有任何代码路径允许写入这个字段（如数据迁移脚本、导入功能），污染值（如 `../../app/config/application-prod.yml`）会被服务端直接拼接读取。**修复**：读取前对 DB 取出的相对路径做规范化校验——`Path.normalize()` 后必须仍以 `attachments/` 或 `preview/` 或 `brand/` 开头，否则拒绝并记 ERROR。成本 0.05 人日，是一条廉价的纵深防御。
2. **下载时的文件名注入**。03 第五道已要求"下载时做 RFC5987 编码并剥离控制字符、换行、路径分隔符"——**已核实这一条是完备的**（覆盖了 `Content-Disposition` 头注入与 CRLF 注入）。05 §4.6 只写了"UTF-8 编码"，**缺少剥离控制字符的要求，需补齐到 03 的水平**。

**修复成本**：0.15 人日
**是否阻塞上线**：否（中低危），但 ZIP Slip 建议随 S-12 一起修

### S-26　简历文件静态加密：本报告的裁决（中危，不阻塞）

**问题**：简历文件是否需要静态加密（at-rest encryption）？

**核实现状**：04 与 03 均无任何静态加密设计。简历原件以明文 PDF/DOCX 存放于 `E:\atmoto-recruit\data\attachments\`，备份同样明文存放于 `F:\` 与离线移动硬盘。

**威胁分析**（区分三种威胁，结论不同）：

| 威胁 | 应用层加密（AES 加密文件内容）是否有效 | 全盘加密（BitLocker）是否有效 |
|---|---|---|
| 磁盘/整机被物理窃取 | ✅ 有效 | ✅ **有效且成本更低** |
| **离线移动硬盘丢失**（03 要求每周人工插拔并拔下存放） | ✅ 有效 | ✅ **有效**（BitLocker To Go） |
| 应用进程被攻破（S-14 场景） | ❌ **无效**——密钥在应用配置里，攻击者拿到进程即拿到密钥 | ❌ 无效 |
| 数据库被拖库（简历元数据） | 不适用 | ❌ 无效 |
| 运维人员/IT 人员越权翻看文件 | ✅ 有效 | ❌ 无效（登录后透明解密） |

**裁决**：**不做应用层文件加密，改做全盘加密 + 离线盘加密。**

理由：
1. **应用层加密对本项目最现实的威胁（S-14 应用被攻破、内部 HR 越权）几乎无效**——密钥必须对应用可用，应用被攻破即密钥失守。它只对"物理窃取"有效，而这一点 BitLocker 做得更好且成本低一个数量级。
2. 应用层加密会**破坏两个已有设计**：① LibreOffice 需要读明文文件才能转换，意味着每次转换要先解密到临时目录，临时明文文件成为新的泄露点；② `robocopy` 增量备份对加密文件仍可工作，但**备份的完整性校验（03 §5.3.1 的 SHA256）与恢复演练都要增加解密环节**，在无专职运维的场景下每增加一个环节就多一分恢复失败的概率。
3. 成本对比：应用层加密约 1.5 人日（加密解密封装 + 临时文件管理 + 密钥轮换预案 + 备份恢复链路适配）；BitLocker 约 **0.2 人日**（开启 + 恢复密钥托管到甲方 IT + 写入运维手册）。

**具体要求**（写入部署清单）：
1. **`E:` 与 `F:` 两块数据盘开启 BitLocker**，恢复密钥由甲方 IT 保管（**不得存放在本机**），密钥保管方式写入 `doc\应急联系人.md`。
2. **离线移动硬盘必须用 BitLocker To Go 加密**——这是最容易丢失的介质（每周人工插拔、拔下后随手存放），且它承载的是**完整的简历库副本**。03 §5.3.1 定义了离线副本机制但**没有任何加密要求**，这是一个实质缺口。
3. 系统盘 `C:` 同样建议开启（配置文件的临时副本、Windows 页面文件可能含敏感数据）。
4. **风险提示（必须向甲方明示）**：BitLocker 恢复密钥丢失 = 数据永久不可读。密钥托管必须有书面流程与至少两处保存（IT 主管 + 公司保险柜/密码管理器）。

**修复成本**：0.2 人日
**是否阻塞上线**：**离线硬盘加密（0.1 人日）阻塞**——因为离线副本一旦启用就立刻承载全量简历，且它是最易丢失的介质。`E:`/`F:` 的 BitLocker 可上线后开启（需停机，可安排在首个维护窗口）。

## 四、公网暴露面

### S-21　RuoYi 原生路径不在任何黑名单内（高危，阻塞）

**风险描述**：07 的 N-01 与 N-11 已识别这一点并给出了修改指令（"03 §3.2⑥ Nginx 配置黑名单区补入 `/login`、`/getInfo`、`/getRouters`、`/captchaImage` 四条"）。本报告**确认该修复必要**，并指出 **07 对影响面的评估偏低**。

07 的 N-11 原文判断："虽然不会真的泄露后台功能（因为 `try_files` 不会代理到 8080），但如果实现者为了让后台工作而在公网 vhost 加了 `/login` 的 proxy_pass，HR 登录接口就直接暴露公网。"

**这个评估遗漏了三点**：

1. **`try_files $uri $uri/ /index.html` 的实际行为是返回门户首页 HTML（HTTP 200）**，不是 404。攻击者请求 `https://campus.atmoto.cn/getRouters` 得到一个 200 的 HTML 页面——这**不会**让攻击者判定"此路径不存在"，反而与门户的任意不存在路径行为一致，属于无信息。这一点 07 判断正确。
2. **但 `/captchaImage` 是个特例**：若实现者按 N-11 裁决用 RuoYi 原生路径，而**学生端注册也需要图形验证码**（03 §5.1.6 第 1 层防刷），则 `/captchaImage` **必须在公网可达**。此时它与 HR 登录用的是**同一个接口**。攻击者可无限调用它（无限流），既是 S-05 的绕过前提，也是一个免费的资源消耗点（Kaptcha 生成图片有 CPU 开销 + 每次生成一条 Caffeine 缓存条目 → **可打满 Caffeine 的 maxSize 导致正常用户的验证码被驱逐**）。
   → **必须为学生端单开一个 `/api/portal/captcha`**，与 HR 端的 `/captchaImage` 分离，前者公网放行 + 限流，后者黑名单 403。**07 的 N-01 重映射表把 `/api/common/captcha` 映射到了 RuoYi 原生 `/captchaImage`，这个裁决在安全上是错的，需推翻。**
3. **`/login` 若被 403，学生端会不会受影响**：不会（学生端登录是 `/api/portal/auth/login`）。但**门户前端的 SPA 路由很可能有 `/login` 这个前端路由**（学生登录页）。此时 Nginx 的 `location ^~ /login { return 403; }` 会**拦截学生访问自己的登录页**——学生点"登录"按钮，浏览器直接导航到 `https://campus.atmoto.cn/login`，得到 403 而非登录页。**这是一个必然发生的功能性冲突，07 未识别。**

**具体失败场景（第 3 点，必现）**：
1. 按 07 的 N-01 指令在公网 vhost 加 `location ^~ /login { return 403; }`。
2. 学生打开门户首页，点"登录/注册"，Vue Router 跳转到 `/login`。
3. SPA 内部跳转不发请求，页面正常显示。
4. 学生**刷新页面**（或从微信分享的登录链接直接打开）→ 浏览器向服务器请求 `/login` → **403**。
5. 现象：登录页时好时坏，取决于是否刷新过。排查成本高。

**修复方案**：
1. **不要用路径黑名单拦 RuoYi 原生接口**——改用**精确匹配**（`location = /login`），只拦 POST 到该路径的 API 请求，不影响 SPA 路由。但 `location = /login` 同样会拦住 SPA 的 GET。**正确做法**：
   - 学生门户的 SPA 登录路由改为 `/signin`（或 `/auth/login`），**避开 `/login`**，从源头消除冲突。这是零成本的命名调整，必须在 05 §5.1 的页面路由表中落实。
   - 然后 Nginx 公网 vhost 用 `location = /login { return 403; }`、`location = /getInfo { return 403; }`、`location = /getRouters { return 403; }`（精确匹配，不影响其他路径）。
2. **`/captchaImage` 拆分**（推翻 07 的 N-01 相关映射）：
   - HR 端：`/captchaImage`（RuoYi 原生）→ 公网 **403**；
   - 学生端：新增 `GET /api/portal/captcha` → 公网放行，`limit_req zone=captcha_api rate=20r/m burst=10`，且**Caffeine 缓存独立于 HR 端**（避免互相驱逐）。
   - 成本：0.1 人日（复用 Kaptcha 的生成逻辑，只是换一个 Controller 入口与缓存 key 前缀）。
3. **更根本的做法（推荐并行实施）**：公网 vhost 改为**白名单模式**——见 S-23。

**修复成本**：0.2 人日
**是否阻塞上线**：**是**

### S-23　Nginx 白名单可被绕过，且当前是"黑名单为主"的错误模式（高危，阻塞）

**风险描述**：03 §3.2⑥ 的配置结构是：
```
location ^~ /api/portal/ { ... proxy_pass ... }   # 白名单 1 条
location ^~ /api/admin/  { return 403; }          # 黑名单 6 条
location ^~ /api/system/ { return 403; }
location ^~ /actuator/   { return 403; }
location ^~ /druid/      { return 403; }
location ^~ /swagger     { return 403; }
location ^~ /v3/api-docs { return 403; }
location / { try_files $uri $uri/ /index.html; }  # 兜底：静态
```

这个结构的安全性依赖于"我们列全了所有该拦的路径"。**每次新增一个后台功能，都要记得加一条黑名单**——这是持续的、容易遗忘的负担，S-21 的四条遗漏就是明证。

**具体绕过场景（逐个核实 Nginx 行为）**：

| 绕过手法 | 请求 | Nginx 实际行为 | 是否绕过 |
|---|---|---|---|
| URL 编码 | `/%61pi/admin/job/list` | **Nginx 在 location 匹配前会对 URI 解码**（`$uri` 是解码后的），故命中 `^~ /api/admin/` → 403 | ❌ 不绕过 |
| 双重编码 | `/%2561pi/admin/...` | 解码一次得 `/%61pi/admin/...`，不匹配 `/api/admin/` → 落入 `location /` → 返回 index.html（200 HTML），**不代理到后端** | ❌ 不绕过（但产生噪音） |
| 路径穿越 | `/api/portal/../admin/job/list` | **Nginx 默认会规范化路径**（合并 `..`），规范化后为 `/api/admin/job/list` → 命中 403 | ❌ 不绕过 |
| **多斜杠** | `//api/admin/job/list` | **`merge_slashes` 默认为 on**，合并后为 `/api/admin/...` → 403 | ❌ 不绕过（**但若有人为了某个需求关掉 `merge_slashes`，立刻绕过**） |
| 大小写 | `/API/ADMIN/job/list` | **`location ^~` 是大小写敏感的**！`/API/ADMIN/` **不匹配** `^~ /api/admin/` → 落入 `location /` → **返回 index.html，不代理** | ❌ 不绕过（因为兜底是静态而非代理） |
| **分号/参数污染** | `/api/portal/;/api/admin/job/list` | `;` 在 URI 路径中是合法字符，`$uri` = `/api/portal/;/api/admin/job/list` → 命中 `^~ /api/portal/` → **代理到后端**，Spring 收到的路径是 `/api/portal/;/api/admin/job/list` → Spring 的 `AntPathMatcher` 不会匹配任何 admin 接口 → 404 | ❌ 不绕过 |
| **尾部空字节/换行** | `/api/admin/job/list%00` | 解码后含 `\0`，Nginx 通常直接 400 | ❌ 不绕过 |

**核实结论：当前配置在 Nginx 语法层面是稳固的，上述七种常见绕过手法都不成立。** 这一点必须如实记录，不做夸大。

**但真正的风险不是语法绕过，而是三个结构性问题**：

1. **黑名单的完备性依赖人工**。S-21 已证明遗漏会发生（RuoYi 原生四路径）。未来任何新增的非 `/api/portal/**` 路径（如某个第三方回调、某个健康检查端点、Spring Boot 的 `/error`）默认落入 `location /`，返回 index.html——**看起来安全（不代理），但一旦有人为某个需求加了一条 `proxy_pass` 到根路径的规则，全部后台接口瞬间暴露**。这不是假设：`location / { try_files ... }` 改成 `location / { try_files $uri $uri/ @backend; }` 是一个非常常见的 SPA+API 同域配置写法。

2. **`merge_slashes` 未显式声明**。默认 on，但若未来因某个 URL 编码需求关闭（这是有真实场景的，如需要保留路径中的 `//`），`//api/admin/` 立即绕过全部黑名单。**默认值不应作为安全依赖，必须显式写死。**

3. **`location /` 的兜底是静态目录，若门户目录下意外出现敏感文件即被 serve**。见 S-25。

**修复方案（把黑名单模式改为白名单模式）**：
```nginx
server {
    listen 443 ssl http2;
    server_name campus.atmoto.cn;
    root E:/atmoto-recruit/web/portal;

    merge_slashes on;          # 显式声明，不依赖默认值
    server_tokens off;         # 见 S-27
    if ($request_method !~ ^(GET|POST|PUT|PATCH|DELETE|HEAD)$) { return 405; }

    # —— 唯一放行的 API 前缀（白名单）——
    location ^~ /api/portal/ {
        limit_req  zone=portal_api burst=20 nodelay;
        limit_conn perip 10;
        proxy_pass http://127.0.0.1:8080;
    }

    # —— 上传接口单独限流（S-19）——
    location = /api/portal/resume/upload {
        limit_req  zone=upload_api burst=3 nodelay;
        limit_conn perip 2;
        client_max_body_size 11m;
        proxy_pass http://127.0.0.1:8080;
    }

    # —— 短信接口单独限流（S-05）——
    location = /api/portal/auth/send-code {
        limit_req  zone=sms_api burst=20 nodelay;
        proxy_pass http://127.0.0.1:8080;
    }

    # —— 关键：任何以 /api 开头但不是 /api/portal/ 的请求，一律 403 ——
    # 这一条使黑名单不再需要穷举，新增后台接口自动被拦
    location ^~ /api/ { return 403; }

    # —— RuoYi 原生固定路径（精确匹配，不影响 SPA 路由）——
    location = /login       { return 403; }
    location = /getInfo     { return 403; }
    location = /getRouters  { return 403; }
    location = /captchaImage{ return 403; }
    location = /logout      { return 403; }
    location ^~ /actuator/  { return 403; }
    location ^~ /druid/     { return 403; }
    location ^~ /swagger    { return 403; }
    location ^~ /v3/api-docs{ return 403; }
    location = /error       { return 403; }

    # —— 静态资源：只允许已知扩展名 ——
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|webp|woff2?|ttf|map)$ {
        expires 7d;
        add_header Cache-Control "public";
    }

    # —— SPA history 回退 ——
    location / { try_files $uri $uri/ /index.html; }
}
```

**关键改动是 `location ^~ /api/ { return 403; }` 这一行**——它把"穷举所有该拦的"变成"只放行明确允许的"。加上它之后，S-21 的遗漏、以及任何未来新增的后台接口，都会被自动拦住，**黑名单从"安全防线"降级为"可读性注释"**。

**修复成本**：0.4 人日（配置重写 0.15 + 逐条实测验证 0.25）
**是否阻塞上线**：**是**

### S-24　纵深防御的三个前提未被验收覆盖（中危）

**核实结论**：`server.address=127.0.0.1` + `bind-address=127.0.0.1` + 路由器只映射 80/443 的纵深防御**设计上成立**（已核实 03 §3.2③ L3 层与 §3.2⑤ 端口表）。这是本方案性价比最高的两行配置，判定有效。

**但成立依赖三个前提，全部未被验收覆盖**：

1. **路由器映射规则由甲方 IT 配置，不在交付范围内**。03 §3.2 的拓扑图标注"★ 仅映射 TCP 443 与 80"，但这是**对甲方的要求，不是本系统能保证的**。若甲方 IT 为了远程运维顺手映射了 3389（远程桌面）——03 §3.2⑤ 的端口表虽写了"3389 绝对不映射"，但**没有任何验收动作去确认它**。
   → **验收必须包含：从公网对公司出口 IP 做一次全端口扫描**（1-65535），确认只有 80/443 开放。这是唯一能证明 L1 层成立的方法。
2. **`server.address=127.0.0.1` 可能被误配**。若 `application-prod.yml` 中该行缺失或被注释，Spring Boot 监听 `0.0.0.0:8080`，此时**内网任意机器可直连 8080 绕过 Nginx 的全部白名单**（内网机器被钓鱼后即可访问全部 admin 接口，无需 VPN 无需 Nginx）。
   → 验收：从**内网另一台机器**（不是本机）执行 `curl http://192.168.10.50:8080/api/admin/...`，必须连接被拒。**注意：从本机 curl 127.0.0.1:8080 会成功，这不能证明配置正确，必须从另一台机器测。**
3. **两个 JWT 密钥必须不同且非示例值**。03 §6.4 要求首次部署时随机生成，但无验收动作。若实现者图省事让两端共用一个密钥，S-13 的"结构性阻断"立即失效——学生 token 可通过 admin 链验签，此时唯一防线退回到"每个接口都写对 `@PreAuthorize`"，而 05 中**确实有接口只标了权限点没标数据范围**（S-06）。
   → 验收：`grep` 生产配置文件确认两个密钥值不同、长度 ≥32 字节、且不等于仓库 template 中的示例值。

**修复成本**：含在验收清单（0.2 人日）
**是否阻塞上线**：**是**（三条实测都必须通过）

### S-25　上传目录与 Nginx root 的隔离仅靠约定（高危，阻塞）

**风险描述**：03 §4 硬约束 1："`data\` 绝不能位于任何 Nginx `root` 之下——这是'附件不可被直接遍历访问'的物理保证。"

**核实结论：设计正确。** 公网 vhost 的 `root` 是 `E:/atmoto-recruit/web/portal`，`data\` 在 `E:/atmoto-recruit/data`，两者是兄弟目录，`data\` 确实不在 root 之下。**这一条已核实成立。**

**但风险在于"约定"没有强制机制**：
1. `deploy.bat` 若未来加入"把某些资源复制到 web 目录"的逻辑（如品牌素材 logo/banner——**这是很可能发生的**，因为门户首页要显示 logo，最省事的做法就是把 `data\brand\logo.png` 复制到 `web\portal\`），则品牌目录会进入 root。品牌素材本身不敏感，但这个操作会**建立一个"data 里的东西可以复制到 web 里"的先例**。
2. Nginx 的 `location /` 兜底 `try_files $uri $uri/ /index.html`——若 `web\portal\` 下意外出现了任何文件（部署脚本的临时文件、`.env`、`application-prod.yml` 的误拷贝、`.git` 目录、source map），**全部可被公网直接下载**。
3. **`autoindex` 未显式关闭**。Nginx 默认 `autoindex off`，但与 `merge_slashes` 同理——默认值不应作为安全依赖。

**具体攻击场景**：
1. 攻击者请求 `https://campus.atmoto.cn/assets/`、`/.git/config`、`/config/`、`/application-prod.yml`、`/index.html.bak`、`/*.map`。
2. 前端构建产物默认包含 source map（Vite 的 `build.sourcemap` 默认 false，但很多项目为排障打开）——source map 泄露**完整前端源码**，含全部 API 路径、字段名、以及可能的硬编码常量。
3. 若 `deploy.bat` 在 web 目录留下过任何中间文件，即被下载。

**修复方案**：
1. **Nginx 侧强制**（已含在 S-23 的配置中）：
   - 静态资源 `location` 用**扩展名白名单**（`\.(js|css|png|...)$`），未列出的扩展名不 serve；
   - 显式 `autoindex off;`；
   - 显式拒绝敏感路径：`location ~ /\. { return 404; }`（拦 `.git`/`.env`/`.htaccess`）、`location ~* \.(yml|yaml|properties|bak|log|sql|map)$ { return 404; }`。
2. **部署脚本侧强制**：`deploy.bat` 在部署完成后调用一个 `verify-web-root.ps1`，扫描 `web\portal\` 与 `web\admin\` 目录，若发现白名单扩展名之外的文件（尤其 `.yml`/`.map`/`.bak`/`.git`）→ **部署失败并报错**。这把"约定"变成"部署门禁"，成本 0.1 人日。
3. **前端构建**：`vite.config.js` 显式 `build.sourcemap = false`（生产）。写入 03 §7.2 M6 的范围。
4. **品牌素材的正确做法**：不复制到 web 目录，通过 `GET /api/portal/brand/asset/{type}` 由后端返回流（匿名可访问，加 `Cache-Control: public, max-age=86400`）。这保持了"data 目录绝不进 web 目录"的铁律。**07 的 N-10 已裁决拆出匿名的 `/api/portal/brand` 接口返回配置，此处只需追加素材流接口，成本 0.1 人日。**

**修复成本**：0.2 人日
**是否阻塞上线**：**是**

### S-28　CC/DDoS 防护：现实评估与可执行措施（中危）

**风险描述**：甲方是家宽/办公宽带出口，**无任何高防能力**。已核实 03 的限流设计只有三个 zone（`portal_api` 10r/s、`sms_api` 1r/m、`limit_conn perip`）。

**必须如实说明的边界**：
- **应用层 CC 攻击**（大量合法 HTTP 请求）：Nginx `limit_req`/`limit_conn` **能有效缓解**，因为攻击流量在 Nginx 就被拒，不消耗后端资源。
- **网络层 DDoS**（SYN flood、UDP flood、带宽打满）：**本方案完全无防护能力，且无法在单机上解决**。办公宽带上行通常 20–100Mbps，一次 1Gbps 的攻击即可打满，此时**连 Nginx 都收不到包**，任何服务端配置都无意义。
- 03 §8 R3 把"DDoS"列在风险中，缓解措施⑦是"每月人工巡检 access.log"——**这是事后发现手段，不是防护**。文档没有对"无法防护网络层 DDoS"这一事实做明示。

**具体场景**：竞争对手或恶意学生在宣讲会当天（岗位投递截止前夜）发起一次几百 Mbps 的攻击 → 公司整个办公网络瘫痪（不只是招聘系统，**全公司断网**，因为共用同一条出口）→ 校招投递中断 + 公司业务中断。

**修复方案**（分层，全部可执行）：

1. **应用层 CC（可防，必做）**：
   - 现有三个 zone 保留，**补充四个**：`upload_api`（6r/m，S-19）、`captcha_api`（20r/m，S-21）、`login_api`（`= /api/portal/auth/login` 与 `/register`，10r/m）、`export_api`（内网 vhost，`= /api/admin/resumes/export` 2r/m，防内部误操作导致的大导出堆积）。
   - `limit_conn perip 10` 保留；追加 `limit_rate_after 2m; limit_rate 512k;`（单连接下载限速，防单个 IP 拖慢附件下载通道）。
   - `client_body_timeout 15s; client_header_timeout 10s; send_timeout 20s;`（防慢速攻击 Slowloris）。**03 当前未配置任何超时，Nginx 默认 60s，对慢速攻击不友好。**
   - `keepalive_requests 100; keepalive_timeout 30s;`

2. **网络层 DDoS（不可防，必须明示 + 准备预案）**：
   - **在交付文档中显式写明**：「本方案对网络层 DDoS 攻击**无防护能力**。攻击发生时公司整体网络（不仅招聘系统）将受影响。这是'单机 + 家宽/办公宽带'部署形态的固有限制，非本系统设计缺陷。」
   - **预案 1（推荐，成本可控）**：域名 DNS 托管到具备免费 CDN/WAF 的服务商（Cloudflare 免费版或阿里云 DCDN），**仅在遭受攻击时切换**。平时 DNS 直指公司 IP（保持"数据不出内网"），攻击时切到 CDN 回源。**注意**：这会引入 07 的 C-09 中已论证过的"第三方中间人"问题（简历数据经第三方链路），因此**只作为攻击时的应急降级，不作为常态**，且必须在切换前经甲方书面同意。预案写入 `doc\应急联系人.md`，DNS TTL 平时设为 **300 秒**（当前无定义，若为默认 86400 则切换要等一天，预案失效）。
   - **预案 2**：07 的 C-09 已设计的"方案 C（云主机纯反代 + WireGuard 回连）"**天然具备抗 DDoS 能力**（云主机有云厂商基础防护，且公司 IP 不暴露）。若甲方公网出口条件本就受限而触发方案 C，此风险自动缓解。**这一点应写入 C-09 方案 C 的收益列——07 只论证了它解决端口封禁问题，未提及它同时解决 DDoS 暴露问题。**
   - **预案 3（零成本）**：`campus.atmoto.cn` 与公司主域 `atmoto.cn` **必须使用不同的出口 IP** 或至少确认攻击招聘系统不会影响公司主站。若共用同一 IP，一次针对招聘系统的攻击会连带打掉公司官网与邮件。**这一点必须在 C-09 的"公网出口确认"三件事中追加为第四件事。**

3. **告警**：`healthcheck.ps1`（每 5 分钟）增加一项——统计 Nginx access.log 最近 5 分钟的请求数，超过阈值（如 3000）触发告警邮件。成本 0.05 人日，是唯一能让甲方在攻击开始 5 分钟内知情的手段。

**修复成本**：0.4 人日（限流 zone 扩展与超时配置 0.2 + 预案文档与 DNS TTL 0.1 + 告警 0.1）
**是否阻塞上线**：否（中危），但**DNS TTL 设为 300 秒**与**确认招聘域名与公司主站不共用 IP**两项属零成本且必须上线前完成

### S-29　证书自动续期失败的后果与兜底（中危）

**风险描述**：已核实 03 §3.2③ 选型 win-acme + Let's Encrypt，`healthcheck.ps1` 每日检查剩余有效期，< 20 天告警。**设计基本合理**。但存在三个未覆盖的失败模式：

1. **HTTP-01 验证依赖 80 端口可达**。若运营商在项目中期封禁 80（国内宽带常见的政策变动），续期会**静默失败**——win-acme 的续期任务在后台运行，失败只写它自己的日志。`healthcheck.ps1` 的"剩余 < 20 天告警"能发现，但这时只剩 20 天窗口，且**如果没人看告警邮件**（无专职运维），90 天后证书过期 → **门户全站不可访问，学生看到浏览器红色警告页**。
2. **证书过期的后果被低估**。03 §8 R3 把它列入风险，但缓解措施只有"自动续期 + 20 天告警"。**没有说明过期后如何在 1 小时内恢复**——而校招季的每一天都关键。
3. **Let's Encrypt 速率限制**：同一域名每周最多 5 张证书。若续期脚本因配置错误反复重试，会触发限制，届时**即使修好了配置也要等一周**。

**修复方案**：
1. **HTTP-01 改为 DNS-01**（03 已提到这是备选，本报告建议**直接作为首选**）：域名 `atmoto.cn` 在阿里云，win-acme 有阿里云 DNS 插件。DNS-01 **不依赖 80 端口**，从根本上消除失败模式 1，且为将来可能的 80 端口封禁提前免疫。成本：0.1 人日（配置一个 AK/SK，权限仅限该域名的 DNS 记录修改）。
2. **告警升级**：`healthcheck.ps1` 的证书检查改为**三级**——剩余 < 30 天：日报中提示；< 20 天：邮件告警；**< 7 天：邮件 + 短信告警给 IT**（复用 03 §5.5 的 P0 级短信通道）。当前只有单级邮件告警，在无人看邮件的场景下无效。
3. **应急预案写入 `doc\应急联系人.md`**：证书已过期时的 30 分钟恢复步骤——① 手动执行 `wacs.exe --renew --force`；② 若失败，临时启用一张阿里云免费 DV 证书（**提前申请一张备用证书并保存在 `app\config\` 下，有效期 3 个月，到期随季度巡检更换**）；③ 替换 Nginx 证书路径并 `nginx -s reload`。**提前准备备用证书这一条是关键**——它把恢复时间从"申请+验证+部署 = 数小时"压到"改配置 reload = 5 分钟"。
4. **HSTS 的陷阱**：03 §3.2③ 说"HSTS 先 `max-age=300` 观察 1 周，稳定后调 `max-age=31536000`"。但 §3.2⑥ 的配置示例里**直接写的就是 `max-age=31536000`**（已核实 03:566）——两处矛盾。**必须按 §3.2③ 的渐进式执行**：因为一旦下发了 1 年期的 HSTS，证书过期时学生浏览器**无法点击"继续访问"**（HSTS 会强制阻断），门户变成 100% 不可访问且用户无法绕过。这使证书过期的后果从"用户看到警告但可继续"升级为"完全不可用"。**在证书续期机制被验证稳定运行至少 2 个月之前，`max-age` 不得超过 86400（1 天）。**

**修复成本**：0.3 人日
**是否阻塞上线**：**部分**——HSTS 的 `max-age` 修正（0 成本）必须上线前完成，其余可后续优化

## 七、给编排器的三条结论

1. **本报告发现的 S-06（HR 间数据级越权）应当被视为与 07 报告的 6 个 Critical 同级**。它不是"设计不够完善"，而是"需求 A-003 要求的权限管理在设计中只实现了菜单/按钮级，数据级为零"，且 03 §7.2 M5 验收标准第③条会必然失败。07 的 N-06 识别了字段缺失，但未识别接口层的 17 处约束全部缺失。

2. **本报告推翻 07 的一处裁决**：N-01 重映射表中"`/api/common/captcha` → RuoYi 原生 `/captchaImage`"。理由：该路径必须同时服务公网学生端与内网 HR 端，与 N-01 自身废除 `/api/common/` 的理由（"一个前缀同时服务两套认证体系，边界不可判定"）完全同构。裁决：**学生端另开 `/api/portal/captcha`，`/captchaImage` 在公网黑名单中 403**。

3. **本报告为 07 的 C-09 方案 C 补充一条收益论据**：云主机纯反代 + WireGuard 回连的方案**同时解决了 DDoS 暴露问题**（公司公网 IP 不再暴露，云主机具备云厂商基础防护）。07 只论证了它解决端口封禁问题。若甲方公网出口条件确实受限，这一附加收益应计入方案 C 的评估。同时，**C-09 的"公网出口确认三件事"应追加第四件：确认招聘域名与公司主站不共用出口 IP**。
