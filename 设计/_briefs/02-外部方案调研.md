# 资料搜集报告：遨天科技校园招聘简历管理系统 — 外部方案调研

> 调研日期：2026-08-06
> 调研范围：开源ATS系统、后台管理脚手架、同类产品功能设计、文档在线预览方案、短信服务商、合规要求

---

## 1. 项目现状基线

### 1.1 已有能力（来自 CLAUDE.md 与需求文档）

- 本项目为从零新建系统，当前无任何已有代码基础
- 甲方（遨天科技）具备内部 IT 运维能力（研发型企业），但无专职运维团队
- 部署形态为单台台式机（Windows 或 Linux），非云端，20 并发以内，数百至数千份简历量级

### 1.2 关键约束（不可协商）

| 约束项 | 具体要求 |
|--------|---------|
| 部署形态 | 单机，非云、非集群、非 K8s |
| 并发规模 | 峰值约 20 并发 |
| 数据规模 | 岗位数十个、简历数百到数千份、附件 <= 10MB |
| 技术成熟度 | 必须成熟稳定、社区活跃、招得到人 |
| 简洁性 | 组件数量最小化，能不加就不加 |
| 可维护性 | 部署/升级/备份需脚本化，一条命令 |
| 中文环境 | 全中文界面，兼容 Windows 中文系统（GBK） |

### 1.3 技术栈（设计简报未限定具体栈，但约束指向）

- 后端：Java（Spring Boot 生态，国内招聘 Java 简历最多）或 Python（Django，开发效率高）
- 前端：Vue 生态（Element Plus / Ant Design Vue）
- 数据库：MySQL / PostgreSQL，单库单表
- 部署：Docker Compose 或单可执行 JAR/Python 包

#### 结论：**不存在可直接套用的成熟中文开源校招 ATS**

检索 Gitee/GitHub 上所有涉及"招聘管理系统"的开源项目后发现：
- OpenCATS 是唯一相对成熟的专用 ATS，但 PHP 技术栈 + 全英文 + UI 老旧，汉化与业务适配成本接近自研
- Gitee 上的 Java 招聘系统基本为毕设/课设级别（如 xcmike/employment），代码质量、安全性、可维护性均不满足企业生产要求
- Odoo Recruitment 需要部署完整 Odoo 实例，对"单机、简洁、20 并发"的场景严重过重

**明确建议：不使用现成 ATS 系统套用，采用"通用后台脚手架 + 自研业务"路线。**

#### 关键发现

**1. JeecgBoot 的协议陷阱（务必注意）**

JeecgBoot 虽然标注 Apache 2.0，但其 LICENSE 文件中明确写了附加条款：

> "允许商用使用，不会造成侵权行为，允许基于本平台软件开展业务系统开发（**在任何情况下，您不得使用本软件开发可能被认为与本软件竞争的软件**）。"

"可能被认为与本软件竞争"是一个非常模糊的表述，存在法律风险。且 JeecgBoot 内置了 AI 平台、BI 报表、工作流引擎、低代码平台、微服务等大量本项目用不到的组件，对单机 20 并发场景严重过重。**明确不推荐**。

**2. RuoYi 系列是 Java 路线的最优解**

- MIT 协议，完全免费商用，无任何附加条款
- 开箱即用的 RBAC 权限模型（用户/角色/菜单/部门/岗位/字典/参数/日志/监控）
- 代码生成器可直接生成 Controller/Service/Mapper/Vue 页面，减少 60%+ CRUD 重复工作
- 社区极其活跃（Gitee Java 区排名前 3），文档齐全，中文优先
- 与 Spring Boot 3.x + JDK 17 兼容，技术栈主流
- 部署轻量：一个 JAR 包 + MySQL 即可运行

**3. Django-Vue-Admin 是 Python 路线的最优解**

- MIT 协议，完全免费商用
- 基于 Django REST Framework，开发效率极高（ORM 成熟、Admin 后台即开即用）
- 如果团队更熟悉 Python，这是比 Java 更好的选择（更少的样板代码）
- 部署非常简单：Python 虚拟环境 + MySQL，甚至可以用 SQLite

**综合推荐：Java 路线用 RuoYi-Vue（前后端分离版），Python 路线用 Django-Vue-Admin。**

### 2.4 Word/PDF 在线预览方案（P0 核心技术难点）

本项目需求：学生上传 Word/PDF 简历附件后，HR 在后台直接在线预览，无需下载。

#### 方案对比

| 方案 | 技术原理 | 优势 | 劣势 | 推荐度 | 适用场景 |
|------|---------|------|------|-------|---------|
| **方案A：纯前端 JS 库直渲** | PDF → pdf.js（Mozilla 官方，Canvas 渲染）；Word → docx-preview 或 @vue-office/docx（JSZip 解压 XML → HTML） | **零后端依赖**，纯前端完成，无需转换服务；部署最简 | Word 复杂格式（表格/公式/页眉页脚/中文竖排）兼容性一般，效果不如原文件 | **PDF: 强烈推荐 / Word: 仅格式简单的简历可用** | 小规模部署，简历格式简单（无复杂排版） |
| **方案B：后端转 PDF + pdf.js 前端渲染（推荐）** | 后端用 LibreOffice headless 将 Word → PDF 转换，前端用 pdf.js 统一渲染 PDF | **最成熟稳定**；统一渲染 PDF 保证显示一致；LibreOffice 开源免费；处理后的 PDF 可缓存复用 | 需后端安装 LibreOffice（Linux 一条命令，Windows 需安装包）；首次转换 1-3 秒；需额外 500MB 磁盘 | **强烈推荐（Word 场景）** | 生产环境，对文档格式保真有要求 |
| **方案C：kkFileView 中间件** | Java Spring Boot 的开源文档预览中间件，内部整合 LibreOffice + pdf.js，提供 REST API | **开箱即用**（启动 JAR 即可）；支持 100+ 格式；14k+ Stars；Apache 2.0 License；有 Docker 镜像；中文文档齐全 | 引入独立服务（额外一个 Java 进程）；占用内存约 512MB+ | **强烈推荐（全格式场景）** | 需要预览多种格式（Word/Excel/PPT/PDF/图片/压缩包） |
| **方案D：第三方预览服务** | 阿里云文档智能、腾讯文档、Office Online Viewer 的 iframe 嵌入 | 零部署 | 内网部署不适用；数据安全风险（简历上传到第三方）；Office Online Viewer 要求公网可访问 URL；付费 | **不推荐** | 仅公网场景且对数据安全无严格要求 |

#### 各方案落地路径

**方案B（LibreOffice + pdf.js）落地步骤：**

1. 部署 LibreOffice（Linux: `apt install libreoffice`；Windows: 下载安装包）
2. 后端调用：`soffice --headless --convert-to pdf input.docx --outdir /output`
3. 前端用 pdf.js 或 vue-pdf-embed 组件渲染生成的 PDF
4. 可选优化：PDF 生成后缓存到本地文件系统，同一文件 MD5 去重

**方案C（kkFileView）落地步骤：**

1. 下载 kkFileView 发行包或 Docker 镜像，启动服务（默认 8012 端口）
2. 业务系统上传文件后，调用 `http://kkfileview:8012/onlinePreview?url=<文件下载地址>`
3. 前端用 iframe 嵌入返回的预览页面
4. 配置 Nginx 反向代理统一对外暴露

**方案A+B 混合（推荐）：**

- PDF 附件 → 直接用 pdf.js 前端渲（零后端转换）
- Word 附件 → 后端 LibreOffice 转 PDF → pdf.js 前端渲染（首次转换后缓存）
- 如果未来需求扩展 Excel/PPT 预览 → 平滑升级到 kkFileView

#### 明确推荐

**本项目推荐：方案A+B 混合（PDF 纯前端 + Word 后端转 PDF + 缓存）。**

理由：
1. 符合"组件最小化"的简洁约束（只引入 pdf.js 一个前端库 + LibreOffice 一个后端工具）
2. 不需要引入 kkFileView 作为独立服务（减少一个进程和内存消耗）
3. 如果后期需要全格式预览，方案 A+B 可无缝升级到方案 C（kkFileView 的核心引擎也是 LibreOffice + pdf.js）
4. LibreOffice 安装简单（Linux 一行命令，Windows 有静默安装包）
5. pdf.js 成熟度极高（Mozilla 维护，GitHub 45k+ Stars）

#### 资质要求与开通流程

1. **第一步：企业实名认证**（1-3 工作日）
   - 需准备：营业执照照片/扫描件、法人身份证照片、企业对公账户信息
   - 遨天科技作为正规企业（已完成工商登记），此项无难点

2. **第二步：申请短信签名**（审核 1-2 工作日 + 运营商报备 5-10 工作日）
   - 签名内容建议：**"遨天科技"**（公司全称或简称，与营业执照一致）
   - 签名类型选择"公司"，通过率最高
   - 需注意：签名必须与认证主体一致，不能用"遨天校招"等与营业执照不一致的名称

3. **第三步：申请短信模板**（审核 < 2 小时）
   - 模板示例：`您的验证码为：${code}，5分钟内有效，请勿泄露。`
   - 模板需包含"遨天科技"签名（系统自动添加）

4. **总计开通周期：预留 15 个工作日**

#### 明确推荐

**推荐阿里云短信。** 理由：与遨天科技可能的阿里云生态已有关系（若已有阿里云账号）；SDK 文档最完善；价格有竞争力；单品发送失败率低。

### 2.6 校招系统的合规参考

#### 2.6.1 《个人信息保护法》下的招聘场景合规要点

| 合规要点 | 具体要求 | 系统设计对应 |
|---------|---------|------------|
| **知情同意** | 收集简历前，需明确告知信息用途并获取用户同意 | 注册/投递页面必须有隐私政策勾选框（默认不勾选），文案示例："我已阅读并同意《隐私政策》和《个人信息收集与使用声明》" |
| **最小必要原则** | 只收集与招聘目的直接相关的信息 | 必填字段仅限：姓名、手机号、教育经历、简历附件。不应要求填写身份证号、家庭住址等敏感信息（除非录用阶段必要，一期不需要） |
| **数据保存期限** | 个人信息保存期限应为"实现处理目的所必要的最短时间"（《个保法》第 19 条） | **行业惯例**：未录用候选人简历保存 **1-2 年**（人才库复用）；已淘汰候选人简历保存 **6 个月-1 年**；已入职员工转人力资源档案系统管理；系统需提供 **定时自动清理 / 匿名化功能** |
| **数据安全** | 采取必要措施防止信息泄露、篡改、丢失 | 传输加密（HTTPS/TLS）、存储加密（密码加盐哈希）、访问控制（RBAC 权限）、操作审计日志（谁在何时看了哪份简历） |
| **用户权利** | 用户有权查询、更正、删除其个人信息 | 学生端"个人信息"页面应提供删除账号/撤销投递/导出数据功能（一期至少预留 API） |
| **合规审计准备** | 2025 年 5 月 1 日起，《个人信息保护合规审计管理办法》正式施行 | 系统设计时保留完整的操作日志，确保能在审计时提供数据处理记录 |

#### 2.6.2 简历数据保存期限的行业实践

| 数据类型 | 建议保存期 | 依据 |
|---------|-----------|------|
| 已录用员工简历 | 转员工档案管理，按劳动法保存（离职后至少 2 年） | 劳动争议仲裁时效 |
| 人才库储备简历（未录用但有潜力） | 1-2 年（需在注册时告知并获得同意） | 行业惯例，符合"最小必要" |
| 已淘汰候选人简历 | 6 个月-1 年 | 《个保法》第 19 条精神 |
| 操作日志 | 不少于 6 个月（等保二级要求） | 网络安全等级保护 |
| 短信验证码发送记录 | 3-6 个月 | 反欺诈与合规追溯 |

#### 2.6.3 隐私政策与告知文案建议

系统需内置可配置的隐私政策页面（支持 HTML），并在以下触点弹出/展示：
- 学生注册页（必须勾选同意）
- 简历投递确认页（再次提示信息用途）
- 页面底部固定链接"隐私政策 & 个人信息保护声明"

## 3. 关键发现

### 3.1 最值得借鉴的方案

**自研 vs 二次开发：明确走"通用脚手架 + 自研业务"路线。**

- **脚手架选型：RuoYi-Vue（Java 路线）或 Django-Vue-Admin（Python 路线）**
  - 两者均为 MIT 协议，完全免费商用
  - 开箱即用：用户/角色/权限/菜单/日志/监控均已内置
  - 一键部署：Java 版一个 JAR + MySQL，Python 版 pip install + MySQL/SQLite
  - 社区活跃，中文文档齐全，招人容易

- **文档预览：方案A+B 混合（pdf.js 纯前端渲 PDF + LibreOffice 后端转 Word → PDF → pdf.js 渲染 + 转换后 PDF 缓存）**
  - 符合"组件最小化"原则
  - 后期可无缝升级到 kkFileView

- **短信服务：阿里云短信**（0.045 元/条，预留 15 工作日开通）

### 3.2 明确不推荐的方案

| 方案 | 不推荐理由 |
|------|----------|
| OpenCATS 套用 | PHP 技术栈、全英文 UI、无校招功能、汉化成本接近自研 |
| Odoo Recruitment | 需部署完整 Odoo 实例，严重过度设计，消耗大量资源 |
| JeecgBoot | Apache 2.0 附加竞业限制条款，法律风险；组件严重过重 |
| SmartAdmin | 开源版不可商用，商业版需授权费 |
| 第三方预览服务（阿里云文档/Office Online） | 简历数据安全风险，内网部署不适用 |
| 纯前端 docx-preview 直渲复杂 Word 简历 | 中文排版、表格、公式兼容性差，无法保证显示保真 |

### 3.3 项目独有的差异化需求（外部方案无法直接覆盖的部分）

1. **航天/硬科技雇主品牌展示**：校招门户需体现航天科技感（深空蓝配色、可配置 Banner/Logo/品牌色），这是通用 ATS 不具备的品牌定制需求
2. **内网部署 + 单机架构**：几乎所有成熟 ATS 都是 SaaS 或集群架构，无法满足"一台台式机、一条命令部署"的约束
3. **硬科技岗位的特殊 JD 格式**：岗位描述可能包含电推进、霍尔推力器、比冲、推力范围等技术参数，需要富文本编辑器和结构化标签支持
4. **涉密行业的数据安全附加要求**：遨天科技涉航天军工，系统需明确"仅处理公开招聘信息"，不得承载涉密内容，需有数据分类标注机制
