## 一、跨设计文档的矛盾点

### C-01 🔴 简历快照 vs 快照自动更新，语义自相矛盾

**冲突来源**：工作流设计（06）第 3 节关于 S-013 的产品结论。

**冲突描述**：
工作流设计同时主张两件事：
1. 投递时生成**简历快照**（冻结投递时点的学生资料）
2. 学生后续修改资料时，「系统自动同步更新已投递的快照（状态仍为 APPLIED / PENDING_SCREEN 时）」

这两条互斥。若快照会被自动覆盖，它就不再是快照，而只是一个到学生资料主表的**引用**——那么"快照"这一设计的存在意义（留证、避免 HR 看到的资料在评审过程中变动、争议时可追溯投递时点内容）全部落空。

**为什么这很重要**：
- ATS 系统做快照的核心目的是**评审一致性与可追溯性**：HR 昨天看到的简历和今天看到的必须是同一份，否则筛选结论无法解释。
- 个人信息保护与劳动争议场景下，"学生投递时提交了什么"是需要能被还原的事实。
- 若允许自动覆盖，会出现一种真实的坏情况：HR 已基于 A 版本资料判定"筛选通过"，学生随后把资料改成 B 版本，记录上却显示 HR 通过的是 B 版本。

**需要裁决的问题**：
1. 快照到底冻结不冻结？
2. 若冻结，学生改了资料想让 HR 看到新版，走什么路径？（撤回重投 / 主动"更新我的投递" / 完全不允许）
3. 需求文档 S-013 原文「同一岗位不可重复投递（**可提示更新简历后重新投递**）」——括号内这句明显暗示甲方**期望存在某种"更新后重投"的路径**，而工作流设计给出的"彻底禁止重复投递"结论可能与甲方原意不符。

**编排层倾向**（供审计参考，非结论）：快照必须冻结；提供显式的「更新我的投递」动作，由学生主动触发生成**新版本快照**，保留历史版本，HR 端标注"该候选人已更新简历（第 N 版）"。这样既满足需求原文括号内的意图，又不破坏快照语义，成本仅多一张快照版本表。

**待核对**：数据架构设计（04）对"简历快照"的表结构设计是否与工作流设计一致。若数据侧设计的是不可变快照表，则两文档已实质冲突，必须统一。

**【核对结果 — 冲突已确认，且双方方案不同】**

数据架构（04）的方案：
- `app_application` 表用 5 个 JSON 字段存快照（snapshot_profile / educations / internships / certificates / activities + snapshot_resume_file）
- 明确声明「快照**不可变**，HR 始终看到投递时刻的版本而非学生最新资料，满足审计合规要求」
- 防重复用 `UNIQUE KEY uk_student_job (student_id, job_id)` 硬约束
- 但「更新简历后重新投递」时：**更新同一条记录**——刷新所有 snapshot_* 字段为最新、`version_no` 递增、status 重置为 PENDING_SCREEN、在 `app_status_history` 追加"学生重新投递"记录

**三方对照**：

| 维度 | 工作流设计（06） | 数据架构设计（04） | 编排层原倾向 |
|---|---|---|---|
| 快照可变性 | 状态为 APPLIED/PENDING_SCREEN 时**自动**同步更新 | 声明"不可变"，但重投时**覆盖**同一行的 snapshot 字段 | 不可变，新增版本行 |
| 触发方式 | 学生改资料即**自动**同步 | 学生**主动**发起"重新投递" | 学生主动 |
| 重复投递 | **彻底禁止**，按钮置灰 | **允许**，走更新同一行 + version_no 递增 | 允许，生成新版本快照 |
| 历史版本 | 无 | `app_status_history` 有流转记录，但**旧版快照内容本身被覆盖丢失** | 完整保留每版快照 |

**关键结论**：
1. 04 与 06 在「是否允许重复投递」上**结论直接相反**——这是必须裁决的硬冲突，不能两个都实现。
2. 04 自称"快照不可变"与其"重投时刷新 snapshot_* 字段"的实现**自相矛盾**：字段被覆盖即不可变性被破坏。它保留的只是流转事件记录，不是快照内容本身。因此 04 同样无法回答"HR 当初通过的到底是哪一版内容"。
3. 04 的方案比 06 更接近需求原文意图（S-013 括号内"可提示更新简历后重新投递"），且用唯一约束保证了数据整洁——**方向可取**，缺陷仅在于旧版快照被覆盖。

**编排层建议裁决**（供审计层复核后定稿）：采用 04 的"唯一约束 + 学生主动重投"骨架，修正其快照覆盖缺陷——将 snapshot 从 `app_application` 的 JSON 字段**外移为独立的 `app_snapshot` 版本表**（application_id + version_no + 各 JSON 字段），`app_application` 只保留 `current_snapshot_id` 指针。这样：唯一约束保留、重投语义保留、历史版本完整、HR 端可标注"该候选人已更新简历（第 N 版）"。增量成本约 0.5 人日。

### C-06 🔴 学生资料表与投递快照的字段冗余边界未定义

**描述**：04 设计了 7 张 `stu_*` 表存学生资料，同时在 `app_application` 存全量 JSON 快照。

**需审计确认**：
1. HR 端简历列表（H-004）的筛选字段（学校、专业、学历）是从 `stu_*` 表连表查，还是从快照 JSON 里取？
   - 从 stu_* 连表查 → **筛选结果与 HR 看到的快照内容可能不一致**（学生改了学校，列表按新学校筛，详情显示旧学校）
   - 从 JSON 取 → MySQL JSON 字段筛选**无法有效走索引**，H-004 要求的"多维度筛选排序"性能与实现复杂度都成问题
2. 正确做法通常是：快照中的**关键筛选字段冗余为 `app_application` 的普通列**（如 snapshot_school / snapshot_major / snapshot_degree），建普通索引，兼顾一致性与可索引性。

**处置要求**：审计层必须确认 04 的索引设计是否覆盖了这一点。若未覆盖，H-004 的"按学校、学历多维筛选"在实现阶段会返工。

### C-02 🔴 LibreOffice 串行队列的排队延迟，与"校招高峰期"场景是否匹配

**冲突来源**：工作流设计（06）第 5 节。

**描述**：方案定为单线程串行转换，自述"20 并发最差排队约 200 秒"。

**质疑点**：
- 校招投递存在**极端峰值**特征——宣讲会现场引导投递、投递截止日前夜，可能出现远超 20 并发的瞬时提交（这与"日常 20 并发"不是一回事）。若 100 名学生在 10 分钟内集中提交 Word 简历，串行队列积压将达 100×10s ≈ 17 分钟。
- 需要确认：转换延迟是否影响**学生侧**体验？（若上传即返回成功、转换在后台跑、学生不等待，则延迟只影响 HR 何时能预览，可接受）
- 队列容量设为 100，**超出后的拒绝策略**未见说明。若触发 `RejectedExecutionException`，学生上传会失败吗？

**需要裁决**：
1. 明确转换延迟只影响 HR 预览时效，不阻塞学生上传（若是，则串行方案可接受，但需在文档中写清）
2. 队列满时的降级策略必须显式定义（建议：入库标记为"待转换"，由定时任务 T2 兜底捞取，绝不因转换失败而让上传失败）
3. 建议补充：PDF 直传（无需转换）应是**主推荐格式**，在学生端上传处显式提示"推荐上传 PDF 格式，可即时预览"，从源头减少转换量

### C-04 🔴 学生端 JWT 有效期 7 天 与 简历数据敏感性的张力

**冲突来源**：接口设计（05）鉴权方案——学生端 JWT 有效期 **7 天**。

**质疑点**：
- 学生常在**公共设备**（学校机房、图书馆、宣讲会现场共用笔记本）登录投递。7 天长效 token 若落在公共浏览器 localStorage，后续使用者可直接接管账号，读取姓名/手机号/身份/教育经历等完整个人信息。
- 无状态 JWT **无法主动吊销**。学生点"退出登录"仅清前端存储，token 本身在服务端仍有效至过期。若学生发现账号异常，系统没有任何补救手段。
- 与 05 文档自身"不引入 Redis"的裁决叠加后，黑名单机制也无处安放（Caffeine 单机可存黑名单，但重启即失效）。

**需要裁决**：
1. 学生端 token 有效期是否应缩短（建议 access token 2 小时 + refresh token 7 天，refresh 落库可吊销）
2. 登出是否需要真正失效（建议 refresh token 落库，登出即删除记录）
3. 是否提供"在其他设备退出登录"能力

**编排层倾向**：refresh token 落库（一张小表，无需 Redis），access token 短效。成本极低，但把"无法吊销"这个真实风险消除了。个人信息保护法语境下，这属于应尽的安全措施。

### C-07 🔴 工作量估算跨文档严重不一致（数量级差异）

**冲突来源**：架构设计（03）与工作流设计（06）。

| 来源 | 估算 | 口径 |
|---|---|---|
| 工作流设计（06） | **P0 共 18 人日**，1 名全栈，约 4 周 | 仅业务流程实现部分 |
| 架构设计（03） | **方案A 59 人日 + 方案B 24 人日 = 83 人日**，1.0 全栈 + 0.5 前端，关键路径约 12 周，加 UAT 共 14 周 | 含环境骨架、RuoYi 去 Redis 化、两个前端工程、公网加固、恢复演练 |

**差异约 4.6 倍。** 这不是简单的加总差异，而是**口径根本不同**：06 只算了业务逻辑编码，03 覆盖了全生命周期（含前端两套工程、基础设施改造、安全加固、验收演练）。

**风险**：若最终方案对外只呈现某一个数字，会造成严重的排期误导。**14 周 vs 4 周对甲方是完全不同的立项决策。**

**处置要求**：审计层必须
1. 统一工作量口径（建议以 03 的全生命周期口径为准，因其覆盖面完整）
2. 将 05（接口设计）、04（数据设计）的估算并入同一张表，交叉核对是否重复计算或遗漏
3. 最终方案给出**一张唯一的工作量总表**，明确标注口径、人力假设、是否含 UAT、是否含缓冲
4. 特别核查：03 的"方案A 59 人日"与"方案B 24 人日"是**互斥选项**还是**叠加项**——若方案B是在方案A基础上的增量，表述需明确，否则易被误读为总量 83

### C-08 🟡 架构设计对 RuoYi 的"去 Redis 化"改造成本，未在选型阶段被计入

**描述**：架构设计指出 RuoYi 有 **7 个依赖点**需要去 Redis 化改造，并列出了改造表。

**问题**：技术裁决基线（00）当初选定 RuoYi 的理由是"开箱即用、覆盖 60% 系统管理端工作量"，但**默认 RuoYi 依赖 Redis 这一事实未被计入成本**。现在需要 7 处改造，等于开箱即用的前提被削弱。

**需审计确认**：
1. 去 Redis 化的 7 处改造总成本是多少人日？是否已包含在 03 的估算中？
2. 改造后是否会影响 RuoYi 后续版本升级（改动框架核心 = 升级困难）？
3. **替代方案对比**：直接保留 Redis（单机部署一个 Redis 服务，内存占用约 50MB）与改造 7 处相比，哪个总成本更低、长期维护更简单？
   - 裁决基线 00 当初排除 Redis 的理由是"20 并发无缓存压力"——这个理由成立，但**没有考虑"框架已依赖它"这一既成事实**
   - 若改造成本 > 3 人日，或会阻碍框架升级，则应重新评估"引入一个轻量 Redis"是否反而更符合"简洁"原则

**这是对裁决基线的合理挑战，审计层有权推翻 00 的相关裁决，但必须给出量化论证。**

### C-09 🟡 域名 ICP 接入备案（10–20 工作日）为新增的项目级阻塞项

**来源**：架构设计（03）上报的三个项目级阻塞项。

| 阻塞项 | 周期 | 状态 |
|---|---|---|
| 阿里云短信签名报备 | 15 工作日 | 已记录于 Q-04 |
| `campus.atmoto.cn` 子域 **ICP 接入备案** | **10–20 工作日** | **新增，此前未识别** |
| 甲方 IT 确认公网出口（固定 IP / 80-443 是否被运营商封禁 / 端口映射权限） | 未知 | **新增，且是方案B的全部前提** |

**严重性**：第三项若不成立（例如公司宽带无固定 IP、或运营商封禁 80/443 家宽端口——这在国内非常普遍），**整个方案 B 部署拓扑不可行**，需改为云服务器或专线，这将推翻"单台台式机部署"这一核心约束。

**处置要求**：这是**立项前必须确认的前置条件**，不是实施期问题。必须在最终方案的显著位置向甲方提示，并准备降级预案（如：仅门户部署到轻量云主机，HR 端与数据库仍在内网台式机）。

## 二、待甲方确认事项（🟡 需用户拍板，不由设计层擅自决定）

### Q-01 校招专用联系邮箱
官网页脚公示邮箱为 `market@atmoto.cn`（市场部）。校招门户页脚与自动通知的发件/联系邮箱不应使用该地址，需 HR 部门（人文发展部）提供专用邮箱（如 `hr@atmoto.cn` / `campus@atmoto.cn`）。
**影响**：门户页脚、邮件通知发件人、学生咨询入口。

### Q-02 公司地址口径
- 官网页脚：北京市海淀区上地信息路12号 **中关村发展大厦二层E座**
- 工商登记：北京市海淀区上地信息路12号1幢2层 **E207室**
两者为同一地点的不同表述。**编排层默认采用官网口径**（对外展示一致性优先）。如需变更请指出。

### Q-03 学生端是否需要公网访问
这是**决定部署拓扑的关键前提**。校园招聘的本质是外部学生投递，理论上必须公网可达；但若甲方计划仅在宣讲会现场用内网设备收集，则拓扑可大幅简化。
**影响**：域名/备案、HTTPS 证书、Nginx 反向代理、安全边界、防火墙策略、等保要求。
**编排层默认假设**：学生端需公网访问，HR 端仅内网访问。架构设计已按此出双拓扑方案。

### Q-04 短信服务的启动时机
阿里云短信企业实名认证 + 签名运营商报备需约 **15 个工作日**。这是**外部依赖，无法通过增加人力压缩**。
**风险**：若不提前启动，将阻塞学生端注册（S-001/S-002）的联调与验收。
**建议**：立项当日即并行提交申请。
**备选**：一期先用邮箱注册替代手机号注册（需甲方同意，会偏离需求文档 S-001）。

### Q-05 简历数据保留期限
《个人信息保护法》要求保存期为实现目的所需的**最短时间**。行业惯例：未录用候选人 1–2 年，已淘汰 6 个月–1 年。
**需甲方（人文发展部 + 法务）明确**具体天数，写入系统配置 `data_retention_days`。
**默认建议**：未录用 365 天，已淘汰 180 天，到期匿名化（保留统计维度，抹除个人标识）而非物理删除。

### Q-06 岗位类别的最终口径
编排层依据官网业务板块，建议按公司真实序列设置：**硬件研发**（电源/结构/控制/测试/工艺）、**软件研发**（数据平台/算法/前后端/低代码）、**职能**。
需甲方 HR 确认是否与其内部岗位序列划分一致——这直接影响岗位发布下拉项与报表分类维度。

### Q-07 是否需要等保备案
商业航天企业 + 公网系统 + 处理个人信息，可能触发**网络安全等级保护**要求（通常二级）。
本设计未按等保要求做专项设计（等保会显著增加成本：日志留存6个月、堡垒机、漏扫、测评费用等）。
**需甲方信息安全负责人确认**是否需要。若需要，方案需追加等保合规章节。
