- **RBAC 基座**：RuoYi-Vue 自带 `sys_user`、`sys_role`、`sys_menu`、`sys_dept`，已覆盖标准 RBAC

- **文件预览**：已决策使用 pdf.js 浏览器端渲染，LibreOffice Headless 做 Word 转 PDF

## 2. 外部参考资料

### 2.1 工作台 (Dashboard) 设计

#### 2.1.1 行业标准做法

**统计卡片交互模式**：

- 主流 ATS 系统（Greenhouse、Lever、Moka、北森）的工作台均采用**可点击的统计卡片**，点击后跳转到对应功能模块的已筛选视图。单纯静态展示的卡片仅用于"纯信息通知"类场景。
- 卡片的视觉层次：大数字（核心指标） > 小标签（指标名称） > 趋势箭头（环比变化）> 微文案（如"较上周 +12%"）。
- 通常展示 4-6 个核心 KPI 卡片，超出则使用分组折叠或 Tab 切换。

**最近动态/最近投递**：

- 行业通行做法是**时间线列表**（类似 GitHub 的 activity feed），每条动态包含：头像/图标 + 行为描述 + 时间戳，整行可点击跳转详情。
- 部分系统（如 Moka）采用"卡片流"模式，每张卡片展示投递者姓名、岗位、投递时间、状态标签。
- "最近投递"通常显示最近 5-10 条，底部有"查看全部"链接。
- 关键交互原则：**动态条目必须可点击导航**，纯文本列表被视为反模式。

**布局参考**：

| 系统 | 工作台布局 |
|------|-----------|
| 北森 | 顶部统计卡片行 → 左侧待办事项列表 → 右侧数据图表。功能入口以图标网格形式呈现 |
| Moka | 顶部 KPI 卡片（可点击）→ 下方左右分栏：左侧为"待处理"任务卡片列表，右侧为招聘漏斗概览 |
| 谷露 | 左侧快捷操作菜单 + 中间数据看板 + 右侧最近动态时间线，三栏布局 |
| Greenhouse | 顶部搜索栏 + 下方以"任务队列"为核心的 Kanban 视图，统计卡片在侧边栏 |

#### 2.1.2 推荐方案（适配本项目）

本项目规模小（几位 HR 同时使用）、部署为单体系统，推荐：

1. **统计卡片**：4 张卡片，全部可点击（待筛选简历数 → 跳转简历列表筛选视图，进行中岗位数 → 跳转岗位管理，本周新增投递 → 跳转投递列表，本月已发 Offer 数 → 跳转已完成列表）。点击时携带筛选参数（如 `?status=pending`）。

2. **最近动态**：单列时间线列表，显示最近 10 条投递记录。每条包含：学生姓名、投递岗位、投递时间（相对时间如"3 分钟前"）。点击跳转简历详情。

3. **布局**：采用上-下结构（而非左右分栏），适配 1920px 以下屏幕。统计卡片行 → 下方左右两栏（左：待处理任务快捷入口，右：最近投递时间线）。

#### 2.1.3 具体实现建议

- 统计卡片使用 Element Plus 的 `el-card` + `el-statistic`（或自定义），hover 时添加 `cursor: pointer` + 轻微阴影提升。
- 最近动态列表复用 `el-timeline` 组件，每条动态绑定 `@click` 跳转。
- 数据通过一个聚合 API 返回（`GET /api/hr/dashboard`），减少请求数。

### 2.2 岗位管理列表

#### 2.2.1 行业标准做法

**表格列排序**：

- **点击表头排序是事实标准**。用户点击列标题即切换排序方向（升序/降序/取消），当前排序列显示三角箭头指示器。
- 行业调研（Digital Artisans UX Polls）显示：**89% 的用户偏好点击表头排序**，仅 11% 偏好下拉菜单排序。
- NGroup 的研究指出：排序控件应紧邻列标题，而非放在表格外部——符合"就近原则"和电子表格的既有心智模型。
- 多列排序（Shift+点击）是高级功能，对本项目不必要。

**岗位分类层级展示**：

- 行业主流做法有三种：
  1. **树形表格**（如北森）：分类和岗位在同一张表格中，通过缩进 + 展开/折叠箭头体现层级，父行为分类，子行为岗位。
  2. **左树右表**（如谷露、Moka）：左侧 `el-tree` 展示分类树，点击分类节点后右侧表格刷新为该分类下的岗位列表。
  3. **面包屑筛选**（如 Greenhouse）：顶部面包屑显示当前分类路径，表格仅展示岗位，分类切换通过面包屑或下拉菜单。

- 对于分类数量少（<20 个分类）、岗位总数少（<200 个）的场景，**树形表格模式最简洁**，一次加载全部数据，前端完成展开/折叠。

#### 2.2.2 推荐方案（适配本项目）

本项目岗位类别属于公司组织架构层级（部门 → 岗位类别 → 岗位），推荐：

1. **采用左树右表布局**（谷露/Moka 模式，Element Plus 原生支持）：
   - 左侧 `el-tree` 展示"部门 → 岗位类别"两级树
   - 右侧 `el-table` 展示选中节点下的岗位列表
   - 点击根节点"全部岗位"显示所有岗位

2. **表格排序**：前端排序 + 后端排序混合。
   - 如果当前列表数据量 < 50 条（一次加载），使用前端排序（`sortable` 不带 `custom`）
   - 如果数据量可能增长，统一使用后端排序（`sortable="custom"` + `@sort-change`）

3. **默认排序**：按创建时间降序（最新岗位在前）。

#### 2.2.3 具体实现建议

- 左侧树使用 `el-tree`，配置 `highlight-current`、`node-key="id"`，绑定 `@node-click` 触发右侧表格数据加载。
- 右侧表格列配置 `sortable="custom"`，监听 `@sort-change` 事件，将 `{ prop, order }` 作为查询参数传给后端。
- 表格列建议：岗位名称、所属部门、岗位类别、招聘人数、状态（上架/下架）、创建时间、操作。
- Element Plus `el-table` 的 `tree-props` 在此场景不适用（因为需要展示不同列），左树右表是更灵活的选择。

### 2.3 简历管理详情页

#### 2.3.1 行业标准做法

**信息架构**：

| 模式 | 代表系统 | 适用场景 | 优点 | 缺点 |
|------|---------|---------|------|------|
| **左右分栏** | Greenhouse, Lever | 简历内容复杂、需要对照操作 | 简历常驻左侧，操作区在右侧，不丢上下文 | 窄屏(<1280px)体验差 |
| **上下布局** | 北森（部分页面） | 简历内容简单、移动端优先 | 响应式友好 | 长页面需要频繁滚动 |
| **Tab 切换** | Moka, 谷露 | 信息类型多且互斥（基本信息/简历预览/沟通记录/评价） | 信息组织清晰、不用滚动 | 切换 Tab 会丢失当前视图的上下文 |

- NNGroup 的研究明确指出：**Tab 适用于同级内容的"微导航"**，而左右分栏适用于"主内容 + 辅助操作"的场景。
- 对于简历详情页，行业主流是 **"左侧简历预览 + 右侧信息与操作面板"** 的分栏模式。左侧通常占 55-65% 宽度，展示 PDF/简历内容；右侧展示结构化信息（基本信息、教育经历、投递记录）和操作按钮。

**附件预览技术方案**：

| 方案 | 适用性 | 本项目适配度 |
|------|--------|------------|
| **pdf.js 内嵌** | PDF 预览的行业标准方案。Mozilla 维护，Firefox 内置使用。通过 `<iframe>` 加载 pdf.js viewer | **高**—已决策采用 |
| **浏览器原生 `<iframe>`** | 仅适用于用户已安装 PDF 插件的场景。移动端支持差、样式不可控 | 低—作为降级兜底 |
| **服务端渲染为图片** | 需要额外服务进程（如 LibreOffice + ImageMagick），延迟高、服务器负载大 | 低—仅在转换失败时做缩略图 |
| **Office Web Viewer** | 微软提供，但需公网可达的 URL，且数据经微软服务器 | **不适用**—简历数据不可出内网 |

- Dropbox 的实践表明：pdf.js 与宿主系统集成时需要处理安全隔离——他们的做法是将 pdf.js 放在独立子域，通过 `sandbox` iframe 加载。
- 对于本项目，已有决策使用 pdf.js 浏览器端渲染，Word 文档通过 LibreOffice 异步转 PDF 后同样走 pdf.js。

**HR 内部备注的交互模式**：

- 行业存在两种主流模式：
  1. **时间线模式**（如 Moka、Greenhouse）：备注按时间倒序排列，每条显示作者、时间、内容。适合"沟通记录"类场景——HR 与候选人的每次沟通、每次评审意见都形成一条时间线。不可编辑历史备注。
  2. **表单模式**（如部分传统系统）：单个富文本编辑区，覆盖式保存。适合"评审总结"类场景——一个候选人在一个阶段只有一条综合评价。
- **行业趋势是时间线模式**，因为它支持协作（多位 HR 对同一候选人各自添加备注），且天然形成审计追踪。

#### 2.3.2 推荐方案（适配本项目）

1. **信息架构**：采用**左右分栏 + 右侧 Tab** 的混合模式。
   - 左侧（约 55% 宽度）：简历附件预览区，使用 pdf.js 的 `<iframe>` 嵌入。
   - 右侧（约 45% 宽度）：使用 `el-tabs` 组织信息：
     - Tab 1 "基本信息"：姓名、手机号、邮箱、学校、专业、学历、毕业时间
     - Tab 2 "教育经历"：列表展示
     - Tab 3 "投递记录"：该学生对本公司所有岗位的投递历史
     - Tab 4 "内部备注"：时间线模式

2. **附件预览**：pdf.js 预构建文件部署在 Nginx 静态目录下。通过 `<iframe src="/pdfjs/web/viewer.html?file=/api/common/file/preview/{uuid}">` 加载。`/api/common/file/preview/` 端点做鉴权后返回文件流。iframe 添加 `sandbox="allow-scripts allow-same-origin"` 安全隔离。

3. **内部备注**：采用**时间线模式**，理由：
   - 一期虽只有一个 HR，但为二期多 HR 协作预留扩展
   - 时间线天然形成审计日志（满足合规要求）
   - 每条备注不可编辑（只能新增），防止篡改争议

#### 2.3.3 具体实现建议

- 使用 `el-timeline` 组件渲染备注时间线，每条备注卡片包含：HR 姓名、操作时间、备注内容。
- 底部固定一个输入区（`el-input` + 提交按钮），无需弹窗即可快速添加备注。
- 左右分栏使用 CSS Flexbox，左侧 `flex: 1 1 55%`，右侧 `flex: 1 1 45%`，最小宽度分别设为 480px 和 360px。屏幕宽度不足时自动切换为上下布局（`flex-wrap: wrap`）。
- 右侧基本信息区使用 `el-descriptions` 组件（Element Plus 提供），适合键值对展示。

### 2.4 分页交互

#### 2.4.1 行业标准做法

**前端分页 vs 后端分页**：

| 维度 | 前端分页 | 后端分页 |
|------|---------|---------|
| **适用数据量** | < 500 条 | 任意 |
| **首次加载** | 慢（全量数据） | 快（仅当前页） |
| **翻页速度** | 即时 | 取决于网络 |
| **搜索/筛选** | 前端过滤 | 后端查询 |
| **适用场景** | 字典数据、配置项、小列表 | 业务列表、管理后台、大数据量 |

- 企业级管理后台的主流选择是**后端分页**。RuoYi-Vue 框架已内置此后端分页模式。
- 前端分页仅在数据量确定很小（如岗位类别管理、字典配置）且不需要服务端搜索时使用。

**分页组件事件**：

- Element Plus `el-pagination` 提供多套事件体系：
  - **老版事件**：`@size-change`（每页条数变化）、`@current-change`（页码变化）
  - **v-model 绑定（推荐）**：`v-model:current-page="page"`、`v-model:page-size="pageSize"`
  - **统一事件（2.4.4+）**：`@change`（页码或每页条数任一变化时触发）

- RuoYi-Vue 3 的推荐实践是使用 `v-model:current-page` + `v-model:page-size`，配合 `@current-change` 和 `@size-change` 调用统一的 `getList()` 方法。

- **不需要** `@update:current-page` / `@update:page-size`（Vue 3 的 `v-model` 已内置双向绑定，这些是旧版写法导致的混淆）。

**分页参数命名**：

- 行业常见约定：`pageNum`(页码) + `pageSize`(每页条数)，RuoYi-Vue 沿用此约定。
- 部分现代 API 使用 `offset` + `limit`，但对于管理后台表格，`pageNum`/`pageSize` 更直观。

#### 2.4.2 推荐方案（适配本项目）

1. **统一采用后端分页**。所有涉及 `el-table` + `el-pagination` 的列表页均走后端分页。

2. **前端分页仅用于**：字典数据（如岗位类别下拉选项）、品牌配置项等不超过 50 条的小型数据集。

3. **事件处理模式**：
   ```javascript
   // 推荐写法（Element Plus + Vue 3）
   const page = ref(1)
   const pageSize = ref(10)
   const total = ref(0)

   const handlePageChange = (val) => {
     page.value = val
     getList()
   }

   const handleSizeChange = (val) => {
     pageSize.value = val
     page.value = 1  // 切换每页条数时重置到第一页
     getList()
   }
   ```

4. **每页条数选项**：`[10, 20, 50, 100]`。默认每页 10 条。这是管理后台表格的行业标准配置。

5. **分页器布局**：`total, sizes, prev, pager, next, jumper`（Element Plus 推荐布局），即：总数、每页条数选择器、上一页、页码、下一页、跳转输入框。

#### 2.4.3 具体实现建议

- 封装一个 `usePagination` composable，避免在每个列表页重复分页逻辑。
- 与 `@sort-change` 协同：排序变化时保持当前页码不变（若排序列变化）或重置到第一页（若数据量可能变动）。
- 搜索/筛选条件变化时**始终重置到第一页**——这是行业标准行为，避免"筛选后数据不足一页但停留在第 3 页显示空列表"的问题。
- 前端分页场景：若 RuoYi-Vue 的 `el-table` 数据源已全量加载，可直接使用 `el-table` 的 `data` 绑定并配合 `el-pagination` 做前端切片（`data.slice((page-1)*pageSize, page*pageSize)`）。

### 2.5 报表与分析

#### 2.5.1 行业标准做法

**招聘漏斗 (Recruitment Funnel) 标准计算方式**：

- **标准公式**：阶段转化率 = (进入下一阶段的候选人数 / 本阶段候选人数) x 100%
- **典型漏斗阶段**（校招场景）：投递 → 筛选通过 → 面试 → Offer → 接受
- **一期简化阶段**（本项目）：投递 → 待筛选 → 筛选通过 / 已淘汰

**关键指标**：

| 指标 | 公式 | 图表类型 |
|------|------|---------|
| 阶段转化率 | (下一阶段人数 / 当前阶段人数) x 100% | 漏斗图 |
| 整体转化率（入职率） | (入职人数 / 总投递数) x 100% | 数字卡片 |
| 各岗位投递量分布 | 按岗位统计投递数 | 柱状图（横向条形图） |
| 投递趋势 | 按天/周统计投递量 | 折线图 |
| 筛选通过率趋势 | 按周统计筛选通过率 | 折线图（含参考线） |
| 学历分布 | 按学历统计投递占比 | 饼图/环形图 |
| 学校来源分布 | 按学校统计投递量 Top N | 横向条形图 |
| 各阶段停留时长 | 进入阶段到离开阶段的平均天数 | 数字卡片 + 柱状图 |

**图表选择原则**（经行业验证）：

| 数据类型 | 推荐图表 | 不推荐 |
|---------|---------|--------|
| 随时间变化的趋势 | **折线图** | 柱状图（趋势不明显） |
| 类别间的比较/排名 | **横向条形图** | 饼图（超过 5 个类别时难以比较） |
| 占比/构成 | **环形图**（≤5 类）或 **堆叠柱状图**（>5 类） | 3D 饼图 |
| 阶段流转/转化 | **漏斗图** | 多个数字卡片 |
| 单一指标 | **数字卡片**（含环比趋势箭头） | 仪表盘（浪费空间） |

**时间维度筛选**：

- 最佳实践是提供**预设时间范围**（最近 7 天、最近 30 天、本月、本季、本年、本届校招）+ **自定义日期范围**。
- 校招场景的特殊时间维度：**按届次**（如 2026 届校招）是整个报表系统的时间锚点。
- 行业普遍在报表页面顶部放置统一的时间筛选器，所有图表联动。

#### 2.5.2 推荐方案（适配本项目）

由于一期报表需求为基本统计（投递量、筛选率、岗位分布），且系统不使用 ECharts 之外的图表库：

1. **图表类型映射**：
   - 投递量趋势（按天）→ 折线图
   - 各岗位投递量排名 → 横向条形图（Top 10）
   - 学历分布 → 环形图
   - 筛选通过/淘汰比例 → 环形图或堆叠柱状图

2. **招聘漏斗**：一期仅需展示"投递 → 待筛选 → 筛选通过/已淘汰"两级漏斗。使用两个数字卡片（待筛选数、已筛选数）配合占比环形图即可。完整的漏斗图（多阶段）留待二期状态流转实现后再做。

3. **时间筛选器**：顶部统一日期范围选择器，默认选中"本届校招开始至今"。

4. **图表库选择**：ECharts（Apache 2.0 协议，国内最成熟，与 Element Plus 生态兼容最好）。不引入商业图表库。

#### 2.5.3 具体实现建议

- 报表数据通过聚合查询计算，不在前端做二次统计。
- 后端提供 `GET /api/hr/report/overview`（概览数字卡片）、`GET /api/hr/report/trend?start=&end=`（投递趋势）、`GET /api/hr/report/distribution?type=job|school|degree`（分布数据）三个聚合端点。
- 报表页面采用**上-下布局**：顶部 4 张数字卡片 → 中部两列（左：投递趋势折线图，右：学历分布环形图）→ 下部全宽（各岗位投递量横向条形图）。
- 时间筛选器的变化触发所有图表的数据重新加载。

### 2.6 系统管理

#### 2.6.1 行业标准做法

**HR 账号管理的 RBAC 最佳实践**：

- 标准 RBAC 模型（用户-角色-权限）是 HR 系统的主流选择。属性级 ABAC（如"只能看本部门的简历"）通常作为 RBAC 的补充而非替代。
- 关键实践：
  1. **预置角色模板**：系统自带"超级管理员"和"HR"两个角色，覆盖 80% 场景。自定义角色按需创建。
  2. **权限粒度**：权限以"菜单+按钮"为最小单位（RuoYi-Vue 已有此模型）。对于简历数据，额外增加**部门数据权限**（本部门、本部门及以下、全部）。
  3. **最小权限原则**：默认角色仅授予完成本职工作所需的最小权限集。
  4. **职责分离**：创建岗位与发布岗位可为不同权限点（如果未来有多 HR 审批流程）。
  5. **操作审计**：RuoYi-Vue 自带的 `sys_oper_log` 已覆盖此需求。

- WorkOS 的多租户 RBAC 指南强调：**为每个租户（部门）建立独立的权限视图**，通过 `dept_id` 在查询时自动注入数据过滤条件。本项目不是 SaaS，但"部门数据隔离"需求类似。

**学生用户与 HR 用户统一管理 vs 分开管理**：

| 维度 | 统一管理（同表） | 分开管理（分表） |
|------|----------------|----------------|
| **认证方式** | 必须统一（如都是密码登录） | 可各自独立（学生用短信验证码、HR 用密码） |
| **安全隔离** | 低——一次 SQL 注入可能同时泄露两类用户 | **高**——拖库影响面减半 |
| **字段需求** | 必须统一字段结构，存在大量 NULL | 各自按需设计字段 |
| **运维复杂度** | 低——一套 CRUD | 中——两套 CRUD |
| **功能扩展** | 困难——一个字段的变更影响两类用户 | 灵活——各自独立演进 |
| **行业做法** | 简单 CMS 系统常用 | **ATS/HR 系统几乎全部采用** |

- 北森、Moka、谷露均采用分开管理：HR 账号在企业组织架构下管理，候选人（学生）数据在独立的候选人库中。
- 本项目的技术方案已明确决策：**学生用 `stu_user`，HR 用 RuoYi 的 `sys_user`**，两者分表。此决策符合行业最佳实践。

#### 2.6.2 推荐方案（适配本项目）

1. **HR 账号管理**：直接复用 RuoYi-Vue 的用户管理模块（`sys_user` + `sys_role` + `sys_menu`），无需自建。
   - 预置角色：超级管理员（全部权限）、HR（岗位管理+简历管理+报表查看，不含系统管理）
   - 预置权限点（菜单权限）：岗位管理（含创建/编辑/上下架/删除）、简历管理（含查看详情/筛选操作/导出/下载）、报表中心（查看）、系统管理（仅超管可见）
   - 预置数据权限：按部门隔离（HR 默认只能看到本部门的岗位和投递）

2. **学生用户管理**：独立于 RuoYi 用户体系，但可在系统管理端提供一个只读的"学生用户列表"页面（不含密码等敏感字段），方便 HR 查看注册情况。

3. **不需要多租户设计**：本项目为单公司使用，部门数据权限通过 RuoYi 的 `dataScope` 机制即可实现，不需要引入 tenant_id 隔离。

#### 2.6.3 具体实现建议

- RuoYi-Vue 的用户管理模块已自带动画 CRUD、角色分配、密码重置，无需重复开发。
- 部门数据权限配置：在 RuoYi 角色管理 → 数据权限中设置"本部门数据"或"全部数据"。
- 简历查询接口自动注入数据权限过滤：
  ```sql
  -- 伪代码，实际通过 RuoYi 的 DataScope 注解实现
  SELECT * FROM app_application 
  WHERE dept_id IN (当前HR角色的数据权限范围)
  ```
- 学生用户列表页：调用 `stu_user` 表，仅展示姓名、学校、注册时间、投递次数，**不展示手机号（脱敏）和密码哈希**。

## 3. 关键发现

### 3.1 最值得借鉴的方案

| 序号 | 方案 | 借鉴要点 | 来源 |
|------|------|---------|------|
| 1 | **Moka 工作台设计** | KPI 卡片可点击导航、左右分栏（待处理+漏斗概览）、时间线动态列表 | 行业竞品分析 + 知乎/CSDN 测评 |
| 2 | **Element Plus 树形表格** | `el-table` 的 `tree-props` + `lazy` 实现部门→岗位层级 | Element Plus 官方文档 + CSDN 实战案例 |
| 3 | **pdf.js + iframe 沙箱** | 简历预览的标准方案，`sandbox` 属性安全隔离 | Mozilla pdf.js + Dropbox 工程实践 |
| 4 | **Moka/Greenhouse 备注时间线** | `el-timeline` 实现不可编辑的沟通记录流 | ATS 竞品功能分析 |
| 5 | **RuoYi-Vue 分页模式** | `v-model:current-page` + `@current-change` → `getList()` 的标准模式 | RuoYi-Vue 官方文档 + Element Plus Pagination API |
| 6 | **ECharts 报表体系** | 趋势→折线、排名→条形、占比→环形、漏斗→漏斗图 | 行业数据分析最佳实践 |
| 7 | **RuoYi RBAC + 部门数据权限** | 菜单权限 + 按钮权限 + 部门数据隔离三级模型 | RuoYi-Vue 自带 + WorkOS RBAC 指南 |

### 3.2 明确不推荐的方案

| 方案 | 排除理由 |
|------|---------|
| **3D 图表** | 降低数据可读性，违反数据可视化最佳实践，Element Plus/ECharts 均不推荐 |
| **无限滚动分页** | 适用于社交信息流而非管理后台数据表；用户无法定位、无法跳转到特定页 |
| **纯前端分页（大数据量）** | 首次加载慢、内存占用大；RuoYi-Vue 的后端分页模式已成熟 |
| **服务端渲染 PDF 为图片** | 服务器负载高、延迟大、图片质量不如浏览器渲染；pdf.js 已是行业标准 |
| **IFrame 直接嵌入 PDF 文件 URL** | 无鉴权保护、无安全隔离；简历附件需通过鉴权代理端点提供 |
| **学生与 HR 共用用户表** | 认证方式不同（短信 vs 密码）、字段不同、安全风险高；行业无此先例 |
| **仪表盘/Gauge 图表** | 浪费空间、不适合展示招聘指标；数字卡片 + 趋势箭头更高效 |

### 3.3 项目独有的差异化需求

以下需求是外部通用方案无法直接覆盖的，需要在设计阶段重点关注：

1. **单机 Windows 部署下的报表性能**：外部 ATS 系统大多部署在 Linux 服务器或云环境，其报表方案通常依赖 Redis 缓存或定时预计算。本项目的报表需在无缓存中间件的情况下保证查询性能——建议通过 MySQL 索引 + 后端聚合查询 + 简单的定时预计算（Spring `@Scheduled` 在凌晨生成汇总数据）来弥补。

2. **LibreOffice 异步转换的用户体验**：外部系统要么不支持 Word 预览（要求 PDF 格式），要么使用商业文档转换服务。本项目使用 LibreOffice headless 做异步转换，需要设计"转换中"的等待态 UI（骨架屏 + 进度提示），这是通用 pdf.js 方案不涉及的部分。

3. **内网 HR + 公网学生门户的双网部署**：外部 ATS 全部是 SaaS 单域名部署。本项目的双网隔离架构（公网 Nginx 只放行 `/api/portal/`）需要特别注意文件预览端点（`/api/common/file/preview/`）的路由配置——该端点对 HR（内网）和学生（公网，仅自己的简历）均需可用，需要 Nginx 白名单放行。

4. **学生投递后修改简历的快照版本机制**：外部 ATS 一般投递后不允许修改简历，或修改后不保留历史版本。本项目设计了"简历快照独立版本表"——HR 查看的是投递时刻的简历快照，学生端展示的是最新版本，HR 端可见"该候选人已更新简历（第 N 版）"。这是一个差异化设计，需要在详情页 UI 中清晰呈现版本切换交互。

5. **极简运维约束下的系统管理**：外部系统有专门的运维团队，系统管理功能可以很复杂。本项目无专职运维，系统管理功能必须"零学习成本"——品牌配置、岗位类别管理、HR 账号管理全部需要极简的 UI 和明确的操作反馈。

1. **[高] Element Plus Table 组件文档** — https://element-plus.org/en-US/component/table

   为什么重要：分页事件命名 (`@current-change` vs `@size-change` vs `@change`)、`v-model` 绑定方式的权威参考。避免因事件名称写错导致分页不生效。
