# 岗位设置优化方案 V1.0

> **文档状态**：✅ 已实施（2026-08-10）  
> **创建日期**：2026-08-10  
> **关联模块**：岗位类别、岗位模板、岗位管理  
> **审查方法**：四Agent并行探索 + 设计审计红队审查

---

## 一、执行摘要

通过对岗位类别（job_category）、岗位模板（job_template）、岗位管理（job_position）三个模块的全链路代码审查，共发现 **19个问题**：4个Critical（阻塞上线）、7个High（重要缺陷）、6个Medium（改善建议）、2个Low（优化建议）。

**核心结论**：三个模块的基础CRUD功能完整，但存在四个"上线即故障"的阻塞性问题，以及若干数据一致性、操作流程、安全风险方面的设计缺陷。建议按优先级分批修复后上线。

## 三、问题清单（按严重程度排序）

### 🔴 Critical（阻塞上线，共4项）

#### C-1：status字段语义四重矛盾

| 来源 | 约定 | 位置 |
|------|------|------|
| DDL注释 | `'0'=启用, '1'=停用` | `init-schema.sql:187` |
| 种子数据 | 8条记录全部 `status='1'` | `init-data.sql:78-86` |
| Controller | `"1"=启用`, `"0"=禁用` | `JobCategoryController.java:97` |
| Portal查询 | `eq(status, "0")` → 查禁用 | `PortalJobServiceImpl.java:149` |

**影响**：Portal端`getFilterOptions()`查询`status='0'`，种子数据全部`status='1'`，学生端"岗位类别"筛选下拉框**永远为空**。P0必做功能S-011"多条件筛选"的类别维度完全不可用。

**修复**：
1. 统一约定`'0'=禁用, '1'=启用`（与RuoYi体系中`sys_dept.status`惯例对齐）
2. 修正DDL注释
3. Portal端`getFilterOptions()`改为`eq(status, "1")`

---

#### C-2：Portal端筛选类别children字段缺失

**现状**：`getFilterOptions()`返回平铺`List<JobCategory>`，实体类无`children`字段。前端`JobListView.vue`用`v-for="child in cat.children"`遍历——`cat.children`永远是`undefined`。

**影响**：Portal端岗位类别筛选器的子类别不显示。学生只能看到父级（硬件研发/软件研发/职能），看不到子级（电源/结构等）。

**修复**：
1. 在`getFilterOptions()`中对categoryList调用`buildCategoryTree()`构建嵌套树
2. `JobCategory`实体添加`@TableField(exist = false) List<JobCategory> children`
3. 完善`buildCategoryTree()`的`attachChildren()`方法

---

#### C-3：hasApplied投递状态字段完全缺失

**现状**：前端`JobDetailView.vue`判断`job.hasApplied`决定按钮状态，后端`PortalJobVo`未定义此字段，`selectJobDetail()`未查询`app_application`表。

**影响**：
1. 已投递学生看不到"已投递"状态，可能重复点击
2. 重复投递触发数据库`uk_student_job`唯一约束异常，学生看到不友好的错误提示
3. 违反需求S-013"同岗位防重复"的UX要求

**修复**：
1. `PortalJobVo`添加`private Boolean hasApplied`字段
2. `selectJobDetail()`中查询当前登录用户是否已投递该岗位
3. 匿名用户`hasApplied`设为`false`

---

#### C-4：URL query传递MEDIUMTEXT字段

**现状**：模板"使用创建岗位"通过URL query传递全部字段（含`description`和`requirement`——MEDIUMTEXT类型，可达16MB）。浏览器URL长度上限约2000字符（部分代理/防火墙截断到2083）。

**影响**：当模板岗位描述超过~1500中文字符时，URL被截断，HR在不知情下创建内容残缺的岗位。

**修复**：改为只传`templateId`，`JobForm.vue`在`onMounted`中通过API请求模板详情获取完整数据。

---

### 🟠 High（重要缺陷，共7项）

#### H-1：种子数据缺失9条子类别

设计文档规划16条（3父+5硬件+5软件+4职能），实际仅8条。软件研发（算法/前端/后端/数据/测试）和职能（人力/财务/行政/法务）的子类别完全缺失。

**修复**：补全`init-data.sql`中缺失的9条子类别种子数据。

#### H-2：HtmlUtils.htmlEscape破坏富文本

`JobAdminController.add()`对`description`和`requirement`调用`HtmlUtils.htmlEscape()`。DDL注释写明"富文本HTML"，但转义后HTML标签变成纯文本，Portal端`v-html`渲染出源码标签文本。

**修复**：用Jsoup等HTML清洗库替代`htmlEscape`——保留安全标签，移除危险标签和事件属性。

#### H-3：删除类别不检查岗位/模板关联

`deleteJobCategoryById()`仅检查子类别（`hasChildren`），不检查：
1. `job_position`表中是否有关联岗位 → 删除后category_id悬垂
2. `job_template`表中是否有关联模板 → 删除后模板category_id悬垂
3. `hasChildren`未加`del_flag='0'`条件 → 已逻辑删除的子类也阻止父类删除

**修复**：删除前检查三类关联，存在则拒绝并提示。

#### H-4：禁用类别不检查已发布岗位

`toggleStatus()`禁用类别时，不检查是否有关联的`status='PUBLISHED'`岗位。禁用后这些岗位在学生端筛选器中不可达，但岗位仍存在——HR可能完全没意识到副作用。

**修复**：禁用时检查关联的已发布岗位数，存在则弹出确认提示。

#### H-5：parent_id的NULL vs 0约定不一致

DDL定义`DEFAULT NULL`（暗示NULL=顶级），种子数据用`parent_id=0`表示顶级。`buildCategoryTree()`兼容了两种判断，但两种约定并存增加维护风险。

**修复**：统一约定`parent_id=0`表示顶级，修改DDL为`DEFAULT 0 NOT NULL`（与RuoYi `sys_dept`一致）。

#### H-6：设计文档种子数据与代码不符

`04-数据架构设计.md`规划16条数据、status全`'0'`，实际代码仅8条、status全`'1'`。设计文档与实际代码严重脱节。

**修复**：补全数据后，同步更新设计文档中的种子数据描述。

#### H-7：job_category表与job_position表无外键约束

两表之间仅通过应用层`category_id`关联，无数据库级外键。删除类别后存在"幽灵岗位"——岗位存在但category_name为空、筛选器不可达。

**修复**：应用层增加关联检查（同H-3），数据库层可选加外键（需评估对现有数据的影响）。

### 🟡 Medium（改善建议，共6项）

#### M-1：EXPIRED枚举定义但从未使用

`JobStatus`定义了`EXPIRED`枚举，字典表预置了`EXPIRED`，但`JobExpireTask`将过期岗位设为`CLOSED`。HR无法区分"手动下架"与"到期自动下架"。

**修复**：`JobExpireTask`改为设置`EXPIRED`状态，或删除EXPIRED枚举（确认不需要后）。

#### M-2：buildCategoryTree的attachChildren为空壳

`/tree`接口调用`buildCategoryTree()`但`attachChildren()`方法体为空。返回数据名义上是"树"，实际是平铺列表。

**修复**：完整实现`attachChildren()`递归挂载子节点（与C-2修复联动）。

#### M-3：定时任务逐条更新而非批量

`JobExpireTask`用for循环逐条`updateById()`。当前岗位数少影响可忽略，但不符最佳实践。

**修复**：改为批量SQL：`UPDATE job_position SET status='EXPIRED' WHERE status='PUBLISHED' AND deadline < NOW()`

#### M-4：hasChildren未过滤del_flag

逻辑删除的子类别仍被计数，导致无法删除"所有子类均已删除"的父类别。

**修复**：`hasChildren()`增加`.eq(JobCategory::getDelFlag, "0")`。

#### M-5：/list与/tree接口语义不一致

`/list`返回全部类别，`/tree`仅返回`status='1'`的。同一数据两个接口返回不同结果，增加前端使用困惑。

**修复**：`/tree`增加可选参数`includeDisabled`，`/list`支持status过滤参数。

#### M-6：category_code自动生成UUID前8位

前端未填`categoryCode`时，后端用`UUID.randomUUID().toString().substring(0, 8)`生成（如`a3f2b1c0`），不可读且低概率碰撞。

**修复**：前端已设必填规则，移除后端自动生成逻辑（或改用`parentCode + "_" + timestamp`）。

### 🟢 Low（优化建议，共2项）

#### L-1：view_count非原子操作

`selectJobDetail()`先SELECT再UPDATE SET view_count+1，极低概率下并发丢失一次计数。当前20并发下可忽略。

#### L-2：模板"使用创建岗位"的XSS风险

当前影响小（textarea不执行脚本），但URL承载HTML的设计本身存在安全隐患（同C-4修复后自动消除）。

## 四、操作流程问题

### 4.1 三模块独立无引导

当前三个模块在侧边栏中并列展示，但逻辑上是**递进依赖关系**：

```
岗位类别 ──▶ 岗位模板（可选）──▶ 岗位管理
 (先建)        (基于类别建)        (基于类别+模板建)
```

**问题**：
- 新HR用户可能不知道先建类别才能建岗位
- 岗位创建表单中类别级联选择器为空时，无引导提示"请先到岗位类别页面创建类别"
- 模板创建表单中类别下拉为空时，无引导提示

### 4.2 岗位模板的角色定位模糊

- DDL注释标注"一期建表不实现业务逻辑"——但代码已完整实现
- 设计文档标注P1（效率增强）——但无预置种子数据
- 模板与岗位字段高度重叠（9/10字段相同），差异仅在于模板多了`templateName`、岗位多了`deadline`/`status`
- HR需要手动创建模板才能体验模板功能——零模板预置降低了功能发现率

### 5.2 流程优化建议

#### 建议1：岗位类别树全面补全

按公司业务序列完整搭建类别树：

```
硬件研发                    软件研发                    职能
├── 电源                    ├── 算法工程师               ├── 人力资源
├── 结构                    ├── 前端开发                 ├── 财务管理
├── 控制                    ├── 后端开发                 ├── 行政管理
├── 测试                    ├── 数据平台                 └── 法务合规
└── 工艺                    └── 测试开发
```

#### 建议2：岗位模板预置种子数据

为每个父级类别至少提供一个预置模板（如"电源工程师（初级）"、"前端开发工程师（校招）"），提升功能发现率。

#### 建议3：增加上下文引导

- 岗位创建页：类别级联选择器为空时显示"暂无可用类别，请先创建"的Empty提示+快捷跳转链接
- 模板创建页：同理
- 岗位列表页：无岗位时显示"创建第一个岗位"引导卡片，区分"从模板创建"和"从空白创建"

#### 建议4：岗位状态优化

- `EXPIRED`状态正式启用，区分"手动下架(CLOSED)"和"到期自动下架(EXPIRED)"
- 岗位列表页增加"到期日期"列，距到期<7天高亮黄色预警
- 支持HR手动"延期"操作（延长deadline并保持PUBLISHED状态）

### 5.3 架构微调建议

#### 模板与岗位的字段冗余治理

当前`job_template`表有10个字段与`job_position`表重叠。建议：

- **方案A（轻量）**：保持现状。模板是"快照"，不与岗位实时同步，符合"模板辅助创建"的定位
- **方案B（重构）**：模板改为引用式——`job_template`只保留`template_name`和`job_position`的外键引用。创建岗位时先保存草稿，模板只记录引用关系。**不推荐**，增加复杂度且不符合P1定位

建议采用方案A，保持当前设计。
